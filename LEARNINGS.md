## Log

### 2026-08-20

- Building issue #149's contrast-check CI job surfaced two Playwright quirks worth remembering for any future Playwright tooling in this repo. (1) The declarative `use.reducedMotion: 'reduce'` config option didn't reliably reach the page's own `matchMedia('(prefers-reduced-motion: reduce)')` in this Playwright version — confirmed by A/B testing the same real spec run with only the config option vs. only an explicit `page.emulateMedia({ reducedMotion: 'reduce' })` call; only the imperative call worked. (2) `test.beforeAll` in a `fullyParallel` multi-worker config runs once _per worker_, not once globally — using it to clear `contrast-results/` before writing caused a real race, since a later-starting worker's cleanup could delete a file an already-running worker had just written. Fixed with Playwright's `globalSetup`, which genuinely runs once in the main process before any worker starts. Both fixes are in `e2e/contrast.spec.ts`/`playwright.contrast.config.ts`/`e2e/contrast.global-setup.ts`, with the reasoning as inline comments rather than promoted to CLAUDE.md — narrow to this one feature, not a repo-wide convention.
- Answering "why isn't issue #106's border-contrast tradeoff in the allowlist" (user question, same issue #149 work) required actually checking `axe-core`'s rule set rather than assuming the checker's scope — `axe.getRules()` shows exactly two contrast rules, both text-only (`color-contrast` WCAG 1.4.3 AA, `color-contrast-enhanced` WCAG 1.4.6 AAA); there is no non-text/UI-component contrast rule (WCAG 1.4.11) in axe-core's stable set at all, so the border tradeoff can never be flagged, allowlist or not. Separately, in the same session, confirmed empirically that axe's selector-generation algorithm strongly prefers `id` over any `data-*` attribute when producing a violation's target selector — an element with only a `data-*` marker and no `id` still fell back to an ambient utility class. Both promoted into [CLAUDE.md](CLAUDE.md)'s new `contrast` job bullet.
- Verifying a GitHub Actions PR-comment-posting feature locally (mocking/dry-running the aggregation script) isn't sufficient confidence that it works — real GitHub API behavior (comment pagination past 30, fork-PR token permissions, the sticky-comment upsert actually finding and updating the right comment) can only be checked against a real run. Did this by temporarily emptying `contrast-allowlist.json`, pushing to the already-open PR, confirming a real comment appeared, then restoring it and confirming the _same_ comment updated in place rather than duplicating — worth the extra two throwaway commits given the user directly asked whether it had actually been tested.
- Building issue #156's deploy-notification relay, Netlify's own docs (`docs.netlify.com`, `open-api.netlify.com`) didn't reliably answer "what does the deploy webhook's `admin_url` field actually contain" — WebFetch summaries of both were vague or inconsistent on whether it's per-deploy or site-general. Got ground truth instead by calling the already-authenticated CLI directly (`netlify api listSiteDeploys --data '{"site_id":"..."}'`) against the live site: confirmed `admin_url` is the general project page, not deploy-specific, so the deploy-specific link needed building as `${admin_url}/deploys/${id}`. Lesson: for "what does this real API actually return" questions, a live authenticated CLI/API call beats doc-scraping when the CLI is already logged in.
- Fire-and-forget webhook relays are easy to falsely believe you've tested: `deploy-notification.ts` (issue #156) always returns `204` regardless of whether its downstream Slack POST actually succeeded, so a passing test against a local fake echo-server endpoint doesn't prove real delivery. Got genuine confidence by additionally POSTing the exact same message body directly to the real Slack Incoming Webhook URL and checking Slack's own response (`200 ok`), separate from exercising the function through `netlify dev` — worth repeating for any future fire-and-forget relay in this repo.
- Bundled two related `self-review` findings on issue #156 (Netlify webhook signature verification; `postToSlack()` never checking `response.ok`) into one GitHub issue (#157) instead of two, since both are the same underlying gap — these Netlify Functions trust their input/output uncritically — and fixing them touches the same shared helper. See [CLAUDE.md](CLAUDE.md)'s `_shared/slack.ts` bullet for the known-gap cross-reference.

Lesson: when two automated reviews disagree, re-derive the answer from the actual markup/values rather than deferring to either review's framing — "different reviewers say different things" isn't itself evidence either is right.
- Reversed the `font-variation-settings: 'opsz' NN` work from the previous session's #107 CSP follow-up (the bracket-class-to-named-`.opsz-*`-class centralization documented below on 2026-08-18): the user tested it directly by disabling the property in browser devtools and found zero visible effect for Fraunces Variable as actually rendered on this site, contradicting the assumed "optical size axis meaningfully changes letterforms at different sizes" rationale that justified converting rather than deleting it. Removed entirely — all 18 call sites, the 5 `.opsz-*` classes in `global.css`, and the CLAUDE.md documentation describing them — rather than kept as now-inert dead CSS. Lesson: general knowledge about a CSS/font feature ("variable fonts' opsz axis does X") is not the same as verifying it does X _for this specific font file as actually loaded_, especially when it's this quick for the user to check empirically — should have either verified in a real browser before centralizing the pattern, or asked, rather than writing a confident-sounding justification for a decorative choice nobody had asked for.
- Issue #118 (`ThemeToggle` briefly shows the wrong active segment on load) took three attempts to actually fix, each caught by checking against a real browser instead of trusting that it compiled and passed the existing suite: (1) the issue's own suggested fix — a lazy `useState(() => ...)` initializer reading `localStorage` — server-renders `'system'` at build time (`client:load` SSRs, no `localStorage`) and then mismatches that on hydration; React 19 doesn't patch attribute-level hydration mismatches ("This won't be patched up," logged to console), so the toggle got permanently stuck on `'system'` for any visitor with a stored theme, worse than the original bug. (2) Switching the correction to `useLayoutEffect` (fires before the browser's next paint) avoided the mismatch but didn't fix the user-visible complaint at all — the SSR-baked `'system'` markup still paints first regardless of which React effect later corrects it, and the user caught the flash still happening in a real reload. (3) The actual fix: a second `<script is:inline>` in `Header.astro`, positioned right after `<ThemeToggle client:load />`, that synchronously (classic script, not a deferred module) patches the buttons' `aria-pressed`/class attributes from `localStorage` before hydration ever runs — mirroring `BaseLayout.astro`'s existing dark-mode pre-paint script. `ThemeToggle.tsx`'s lazy initializer computes the identical value, so hydration's client render matches what the script already put in the live DOM (hydration compares against current DOM state, not original network bytes) — no mismatch. This surfaced a second, unrelated blocker: the new `is:inline` script was silently blocked by CSP in a real `netlify serve` build despite the header's `'unsafe-inline'`, because Astro's auto-generated CSP `<meta>` tag is a second, independent, hash-only policy that also applies to it, and Astro doesn't auto-hash author-written `is:inline` scripts (only its own processed ones) — fixed by manually computing the script's SHA-256 and registering it via `security.csp.scriptDirective.hashes` in `astro.config.mjs` (documented there and in [CLAUDE.md](CLAUDE.md)'s ThemeToggle bullet, including how to recompute it if the script ever changes). Verified with Playwright against the actual `netlify serve` build (not `astro dev`, since the CSP `<meta>` only exists in `build`/`preview` output): blocking every hydration `.js` request still left the toggle showing the correct segment, and polling under 20x CPU throttling from the earliest possible moment never observed the wrong one. Also: an orphaned `astro dev` daemon from manual testing (the exact process documented in this file's 2026-06-25 entry) caused 10 unrelated e2e failures on the first post-fix `npm test` run — `lsof -ti:4321` found the real PID that plain `pkill` had missed again, and killing it plus clearing `node_modules/.vite` restored a clean 108/108 pass, confirming the failures were stale-cache noise, not a real regression.
- Removing it surfaced a real, separate gotcha worth its own note: after deleting all source references, a fresh `npm run build` (with `dist/`, `.astro/`, and `node_modules/.vite` all removed first, ruling out a stale build cache) still emitted CSS for the exact opsz-72 bracket-value class that used to be used site-wide. Root cause: Tailwind v4 needs no content config and auto-scans every git-tracked file for class-name-shaped patterns, and CLAUDE.md's own prose still contained that literal bracket string as a "here's the syntax we used" example. Tailwind doesn't know or care that the string was inside a markdown code span describing past work rather than actual markup — it pattern-matches and generates the utility regardless. Fixed by rewriting the CLAUDE.md passage to describe the pattern without embedding the literal now-unused value (worth noting: writing that literal string out even once more, anywhere a future build might scan, reintroduces the exact same dead-CSS bug this entry is about — described here in prose instead of by example for that reason). General lesson: don't write a real Tailwind arbitrary-value bracket string in prose documentation for a value that isn't _also_ genuinely used somewhere in `src/` — Tailwind's content scanning doesn't distinguish "used in markup" from "mentioned in a doc example," so an unused example silently ships as dead, real CSS.

- Writing `e2e/contact-form.spec.ts` (#113) hit an Astro-islands hydration race: `ContactForm` is `client:load`, and a Playwright click landing before hydration attaches the React `onSubmit` handler falls through to a _real native form submission_ (`method="POST"`, no `action` — posts to the current page), reloading the page and wiping test state. Fixed by intercepting `POST` requests to `/` and checking `route.request().isNavigationRequest()`: when true (the unhydrated case), fulfilling with status `204` makes Chromium treat it as "cancel navigation, leave the current document as-is" (a known no-op-navigation trick), so a `toPass()` retry can safely re-click once hydration completes. Separately, that same retry-around-an-async-click pattern exposed a genuine double-submit bug on the success path: a retry could fire a second click while the first submission's `handleSubmit` was still in flight, and since success calls `form.reset()` before React's re-render swaps to the confirmation view, the second call read already-cleared `FormData`, producing a spurious validation-error render instead of the confirmation. Fixed in `ContactForm.tsx` itself with `if (status === 'submitting') return` at the top of `handleSubmit` — real UX hardening (blocks duplicate network requests from rapid double-clicks), not just a test workaround.
- Follow-up, twice over: the `toPass()`-retry-wrapped-click workaround above (and a later refinement moving `.fill()` inside the retry, verified with 3 consecutive local full-suite runs) both looked fully fixed locally but still failed intermittently in GitHub Actions CI once #109 landed (`client:load` → `client:visible`) — CI's slower/more-constrained runners made pre-hydration clicks land more often, and retrying a reactive workaround just retries into the same race, not away from it. Replaced the whole retry-based approach with a **deterministic** hydration-complete check: `page.waitForFunction()` polling for the submit button DOM node to carry a React-internal `__reactProps$...` key (proof React actually attached to that element), awaited once before any interaction, no retry loop needed afterward. Verified this holds under real adversity, not just repetition: passed 80/80 runs locally, 40/40 under CI's exact `workers: 1` config, and correctly detected hydration (591ms) and behaved correctly under Chrome DevTools Protocol 6x CPU throttling (`Emulation.setCPUThrottlingRate`) simulating a much slower runner. General lesson: a flake that "passes reliably locally" after a fix is not evidence the fix addressed the actual race if the fix is still reactive (retry-after-failure) rather than deterministic (wait-for-true-precondition) — CI hardware/scheduling differences can expose exactly the timing window a local machine never hits, and the fix that actually closes a race is the one that removes the race's precondition, not the one that recovers from it faster.
- Implementing issue #107 (CSP hardening) with Astro's built-in `security.csp` (astro.config.mjs), a multi-agent `self-review` pass surfaced — and a targeted follow-up experiment confirmed — that the auto-generated `<meta>` CSP does **not** actually cover `BaseLayout.astro`'s dark-mode `is:inline` script, despite CLAUDE.md's first-draft documentation claiming it did. Root cause: a `<meta http-equiv="Content-Security-Policy">` tag only governs content parsed _after_ it in the document (CSP spec behavior, not an Astro bug), and Astro places its auto-generated meta tag late in `<head>` (it has to, since it needs to have seen the whole page first) — while `BaseLayout.astro` necessarily renders `<ClientRouter />` and the dark-mode script early in `<head>`, before Astro's meta tag, so both are structurally exempt from it. Confirmed two ways: computed the dark-mode script's exact SHA-256 from a real build and searched the generated meta content (absent), then temporarily stripped `netlify.toml`'s header `'unsafe-inline'` and watched dark mode break outright, with the browser's own CSP violation message citing exactly that hash as what would be needed. The header's `'unsafe-inline'` is genuinely the only thing protecting any `BaseLayout.astro`-authored `<head>` content — the meta CSP's real, verified value is hardening everything Astro places in `<body>` (island hydration, `ImageLightbox.astro`), which is also where a realistic XSS-injected script would actually land. Corrected CLAUDE.md to state this precisely rather than the earlier blanket "security.csp hardens script-src" framing. Lesson: a claim like "verified: injecting an arbitrary script gets blocked" is not equivalent to "every script on the page is covered" — the position of the _injection point relative to the CSP delivery mechanism_ matters, and a meta-tag CSP's coverage boundary needs checking per-script, not assumed page-wide.
- Same session, a separate `self-review` pass caught that `npm run build` prints `[WARN] [config] Shiki syntax highlighting uses inline styles that are not compatible with Content Security Policy (CSP)` — Astro's default Markdown/MDX code-fence highlighter emits its own per-token inline `style="color:..."` attributes, which the now-strict, `'unsafe-inline'`-free `style-src` meta CSP can't permit. No published content has a code fence yet (all `blog/` posts are `draft: true`), so this is a known, accepted, currently-inert gap rather than an active bug — documented in CLAUDE.md so the first code-fenced post doesn't ship silently-unstyled with nothing in CI to catch it.

- Root-caused the "dark mode persists across client-side navigation" `navigation.spec.ts` failure (previously an open question): Astro 7's `astro dev` auto-detects agentic CLI environments via the `am-i-vibing` package (it checks for `CLAUDECODE`, among others) and silently daemonizes itself in the background instead of blocking in the foreground. When Playwright's `webServer` spawns `npm run dev:astro` under Claude Code, the spawned process inherits that env var, exits immediately after forking the real daemon, and Playwright loses the ability to tear that daemon down — it survives past the test run. Fixed in `playwright.config.ts` by setting `env: { ASTRO_DEV_BACKGROUND: '1' }` on the `webServer` config, which opts back into normal foreground behavior (the name is misleading — setting it disables the auto-background, it doesn't enable it) so Playwright always owns a fresh, correctly-torn-down server. Confirmed fixed across two full build-then-test cycles with no orphaned daemon left behind either time. This is local-environment-only (CI never sets `CLAUDECODE` and runs build/test in isolated jobs), so it never showed up as a real CI failure — the PR #40 "CI failure" was likely something unrelated.
