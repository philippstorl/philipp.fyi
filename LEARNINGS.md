# Learnings

A dated, append-only log of what was discovered while working on this repo — the history and reasoning that neither of the other two mechanisms keeps. Standing rules and conventions belong in [CLAUDE.md](CLAUDE.md) (kept current there via the `doc-sync` skill); feedback about working style belongs in Claude's own cross-session memory. This file is for context that doesn't rise to either: a decision and why, a dead end, an open question, or domain knowledge about the tooling itself rather than the site.

Updated automatically at the end of each session; read automatically at the start of the next one.

## Open questions

- Whether `preflight/SKILL.md` should stop restating CLAUDE.md's command list verbatim (flagged by `self-review` on 2026-06-25) — redundant but arguably more robust against either file being edited in isolation; undecided.

Surfaced by `self-review` during the issue #64 HTML-comment cleanup (the deleted `WorkSection.astro` comment naming "Storyblok migration" as the featured card was the only place partially documenting this coupling). Out of scope there; still undecided whether the fix is wiring `WorkSection.astro` to select by `featured: true` instead of order-position, or removing the field.

- **Second follow-up:** in-body case-study/blog headings (via `prose.ts`'s `PROSE_CONTENT_CLASSES`) got the same `font-normal` → `font-bold` treatment, and figcaptions (`ResponsiveFigure.astro`) got `italic`, as two separate explicit asks. Real discovery while implementing the italic: `@fontsource-variable/geist` splits normal and italic into two separate CSS files (`index.css` vs. `wght-italic.css`) — only `index.css` had been imported by the original font swap, so `italic` anywhere on the site, including Tailwind Typography's own pre-existing `prose-blockquote` italic styling, had been silently rendering as browser-synthesized fake-oblique with no real italic glyphs at all. Importing `wght-italic.css` fixed the new figcaptions and, as a side effect, corrected blockquote italics on `recommendations.astro`/case-study pull-quotes that had been faux-italic the whole time. `self-review` caught one more thing: `ImageLightbox.astro`'s `#lightbox-caption` mirrors the same caption text as the source `<figcaption>` but is a separate element with its own class list, so it didn't automatically inherit the italic — added it there too. See [CLAUDE.md](CLAUDE.md)'s font-bold-headings bullet (extended) and the new fontsource-italic-file-split bullet.
- Issue #274 (case-study images not filling 100% width on mobile) went through three implementation rounds, each caught by a `self-review` pass. Round 1 added a `layout: 'full-width' | 'constrained'` field to `content-image-sizing.ts`'s `FigureSizing` and a hand-rolled `[data-astro-image="full-width"]{width:100%}` rule in `global.css` — review caught that `leadership-operating-model.mdx`/`storyblok-migration.mdx`'s grid CSS had been made responsive without updating their paired `gridFigureSizing(2)` calls (still describing a permanent half-width `sizes`), fixed by switching to `responsiveGridFigureSizing(TWO_COLUMN_RESPONSIVE_TIERS)`, and flagged the hand-rolled CSS as duplicating Astro's own `image.responsiveStyles` output without `:where()`. Round 2 "fixed" that by enabling the `image.responsiveStyles` config flag instead — seemingly the more robust, framework-maintained choice. Four independent parallel review passes then converged on why that was actually worse: the flag's stylesheet ships in a **new** CSS layer (`astro.images`), and per the cascade-layers spec a layer's priority is set by when it's _first declared_ — since this stylesheet is injected after Tailwind's own `theme/base/components/utilities` layer declaration, `astro.images` outranks even `utilities` regardless of specificity, so its unconditional `:where([data-astro-image]){height:auto}` rule silently beat `WorkCard.astro`'s `h-full` utility on its own `layout="constrained"` cover — confirmed via a real sub-pixel computed-style mismatch, invisible today only by coincidence. Round 3 reverted the flag and went back to the narrow hand-rolled rule, done properly this time: wrapped in `:where()` and placed inside this repo's own `@layer base` (not a framework-injected layer), scoped only to `full-width` (a value `WorkCard` never has). General lesson: a config flag that injects a framework's own CSS isn't automatically safer than a narrow hand-written rule — where that stylesheet lands in cascade-layer order relative to the rest of the site's CSS matters more than who wrote it. Also fixed a doc-sync gap the review surfaced: README.md and `.claude/skills/add-content/SKILL.md` both still held up `gridFigureSizing(3)` as the canonical multi-column-grid example, which would have walked a future case-study author straight back into this bug. See [CLAUDE.md](CLAUDE.md)'s `image.responsiveStyles` and `layout` bullets for the shipped result.
- Issue #253: the "Open questions" bullet pinning `astro` to exact `7.0.2` pending an upstream fix for the 7.0.4 build regression was stale — `package.json` now has `astro` at `7.2.4` via a clean chain of exact-version Dependabot bumps (7.0.2 → 7.0.9 → 7.1.3 → 7.1.6 → 7.2.0 → 7.2.2 → 7.2.4), well past the "past 7.0.5" retry threshold the question named. - Issue #229 claimed `tsconfig.json`'s `"ignoreDeprecations": "6.0"` is a no-op, verified only via `npx astro check` producing byte-identical output with/without the field. That check has a blind spot: `astro check`'s diagnostics don't include TypeScript's compiler-option-level diagnostics. Running plain `tsc --noEmit -p tsconfig.json` (installed TypeScript 6.0.3) shows the field is genuinely load-bearing — removing it surfaces a real `TS5101` error for the `baseUrl` option this same tsconfig still sets (needed for the `@/*` path alias); confirmed reproducibly both directions. First pass didn't implement the issue's suggested fix since deleting only `ignoreDeprecations` would ship a real (if CI-invisible, since nothing here invokes plain `tsc`) regression — posted the finding as a GitHub comment on #229 instead of opening a PR. General lesson for this repo: `astro check`/`npm run typecheck` is not equivalent to plain `tsc` for verifying whether a `tsconfig.json` compiler option is actually inert — a future "is this tsconfig field a no-op" question needs a direct `tsc --noEmit -p tsconfig.json` check.
- **Follow-up, same day:** found the actual fix for #229 rather than leaving it unresolved. `baseUrl` itself is what's deprecated (TS5101, removed in TS 7.0) — `ignoreDeprecations` was only suppressing the symptom, not the cause. Since TypeScript 4.1+, `paths` no longer needs `baseUrl` at all; it resolves relative to the tsconfig's own directory. Dropped both `baseUrl` and `ignoreDeprecations`, and changed `"@/*": ["src/*"]` to `"@/*": ["./src/*"]` — without the explicit `./`, TypeScript throws a _different_ compiler-option error (`TS5090`, "non-relative paths are not allowed when baseUrl is not set") that `astro check` also doesn't surface, only plain `tsc --noEmit` does. Verified clean with `tsc --noEmit`, `astro check`, `npm run build` (confirms Vite/Astro's own alias resolution isn't tied to `baseUrl` either), and the full `npm test` suite (181 passed). Landed on the same PR/branch as the earlier no-fix comment (`docs/learnings-issue-229-tsconfig-finding`, PR #243) rather than opening a duplicate.
- Issue #226 (CI GitHub Actions not pinned to commit SHAs): resolved each action's real commit SHA via `gh api repos/<owner>/<repo>/git/refs/tags/<tag>`, cross-checked against `gh api repos/<owner>/<repo>/commits/<tag>` — both agreed, and each tag's `.object.type` came back `"commit"` rather than `"tag"`, confirming these are lightweight tags where the ref SHA is directly the commit SHA with no annotated-tag object to dereference. Pinned to the latest patch under each major version already in use (checkout v4→v4.4.0, setup-node v4→v4.4.0, upload-artifact v4→v4.6.2, github-script v7→v7.1.0), per the issue's own instruction, rather than the exact tag GitHub's quickstart docs show. `self-review` caught that CLAUDE.md's Node-26 bullet still quoted the literal string `actions/setup-node@v4` after the diff removed every occurrence from `ci.yml` — fixed, and used as the prompt to also add a CLAUDE.md bullet documenting the SHA-pinning convention itself, which hadn't been written down before this issue.
- Issue #225 (`content-image-sizing.ts` srcset overfetch): before implementing anything, verified by hand that the issue's own suggested fix ("add a 1.5x step to each ladder") does not actually close the flagged gap — no multiple of either tier's base (352 or 592) lands between 592 and 704, since that gap is a property of the relationship between the two different tiers' anchors, not either ladder's own internal spacing. Verified against real build output both times (not just hand math): the two flagged images gained exactly the predicted 646px candidate, and after the guard fix, unrelated call sites' `widths` arrays came back byte-identical to pre-change. See [CLAUDE.md](CLAUDE.md)'s new `content-image-sizing.ts` bullet for the full writeup and measured before/after overfetch numbers.

- Issue #215 (mobile nav pushed page content down instead of overlaying it): the backdrop element has to be a sibling of `<header>`, not a child — nesting it inside would put it in the header's own stacking context, where any explicitly `z-index`ed descendant paints above the header's normal-flow content per the CSS stacking spec, dimming the header bar itself instead of just the page beneath it. It needs its own `transition:persist` too (matched by `id`, same as `#site-header`), or a client-side navigation swaps it for an inert copy and leaves the toggle script's cached `getElementById` reference pointing at a detached node. `self-review` caught a second, subtler bug: the new scroll-lock rule (`html:has(#mobile-nav:not(.hidden)) { overflow: hidden }`) needed scoping inside `@media (width < 768px)` to match `#mobile-nav`'s own `md:hidden` — unscoped, it reproduced exactly the class-vs-computed-display mismatch `isMenuOpen()` already had to guard against (issue #185), where leaving the menu "open" class-wise while resizing past `md` would strand `overflow: hidden` on `<html>` indefinitely. See [CLAUDE.md](CLAUDE.md)'s new `#mobile-nav` overlay bullet for the full writeup, including the animate-on-display-change technique used for the open transition (no JS beyond the existing `hidden`-class toggle).
- Issue #175 (csp-report.ts request caps): chose `MAX_BODY_BYTES = 50_000` and `MAX_REPORTS_PER_REQUEST = 25` since a real report (even the legacy shape, which embeds the full CSP policy string) runs well under 2KB — 50KB/25 leaves headroom for a genuine multi-violation batch while bounding fan-out. `self-review` flagged that measuring the size cap via `Buffer.byteLength(rawBody, 'utf8')` on an already-`req.text()`-decoded string was theoretically unsound (re-encoding a UTF-8-decoded string is implementation-defined for malformed input, so it isn't guaranteed to equal the real wire byte count) — switched to `req.arrayBuffer().byteLength`, measured before any decoding happens. Empirically tried to reproduce an actual undercount in Node with several malformed-UTF-8 byte patterns (lone continuation bytes, out-of-range 4-byte sequences, truncated multi-byte leads) and never found one — decode-then-reencode only ever expanded in Node's `Buffer`/`TextDecoder`, never shrank — so the specific exploit may not be reachable in this runtime, but measuring raw bytes directly is strictly more correct regardless and was kept. See [CLAUDE.md](CLAUDE.md)'s `csp-report.ts` bullet for the shipped behavior.
- `netlify dev` (not just `netlify serve`, which this file already documented on 2026-07-02-adjacent history) has the same git-worktree root-resolution bug: run from inside a `.claude/worktrees/agent-.../` checkout, it bundles the **main repo's** copy of `netlify/functions/*.ts` instead of the worktree's own edited file, despite the process's own `cwd` correctly being the worktree. ### 2026-08-20

- Building issue #149's contrast-check CI job surfaced two Playwright quirks worth remembering for any future Playwright tooling in this repo. (1) The declarative `use.reducedMotion: 'reduce'` config option didn't reliably reach the page's own `matchMedia('(prefers-reduced-motion: reduce)')` in this Playwright version — confirmed by A/B testing the same real spec run with only the config option vs. only an explicit `page.emulateMedia({ reducedMotion: 'reduce' })` call; only the imperative call worked. (2) `test.beforeAll` in a `fullyParallel` multi-worker config runs once _per worker_, not once globally — using it to clear `contrast-results/` before writing caused a real race, since a later-starting worker's cleanup could delete a file an already-running worker had just written. Fixed with Playwright's `globalSetup`, which genuinely runs once in the main process before any worker starts. Both fixes are in `e2e/contrast.spec.ts`/`playwright.contrast.config.ts`/`e2e/contrast.global-setup.ts`, with the reasoning as inline comments rather than promoted to CLAUDE.md — narrow to this one feature, not a repo-wide convention.
- Answering "why isn't issue #106's border-contrast tradeoff in the allowlist" (user question, same issue #149 work) required actually checking `axe-core`'s rule set rather than assuming the checker's scope — `axe.getRules()` shows exactly two contrast rules, both text-only (`color-contrast` WCAG 1.4.3 AA, `color-contrast-enhanced` WCAG 1.4.6 AAA); there is no non-text/UI-component contrast rule (WCAG 1.4.11) in axe-core's stable set at all, so the border tradeoff can never be flagged, allowlist or not. Separately, in the same session, confirmed empirically that axe's selector-generation algorithm strongly prefers `id` over any `data-*` attribute when producing a violation's target selector — an element with only a `data-*` marker and no `id` still fell back to an ambient utility class. Both promoted into [CLAUDE.md](CLAUDE.md)'s new `contrast` job bullet.
- Verifying a GitHub Actions PR-comment-posting feature locally (mocking/dry-running the aggregation script) isn't sufficient confidence that it works — real GitHub API behavior (comment pagination past 30, fork-PR token permissions, the sticky-comment upsert actually finding and updating the right comment) can only be checked against a real run. Did this by temporarily emptying `contrast-allowlist.json`, pushing to the already-open PR, confirming a real comment appeared, then restoring it and confirming the _same_ comment updated in place rather than duplicating — worth the extra two throwaway commits given the user directly asked whether it had actually been tested.
- Building issue #156's deploy-notification relay, Netlify's own docs (`docs.netlify.com`, `open-api.netlify.com`) didn't reliably answer "what does the deploy webhook's `admin_url` field actually contain" — WebFetch summaries of both were vague or inconsistent on whether it's per-deploy or site-general. Got ground truth instead by calling the already-authenticated CLI directly (`netlify api listSiteDeploys --data '{"site_id":"..."}'`) against the live site: confirmed `admin_url` is the general project page, not deploy-specific, so the deploy-specific link needed building as `${admin_url}/deploys/${id}`. Lesson: for "what does this real API actually return" questions, a live authenticated CLI/API call beats doc-scraping when the CLI is already logged in.
