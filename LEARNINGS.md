# Learnings

A dated, append-only log of what was discovered while working on this repo — the history and reasoning that neither of the other two mechanisms keeps. Standing rules and conventions belong in [CLAUDE.md](CLAUDE.md) (kept current there via the `doc-sync` skill); feedback about working style belongs in Claude's own cross-session memory. This file is for context that doesn't rise to either: a decision and why, a dead end, an open question, or domain knowledge about the tooling itself rather than the site.

Updated automatically at the end of each session; read automatically at the start of the next one.

## Open questions

Both `/route` and `/route/` currently resolve; no `netlify.toml` redirect exists for this.

## Log

### 2026-06-25

- Creating a brand-new top-level `.claude/skills/` directory mid-session isn't picked up by Claude Code's live file watcher — it only watches directories that already existed when the session started. A restart (or fresh session) is required before any skill in a newly-created directory becomes invocable. Editing skills inside an already-watched directory does take effect live.
- A skill invoked with `context: fork` (e.g. `self-review`) only loops back to the orchestrator when Claude invokes it mid-task and stays in the same turn. If a human runs it directly as a standalone `/self-review`, the findings return as plain output with nothing to act on them automatically — see CLAUDE.md's `self-review` section for the fix-it-yourself follow-up this requires.
- Deleted `feedback_american_english.md` and `feedback_commit_scope.md` from local memory — both were already fully duplicated in committed files (CLAUDE.md's "American English spelling" bullet, and `conventional-commits/SKILL.md`'s "Scope" section). Repo-specific corrections should get promoted to a portable, committed file instead of resting in local-only memory; `doc-sync`'s table now has an explicit row for this.
- When evaluating whether a recurring task is worth a dedicated skill, check git history for repeat incidents rather than going on plausibility alone. This justified the four original skills (real, repeated patterns) and was also the reason to decline a contrast-check skill despite CLAUDE.md flagging color changes as "accessibility-sensitive" — zero actual contrast incidents in history.
- Chose a non-blocking nudge (`systemMessage`/`additionalContext`) over a hard `decision: block` gate for the `doc-sync` Stop hook. A path-based heuristic will have false positives on routine changes; blocking on those would cause worse alert fatigue than occasionally missing a real doc update.
- This repo already links PRs to issues via a `Resolves` block (PRs #18, #25), just applied inconsistently — promoted into `conventional-commits/SKILL.md`. Separately: grepping PR bodies for "fixes/closes/resolves" to detect this produced false positives from Dependabot's upstream changelog text (e.g. a dependency's own release notes saying "Fixes #1234"), unrelated to this repo's issues.
- First real `self-review` run found two genuine bugs in `check-doc-sync.js` (the `systemMessage` field doesn't reach the agent's own context; the regex missed several doc-relevant paths) and a valid simplification (three `git` shellouts collapsed to one) — all fixed same-session. It also raised one finding that turned out to be wrong, refuted using a doc fetch from earlier in the same session that the isolated reviewer had no way to see — a reminder that the orchestrator's extra context is a real asset, not just the reviewer's isolation.
- This file's structure deliberately diverges from the source article's 5-section template (Patterns That Work, Mistakes to Avoid, Domain Knowledge, Open Questions, Consolidated Principles) — kept only "Open questions" and "Log," and dropped the other three because they'd duplicate CLAUDE.md (via `doc-sync`) and memory (the `feedback` type) respectively.
- When bringing a critical config file under a new formatter (PR #36, 2026-06-25: `netlify.toml` under `prettier-plugin-toml`), verify semantic equivalence by parsing before/after and deep-equaling the result (e.g. via `@iarna/toml`) rather than just eyeballing the diff.
- When a test fails after a change that doesn't plausibly touch what it's testing, reproduce the failure against a clean `git stash`'d version before assuming the change caused it (PR #40, 2026-06-25, for `navigation.spec.ts` failures unrelated to a comment-cleanup change). See the open question below, though — the underlying failure deserves a second look, not just the "pre-existing, ignore it" conclusion that reproduction step led to.
