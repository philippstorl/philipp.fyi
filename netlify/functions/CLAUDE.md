# netlify/functions/CLAUDE.md

Guidance for Claude Code when working on this repo's Netlify Functions. Loaded automatically only when working with files under `netlify/functions/` — see the root [CLAUDE.md](../../CLAUDE.md) for repo-wide conventions. Moved here verbatim from root CLAUDE.md by issue #305 to keep this detail out of every session's resident context when it isn't relevant.

- **CSP violation reports go to `netlify/functions/csp-report.ts` (issue #146), the repo's first Netlify Function** — `netlify.toml`'s CSP header sets both `report-to`/`report-uri` at that one endpoint (broader browser coverage), which normalizes both report shapes, logs each to a `csp-reports` Netlify Blobs store, and posts to Slack if `SLACK_WEBHOOK_URL` is set. Only the header-delivered CSP can carry these directives — the spec excludes them from `<meta>`-delivered policies, so `astro.config.mjs`'s meta CSP needed no change.
    - `SLACK_WEBHOOK_URL` is dashboard-only, never committed — one of three exceptions (alongside `SLACK_DEPLOY_WEBHOOK_URL` and `DEPLOY_NOTIFICATION_WEBHOOK_SECRET` below) to the Deployment section's "configuration lives entirely in netlify.toml" claim.
    - Local `netlify dev` Blobs writes go to a gitignored local emulation (`.netlify/blobs-serve/`), never the real deployed store — confirmed by testing.
    - **The Slack message links to the `csp-reports` Blobs store and embeds the full stored record as a code block, not just the four curated summary fields** (issue #200) — `blobsStoreUrl()` builds `https://app.netlify.com/projects/${context.site.name}/blobs/site:csp-reports` from the second `context` argument Netlify Functions v2 pass to the handler (typed locally as a minimal `FunctionContext`, not imported from `@netlify/functions`, for the same transitive-dependency reason `verify-netlify-signature.ts` avoids `jsonwebtoken` — see the bullet below); it's only included in a given report's Slack message if that report's own `store.setJSON` call actually succeeded, so the link never points at an entry that was never written. Real Slack **thread** replies (the original ask) aren't possible here — incoming webhooks always post top-level messages and never return a `ts` to thread against; that requires switching to `chat.postMessage` with a bot token, which needs new Slack app configuration outside this repo, so it was deliberately not pursued. **Because this endpoint is unauthenticated by design (see below), every field embedded in the Slack message — the four summary lines and the full JSON block alike — is attacker-controlled and must be sanitized before being sent, uniformly, not just inside the code block**: `sanitizeSlackText()` replaces `&`/`<`/`>` per Slack's own mrkdwn escaping requirement (unescaped, a crafted report could inject a live `<!channel>` mention or a spoofed `<url|label>` link) and swaps literal backticks for a lookalike character, applied to every attacker-controlled string this function interpolates. An earlier version only neutralized backticks inside the JSON block, reasoning the four summary lines just needed `&`/`<`/`>` escaping — wrong, caught by manually posting a crafted report (a `violated-directive` value containing three backticks) through a local Netlify Dev instance and inspecting the exact payload that reached a mock webhook: the stray backticks in a summary line paired with the JSON block's own opening fence and scrambled every line in between, since Slack's fence-matching is purely textual and doesn't know one triple-backtick run was "supposed to" be inline. The JSON block is pretty-printed (`JSON.stringify(record, null, 2)`), not compact — readability of what actually renders in Slack was judged more valuable than fitting marginally more raw data under the truncation cap, since real CSP reports are small and truncation is a rare, defensive-only case. It's capped at `MAX_JSON_BLOCK_LENGTH` (3500 chars, still local to `csp-report.ts` — the JSON-block cap has no equivalent in `deploy-notification.ts`); the four summary lines are separately capped at `MAX_FIELD_LENGTH` (500 chars each) — an oversized `blocked-uri`/`document-uri` could otherwise produce an unbounded Slack message even with the JSON block's own cap in place, caught by a `self-review` pass. `truncateForSlack()` is the one place both caps are enforced: it truncates by Unicode code point (not raw `.slice()`, which can split a UTF-16 surrogate pair) and truncates _before_ sanitizing, so a cut can never land mid-entity inside a `&amp;`/`&lt;`/`&gt;` sequence that sanitizing would otherwise introduce. **`sanitizeSlackText()`/`truncateForSlack()` moved into `netlify/functions/_shared/slack.ts` (issue #222)** — they were originally local to this file, but they're generic Slack-mrkdwn helpers with nothing CSP-specific about them, and `deploy-notification.ts`'s `summarize()` had the identical unsanitized-interpolation gap for its own attacker-influenceable fields (chiefly `branch`, a real git branch name). Moved verbatim, not reimplemented, and re-verified with the same crafted-payload-through-a-mock-webhook method afterward to confirm `csp-report.ts`'s own behavior didn't change. `deploy-notification.ts`'s call site (`sanitizeField()`, a thin wrapper the same shape as this file's own `truncateField()`) coerces each field with `String()` before sanitizing, since its payload is only cast (`as DeployNotification`) rather than runtime-validated — caught by `self-review`: the first version passed the field straight through, which would throw out of the whole invocation instead of degrading gracefully the moment Netlify ever sends a non-string value for one of these fields. **`MAX_FIELD_LENGTH` itself stays independently declared in both files** (500 in each, not hoisted into `_shared/slack.ts` alongside the functions that use it) — flagged as a minor drift risk by the same `self-review` pass, left as-is since the issue that prompted this move scoped it to relocating the two functions specifically, not every constant they're parameterized by. **Each report's Slack-post step is wrapped in its own try/catch, separate from the Blobs-write try/catch** — `normalize()`/`summarize()` have no guard of their own, so a malformed report (`null`, or a shape neither of `normalize()`'s branches expects) throws synchronously; without the wrapper that throw rejects the whole per-report `Promise.all` task with nothing to catch it, which both fails the batch's still-pending sibling reports and turns the handler's response into a 500 instead of `204` — also caught by `self-review`, then verified by POSTing a `[null, <valid report>]` batch through a local Netlify Dev instance: the malformed entry logged and was skipped, while the valid sibling's Blobs write and Slack post both still completed and the handler still returned `204`.
    - **The handler caps both request size and batch fan-out before doing any work, since this endpoint is unauthenticated by design** (issue #175): a `Content-Length` header over `MAX_BODY_BYTES` (50,000) is rejected with `413` before the body is even read; the body is then re-checked against the same cap on its actual byte length (`req.arrayBuffer().byteLength`, not a decoded-then-`Buffer.byteLength`-re-measured string — re-encoding a UTF-8-decoded string is implementation-defined for malformed input and shouldn't be trusted to equal the real wire size, caught by `self-review`) in case `Content-Length` was absent or understated. A real report (even the legacy shape, which embeds the full CSP policy string) runs well under 2KB, so 50KB/`MAX_REPORTS_PER_REQUEST` (25) leaves headroom for a genuine multi-violation batch while bounding one request's Blobs-write/Slack-post fan-out; an oversized array is `slice()`d to the first 25 rather than rejected outright, with a `console.warn` logging the original count. **The `Content-Length` pre-check only avoids buffering the body when the header is honest** — when it's absent or lies small, `req.arrayBuffer()` still reads the full body into memory before the byte-length re-check can reject it, so Netlify's own platform body-size limit is the actual backstop against worst-case memory for that case, not this function's own check (this is also why the issue is rated Low, not High: the suggested fix's "reject before parsing" was implemented, "reject before reading" wasn't, and the platform limit was judged sufficient for the gap).
    - **`netlify/functions/csp-report-cleanup.ts` (issue #252), the repo's third Netlify Function, is a V2 scheduled function that deletes `csp-reports` Blobs entries older than 30 days on a daily cron** — neither `SetOptions` nor `store.setJSON()` exposes a TTL/expiration field, so nothing else prunes the store, and issue #252's own audit judged a retention job better ROI than rate-limiting the endpoint itself for a low-traffic personal site (rate limiting stays undone; revisit only if abuse actually shows up in the store's growth). Declared via a `config` export (`{ schedule: '0 3 * * *' }`) inside the function file itself, not a `netlify.toml` `[functions."name"]` block — confirmed as the shape the installed `@netlify/functions` (5.3.0, a transitive `netlify-cli` devDependency, not a direct one, same reason `verify-netlify-signature.ts` avoids `jsonwebtoken` — this file writes a plain object literal matching `Config`'s shape rather than importing that type) actually supports by reading its `main.d.ts`, not assumed from memory, since which mechanism a given version supports is version-specific. 30 days was chosen as a middle ground: long enough to look back at a real incident, short enough to bound growth given the endpoint's own per-request caps (issue #175) are the only thing limiting how fast the store fills between runs. **Reads each entry's age from its key, not its stored body** — `csp-report.ts` already writes every entry as `` `${receivedAt}-${crypto.randomUUID()}` ``, and `receivedAt` is `Date#toISOString()` (always exactly 24 characters), so `parseEntryTimestamp()` slices the key's first 24 characters instead of a `store.get()`/`getMetadata()` round trip per entry; an unparseable prefix is left alone rather than guess-deleted. `store.list()` (no `paginate: true`) already walks every page internally (confirmed by reading `@netlify/blobs`'s compiled `list()`, which `collectIterator()`s its own async iterator before returning), so one call sees the whole store. **Deletes run in bounded batches of 25 (`DELETE_BATCH_SIZE`, matching `csp-report.ts`'s own `MAX_REPORTS_PER_REQUEST`), not one unbounded `Promise.all`** — caught by `self-review`: the store has no write cap of its own (only one POST's fan-out is bounded), so a large accumulated backlog could otherwise fire hundreds of concurrent `store.delete()` calls in a single run. **Verified with a throwaway harness, not just types** — a plain Node `http` server stood in for the real Blobs edge API (GET list / PUT set / DELETE, matching the exact request shapes `@netlify/blobs`'s compiled client makes), seeded via a fake base64 `NETLIFY_BLOBS_CONTEXT` pointing its `edgeURL` at that local server (same pattern the bullet below documents), with old/recent/boundary/malformed-key entries plus 60 bulk entries to exercise the batching loop across multiple batches — confirmed old entries deleted, recent and malformed-key entries kept, and all 60 bulk entries cleared across 3 batches. Same worktree-bundling and `SLACK_WEBHOOK_URL=""` precautions as the `netlify dev` workaround below, though this function makes no Slack calls at all. **Known gap, left as-is (raised and declined during `self-review`):** the handler always returns `204` even if every delete in a run failed (e.g. revoked Blobs permissions) — `console.error` is the only signal, with no Slack alert the way `csp-report.ts`/`deploy-notification.ts` have. Wiring one in via the existing `_shared/slack.ts` helper would be easy, but was judged out of scope for a minimal cleanup job with no side effects beyond deleting already-low-value data; revisit if function logs ever prove insufficient to notice a systemic failure here.
    - **Verifying this against a real `netlify dev` instance from inside a git worktree needs two workarounds, not just the usual `ASTRO_DEV_BACKGROUND=1`.** First, `netlify dev`/`netlify serve` run from a worktree checkout (`.claude/worktrees/agent-.../`) bundle the **main repo's** copy of `netlify/functions/*.ts`, not the worktree's own edited one — the same git-worktree root-resolution bug LEARNINGS.md documents for `netlify serve` (confirmed there via a served page missing content the worktree's build had; confirmed here for `netlify dev` via `lsof -p <pid>` showing an open file descriptor on the main checkout's `netlify/functions/csp-report.ts`, despite the process's own `cwd` correctly being the worktree). Worked around by bundling the worktree's own file with `esbuild` directly (`--bundle --platform=node --format=esm --external:@netlify/blobs`, output written _inside_ the worktree so Node's `node_modules` resolution for the externalized import still finds it) and importing that bundle from a throwaway script that calls the handler directly with hand-built `Request` objects — sidesteps netlify-cli's function bundler entirely, so the worktree bug can't reoccur regardless of which function is being tested. Second, **this repo's real Netlify project has `SLACK_WEBHOOK_URL` configured on the dashboard, and `netlify dev`/`netlify env:list` pull it into any local run** (confirmed via `netlify env:list`, which named the real linked project) even with no local `.netlify/state.json` — a test POST that reaches `postToSlack()` would otherwise post real messages to the production CSP-alerts Slack channel. Always export `SLACK_WEBHOOK_URL=""` (falsy, so `postToSlack()`'s `if (webhookUrl)` guard skips it entirely) before any local run that might exercise this function, whether via the worktree-bundle workaround above or a working `netlify dev`. `getStore()` also throws synchronously (`MissingBlobsEnvironmentError`) outside of a real Netlify Blobs context, which is _not_ wrapped in the per-report try/catch (only `store.setJSON()` is) — a standalone harness needs a fake base64 `NETLIFY_BLOBS_CONTEXT` env var (`{siteID, token, edgeURL}`, any values) so `getStore()` succeeds and the actual write fails downstream instead, inside the try/catch, the same as a real Blobs outage would.
    - `netlify dev` spawns `astro dev` as its framework server and hits the same agentic-auto-daemonization issue `playwright.config.ts` documents — run it with `ASTRO_DEV_BACKGROUND=1` too.
    - `.netlify/**` was added to `eslint.config.mjs`'s `ignores`: `netlify dev`/`netlify build` bundles each function's deps into `.netlify/functions-serve/`, which isn't source and shouldn't be linted.
- **Netlify deploy notifications go to Slack via `netlify/functions/deploy-notification.ts` (issue #156), the repo's second Netlify Function** — Netlify's native Slack notification type is gated behind Pro/Enterprise, and its generic Outgoing Webhook notification posts the raw deploy-object JSON (`state`, `context`, `branch`, `error_message`, `deploy_ssl_url`, `admin_url`, …) directly, which Slack's Incoming Webhook endpoint rejects with `400 no_text` since it has no `text`/`blocks` field. This function receives that raw POST, reformats it into a `{"text": "..."}` Slack message (✅/❌ by `state`, with context/branch/error/deploy-link), and forwards it to a **separate** Slack Incoming Webhook — kept distinct from CSP reporting's channel by design. The two Netlify dashboard "Deploy succeeded"/"Deploy failed" Outgoing Webhook notifications point at `/.netlify/functions/deploy-notification`, not a raw `hooks.slack.com` URL directly (that's the actual bug this fixes: Netlify's raw payload was already being POSTed straight to Slack and silently failing). Unlike `csp-report.ts`, this function doesn't write to Blobs — it's a pure relay, nothing here needs persisting for later review.
    - `SLACK_DEPLOY_WEBHOOK_URL` is dashboard-only, never committed — the second of the three `netlify.toml`-completeness exceptions noted above; `DEPLOY_NOTIFICATION_WEBHOOK_SECRET` (the third) is documented two bullets down.
    - **The actual fetch-to-Slack-webhook mechanics (POST, headers, try/catch, `console.error`) live in `netlify/functions/_shared/slack.ts`'s `postToSlack()`, shared by both `csp-report.ts` and `deploy-notification.ts`** (the file also exports `sanitizeSlackText()`/`truncateForSlack()`, moved here from `csp-report.ts` by issue #222 — see that bullet above for why), rather than each function repeating its own copy — extracted at the 2nd occurrence rather than waiting for a 3rd/4th copy (the threshold most other shared-component extractions in this file use), a deliberate exception for this specific pair since both functions do the exact same "POST `{text}` to a webhook URL, swallow network errors" operation with nothing else in common to justify keeping them separate. Each call site still owns its own message-formatting (`summarize()`) and passes the finished text plus a call-site-specific error-log message into `postToSlack(webhookUrl, text, errorContext)`. The underscore prefix (`_shared/`) is a Netlify Functions convention — files/directories starting with `_` are excluded from being bundled as their own function, so it's importable via a plain relative import without becoming a third `/.netlify/functions/...` endpoint itself. **`postToSlack()` also checks `response.ok` after the `fetch` resolves** (issue #157) and `console.error`s the status/statusText when it isn't — a revoked/mistyped webhook URL or a Slack-side error used to resolve without throwing, silently going dark with nothing logged anywhere; that logging/observability gap is now closed for both call sites in the one shared function. This only fixes visibility, not the caller-facing contract: `postToSlack()` still returns `void` and never throws, so a Slack-side failure doesn't change the `204`/`200` either function returns to its own caller (Netlify's webhook dispatcher, or the browser sending a CSP report) — by design, since neither caller could usefully act on a different status code, but worth knowing if a future change ever wants Slack delivery failures to be visible beyond the function log.
    - **`deploy-notification.ts` verifies Netlify's `X-Webhook-Signature` JWS before trusting the POST body, and fails closed** (issue #157): `netlify/functions/_shared/verify-netlify-signature.ts`'s `verifyNetlifySignature(rawBody, header, secret)` checks the JWT is `HS256`-signed with `DEPLOY_NOTIFICATION_WEBHOOK_SECRET` (a per-notification secret configured in the Netlify dashboard, dashboard-only like the two Slack URLs above), that its `iss` claim is `"netlify"`, and that its `sha256` claim matches the SHA-256 digest of the raw body — implemented by hand against Node's `node:crypto` (`createHmac`/`timingSafeEqual`/`createHash`) rather than pulling in a JWT dependency for this one narrow use. `jsonwebtoken`/`jws` do exist in `package-lock.json`/`node_modules` today, but only as transitive `devDependencies` of `netlify-cli` — not a direct `package.json` dependency, and not something a production Netlify Function should rely on being present, since a `netlify-cli` upgrade could drop that transitive chain at any time. Both comparisons use `timingSafeEqual` (the HMAC signature, and the `sha256` body-digest claim), not a plain `===`, for consistency even though the digest itself isn't secret. The function reads `req.text()` (not `req.json()`, and wrapped in its own try/catch) so the exact raw bytes are available for the digest, `JSON.parse`s afterward. If `DEPLOY_NOTIFICATION_WEBHOOK_SECRET` isn't configured, or the signature doesn't verify, the function returns `401` (logging why, in both cases) rather than falling back to trusting the body — deliberately different from the two Slack-URL env vars' "silently skip if absent" pattern, since accepting an unauthenticated payload here is exactly the vulnerability the issue was about. **Known gap:** `verifyNetlifySignature()` checks `alg`, the HMAC signature, `iss`, and the body digest, but not any timestamp/freshness claim — a captured valid (header, body, signature) triple stays replayable indefinitely. Low real impact today since `deploy-notification.ts` is a pure Slack relay with no side effects beyond posting a message, but worth revisiting if this verifier is ever reused for a webhook with side effects that matter. **`csp-report.ts` deliberately has no equivalent signature check** — it's hit directly by browsers via the CSP `report-to`/`report-uri` directives (see the bullet above), not by a Netlify Outgoing Webhook notification, so there's no Netlify-signed JWS to verify in the first place; the endpoint is unauthenticated by design, the same as any CSP violation reporting endpoint on the web. Don't add a signature check there under a future pass at this issue's suggested scope — there's no secret to check it against.
