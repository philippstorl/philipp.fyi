# Adding content

This site has three content collections, each with different ordering rules and different coupling to the e2e tests. The schema itself is defined in `src/content.config.ts` — read it if anything below seems out of date. The risk with this task isn't writing the content, it's forgetting one of the files that has to change alongside it.

## Case study (`src/content/work/`)

1. Create `src/content/work/<slug>.mdx` — the filename **is** the URL slug (`/work/<slug>/`), so pick it deliberately; it can't be changed later without breaking links.
2. Frontmatter:
    - `title`, `description` — plain strings. `description` is shown on the work card and the case-study page's own intro, and is also what `<meta name="description">`/`og:description`/`twitter:description` use — one field, no separate meta-only variant. Keep it at or under ~155 chars (Google/social previews truncate past that) and write it tight from the start; a punchy, snippet-length sentence has read better everywhere it's been tried than a longer narrative one, so don't reach for extra length assuming the on-page copy needs more room.
    - `year` — a 4-digit year (`"2024"`) or an en-dash year range for multi-year work (`"2022–2024"`, using an actual en dash `–`, not a hyphen `-`) — validated by a zod regex, anything else fails the build.
    - `tags: [...]` — at least one tag; an empty array fails the build.
    - `category` — must be exactly `"Engineering"`, `"Leadership"`, or `"Design"` (zod enum, anything else fails the build).
    - `order` — a nonnegative integer (zod `.int().nonnegative()`). List the existing files in this directory and use one higher than the current max. The lowest `order` gets the wide, full-row card in `WorkGrid.astro`; there's no separate `featured` flag (removed in issue #300).
    - `draft` — defaults to `false`.
    - `coverImage` — optional, e.g. `"./screenshot.png"`. Only set it if you actually have a screenshot in the same folder; it's the teaser shown on the homepage work card. Omitting it is fine — the card falls back to a text-only layout.
3. Body: screenshots go through `<ResponsiveFigure>` (`src/components/ui/ResponsiveFigure.astro`), not a hand-written `<figure><Image/><figcaption/></figure>` block — pass `src`/`alt`/`caption` plus a sizing spread from `src/utils/content-image-sizing.ts` (`{...responsiveGridFigureSizing(THREE_COLUMN_RESPONSIVE_TIERS)}` for a grid cell whose column count changes at breakpoints, `{...fullWidthFigureSizing()}` for a standalone full-width figure, etc. — see "Responsive image sizing" below for the full set and when to use each). **Never use `gridFigureSizing(N)` for `N > 1`** — it renders correctly on desktop but freezes the image at its desktop-capped width even once the grid has collapsed to one column on mobile (issue #274); reach for `responsiveGridFigureSizing` with the matching tier constant instead, paired with responsive grid classes (`grid-cols-1 sm:grid-cols-N`), for any grid whose column count changes across breakpoints. **Don't also pass an explicit `width` prop** — every sizing helper's spread already includes the correct `width` as part of what it returns; a hand-typed `width` is either redundant (if it appears before the spread) or silently wrong (if it appears after the spread and overrides the computed one, desyncing the image from its own `sizes`/`widths`). This automatically gets the click-to-enlarge lightbox via `ImageLightbox.astro` — no extra markup needed beyond the `ResponsiveFigure` call itself.
4. Update tests — the homepage renders **every** work entry (no preview slice), so both of these need to change:
    - `e2e/work.spec.ts` — add `{ slug, title }` to the `caseStudies` array so the new page gets its own render assertion.
    - `e2e/home.spec.ts` — the test named `shows all N work cards` asserts `toHaveCount(N)` where N is the current total. Bump it to match the new total.
    - `e2e/meta-description-length.spec.ts` — add `{ reportedPath: '/work/<slug>/', gotoPath: '/work/<slug>/' }` to its `pages` array so the new case study's meta description length is guarded too, not just the ones that happened to be over length when that test was written.

## Responsive image sizing (case-study and future blog screenshots)

This is the full reference for the sizing helpers referenced in step 3 above — read it before adding a new screenshot grid or changing an existing one.

- **Case study screenshots get a lightbox automatically.** Any `<figure>` containing an `<img>` within a case study's MDX body is picked up by `ImageLightbox.astro` (mounted once in `CaseStudyLayout.astro`) — click/tap to enlarge, with gallery navigation across the whole article. This is a byproduct of using `<ResponsiveFigure>` (below) for every screenshot, not a separate step: don't hand-write a `<figure><Image/></figure>` block to get it — that bypasses `ResponsiveFigure`'s responsive sizing and full-resolution `data-lightbox-src` handoff, silently reintroducing full-native-resolution images into the prose column (the exact bug issue #180 fixed). Don't reach for a library or React for the lightbox itself either way.
- **The responsive-image logic and the figure/caption markup are two separate components, not one.** `src/components/ui/ResponsiveImage.astro` (`src`/`alt`/`width` required; `class`/`data-lightbox-src` optional; then either `densities` alone, or `sizes` + `widths` together) renders a single responsively-sized `<Image>` and nothing else — no figure, no caption, no styling opinion (it takes whatever `class` it's given; it doesn't default to `rounded-xl border border-border` itself). `src/components/ui/ResponsiveFigure.astro` composes it: `<figure>` + `<ResponsiveImage>` + `<figcaption>`, and it's the one that supplies the content-image visual default (`rounded-xl border border-border`, overridable via `imgClass`) and generates the lightbox full-resolution source (below). Split this way because a responsive image and a captioned figure are different, independently-useful things — a future call site that needs a sized image without a caption (a hero, a card, anything not in a content body) reaches for `ResponsiveImage` directly rather than being forced into figure markup it doesn't want. Every in-body content image (case study MDX today; blog MDX once posts are published) goes through `ResponsiveFigure.astro` (`src`/`alt`/`caption`/`width` required; `class`/`captionClass`/`imgClass` optional; then either `densities` alone, or `sizes` + `widths` together), not a hand-written `<figure><Image/><figcaption/></figure>` block — issue #180 found every case-study MDX image shipping at full native resolution (some over 3000px wide) into a ~720px prose column with no responsive sizing, at the 4th+ file's worth of identical figure markup, the same "Nth copy" threshold `WorkGrid.astro`/`SectionHeader.astro`/`PageHeader.astro` were extracted at. Both live in `ui/`, not `work/`, deliberately: neither has case-study-specific import or logic (`ResponsiveFigure`'s lightbox interop, below, is generic — it works for any `.prose figure` regardless of which page mounts `ImageLightbox.astro`), so they're general-purpose primitives for any future long-form MDX content body, matching `PageHeader.astro`/`InterlinkCard.astro`'s placement as "used across dedicated content, not homepage-only." `ResponsiveImage` renders one of two mutually-exclusive Astro `<Image>` modes (confirmed via `node_modules/astro/dist/assets/types.d.ts` and `services/service.js` — `densities` and `layout`/`widths` cannot both be set on one `<Image>`), chosen per call site based on whether the figure's rendered width actually changes across breakpoints:
    - **`densities={[1, 2, 3]}` (the default, no `sizes`/`widths` passed) only for a figure whose display width is truly viewport-invariant** — nothing in the current case studies qualifies, because `CaseStudyLayout.astro`'s container (`mx-auto max-w-3xl px-6`) is itself fluid below its 720px cap, so even a fixed-3-column grid's cell width shrinks on a narrow phone. An earlier version of this fix used `densities` for exactly that "fixed column count" case, reasoning the box width was "genuinely constant" — wrong, caught by `self-review`: pixel-density (`x`-descriptor) `srcset` picks purely by device pixel ratio with no awareness of box size at all, so a phone with a real ~98px 3-column cell but a 3x-DPR screen was still forced to fetch the same 687px (3x-of-229) variant a full-size desktop retina display would get, a real multi-x overfetch specifically on the mobile/cellular connections the original issue called out. Keep `densities` available on `ResponsiveImage` for a genuinely fixed-pixel future use case (an icon, a fixed-size avatar), but don't reach for it inside this prose container.
    - **Every current case-study figure instead uses `layout="constrained"` + `sizes` + an explicit `widths` array, computed by `src/utils/content-image-sizing.ts`'s helpers rather than hand-typed per call site.** `responsiveGridFigureSizing(tiers)` for a grid whose column count itself changes with `sm:`/`lg:` (`voices-conference-website.mdx`'s three responsive grids, `tiers` ordered widest-condition-first with the last tier's `minWidth` omitted as the sub-`sm:` fallback) is the one real implementation; `gridFigureSizing(columns)` for a grid whose column count never changes across breakpoints (`columns` accepts `1 | 2 | 3`, since a single-column "grid" is exactly the full-width-figure case — `leadership-operating-model.mdx`'s nested 2-column, `storyblok-migration.mdx`'s 2-column pairs) is a thin wrapper that calls `responsiveGridFigureSizing([{ minWidth: 768, columns }, { columns }])` rather than reimplementing the same "cap at 768px, go fluid below it" math a second time — a `code-review` pass found the two functions had drifted into two independently-maintained copies of that logic; `fullWidthFigureSizing()` for a standalone full-column figure delegates to `gridFigureSizing(1)` in turn; `fixedWidthFigureSizing(width, row?)` for a figure with its own explicit width narrower than the column (`storyblok-migration.mdx`'s mobile-nav figure at 430, an existing explicit width predating this component) stays its own separate implementation, since a fixed-width figure's math (breakpoint derived from `width + padding`, optional row-sharing) isn't a special case of the grid-column math the other three share. None of these take the source image as a parameter — see the `widthLadder()` bullet below for why. Each returns `{ width, sizes, widths }`, spread directly onto `<ResponsiveFigure {...gridFigureSizing(3)} />` — this is also why the fix for the above `densities` bug wasn't "add a `sizes` string per call site" (50 hand-typed, error-prone `calc()` strings) but a small typed helper module: `sizes` alone isn't enough, `widths` has to cover the same tiers `sizes` describes or the browser silently under-resolves at an in-between breakpoint (the next bullet) — computing both together from one shared source keeps them from drifting apart the way hand-typed strings already had once.
    - **`brand-evolution.mdx`'s 10 screenshot-comparison grids moved from `gridFigureSizing(2|3)` + bare `grid-cols-2`/`grid-cols-3` to `responsiveGridFigureSizing(TWO_COLUMN_RESPONSIVE_TIERS | THREE_COLUMN_RESPONSIVE_TIERS)` + `grid-cols-1 sm:grid-cols-2 [lg:grid-cols-3]`** (issue #255), matching the pattern `voices-conference-website.mdx` already used — a fixed column count with no responsive prefix never drops to fewer columns on a narrow viewport, so at a real 320px width each of these grids' figures rendered at ~80×114px (image itself 80×66px), illegible for a case study whose whole point is showing visual differences between screenshots. Measured before/after with real Playwright `getBoundingClientRect()` calls against a built `astro dev` server, not just read from the code: 80px → 272px, matching `voices-conference-website.mdx`'s equivalent grids exactly at the same viewport. The issue's own text undercounted the affected grids as "6" (revised once already, from an initial "4") — the real count, confirmed by grepping the file's `grid grid-cols-` wrapper divs, is 10 (24 individual `gridFigureSizing()` calls); all 10 were converted, not just 6, since leaving any subset on the fixed-column pattern would reintroduce the identical bug for no reason. **`leadership-operating-model.mdx` and `storyblok-migration.mdx` still use `gridFigureSizing(2)` + bare `grid-cols-2` for their own comparison grids and have the same latent 320px-illegibility gap** — out of scope for issue #255, which named only `brand-evolution.mdx`, but worth fixing the same way in a future pass rather than assuming it's already covered.
    - **`layout="constrained"`'s own default `widths` (Astro auto-generates `[width, 2×width, ...breakpoints]`) is not enough once a custom `sizes` string describes more than one non-trivial tier — it silently under-resolves the tiers it doesn't know about.** Caught by `self-review`: an earlier version of the three-tier responsive grids (`"(min-width: 1024px) 229px, (min-width: 640px) 352px, calc(100vw - 48px)"`) passed only `width={229}` and let Astro auto-double it to `[229, 458]`, leaving the declared 352px tablet tier with no 2x/3x candidate at all — a 2x-DPI device in the 640–1023px window needed ≥704px and only ever got 458px, a real, visible blur regression on that breakpoint. Fixed by passing an explicit `widths` prop (allowed alongside `layout`/`sizes` — confirmed in `types.d.ts`'s `ImageSharedProps` union, only `densities` is mutually exclusive with `layout`/`widths`) computed from every tier's own 1x/2x/3x, not just the smallest one; `ResponsiveImage.astro`/`ResponsiveFigure.astro`'s `sizes`-branch `Props` now requires `widths` rather than treating it as optional, so this can't quietly regress again by omission.
    - **`content-image-sizing.ts`'s `widthLadder()` is deliberately unclamped against any source's native width, and none of the four exported sizing functions take the source image as a parameter at all.** An earlier version clamped every candidate to `ImageMetadata.width` by hand (replacing an even earlier one that hand-checked native resolution with `sips` and manually overrode `densities={[1, 2]}` on the one narrow-source figure, `voices-conference-website.mdx`'s `voices2026Agenda`, that needed it) — but a `code-review` pass found this duplicated logic Astro's own `getSrcSet()` (`services/service.js`) already performs on any `widths` array passed to a locally-imported image's `layout="constrained"` `<Image>`: it filters candidates down to `<= source.width` and pushes the native width back in as a fallback whenever that filtering would otherwise leave the list empty — confirmed by reading that exact code path, not assumed. Since a non-empty ladder (`[base, base*2, base*3]` is always non-empty, `base` being a positive layout dimension) can never trigger Astro's "already empty" no-fallback edge case, relying on Astro's own clamp is strictly equivalent to the hand-rolled version and removes a second copy of the same logic to keep in sync. Once the clamp moved downstream, `src: ImageMetadata` became a genuinely unused parameter on every sizing function (confirmed by `astro check`, which flags unused-but-declared parameters as hints even where ESLint's default "after-used" unused-vars mode doesn't) — removed rather than suppressed, since these functions are now pure functions of layout geometry (column count, fixed width) with no per-image input to begin with. Every MDX call site was updated to drop the now-unused first `src`/`img` argument (e.g. `gridFigureSizing(img, 3)` → `gridFigureSizing(3)`) — `<ResponsiveFigure src={img} ... />` still needs the import for its own `src` prop, so this only removes the redundant second reference, not the import itself.
    - **`CONTAINER_CAP_BREAKPOINT` is `768`, not `768 + 48 = 816`.** A `code-review` pass caught that the original constant double-counted the container's `px-6` padding: Tailwind's global `box-sizing: border-box` (`preflight.css`, confirmed directly, no override in this repo) means `max-w-3xl`'s `max-width: 768px` already governs the border-box (content plus padding), not content alone, so the container reaches its 720px content-width cap exactly when the viewport hits 768px, not 816px. The wrong constant meant every `sizes` string picked the fluid fallback instead of the fixed pixel value for any viewport in [768px, 816px), a real (if narrow) overfetch window undetected until an independent review checked the box-sizing model rather than trusting the original hand-derived comment.
    - **`responsiveGridFigureSizing`'s multi-tier `sizes` string needs a fixed/fluid split per tier, not just one for the whole grid.** A grid's own Tailwind breakpoint (e.g. `sm:` at 640px) can fire well before the container reaches its 768px cap — for the viewport range in between, that tier's column count is active but the container is still fluid, so a flat `(min-width: 640px) 352px` (the capped value) overstates the real box width by up to ~20% in that window. Every tier with `minWidth < 768` now emits two conditions instead of one — `(min-width: 768px) {capped}px` for once the container is truly capped, then `(min-width: {tier.minWidth}px) {fluid formula}` for the range below that — while a tier with `minWidth >= 768` still emits just one (the container is already capped by the time its own breakpoint can fire). This only ever produces one such split per `tiers` array in practice, since every real grid in this codebase has at most one tier with `minWidth` below 768 (`sm:`'s 640, always the narrowest non-fallback tier) — a `tiers` array with two or more sub-768 tiers would need the ordering re-verified by hand, since the split doesn't defend against that case.
    - **`image.responsiveStyles` stays disabled in `astro.config.mjs`, including after issue #274 — flipping it on was tried and reverted.** That flag bundles an additional stylesheet for Astro's own `data-astro-image-*` attribute hooks (confirmed via `generateImageStylesCSS.js` — a real `@layer astro.images` inline `<style>` block Astro injects and auto-hashes like any other non-`is:inline` `<style>` tag, not a `style="..."` attribute, so it's not a CSP problem either way per CLAUDE.md's `style-src` bullet). Issue #274 introduced `layout="full-width"` (next bullet), whose `width: 100%` rule has no Tailwind-preflight equivalent — a real, non-redundant reason to reconsider the flag, unlike `constrained`/`none`'s `max-width: 100%`/`height: auto`, which already exist via preflight. Enabling the flag was tried first, and reverted: its stylesheet ships in a **new** CSS layer, `astro.images`, and per the CSS cascade-layers spec a layer's priority is set by the order it's _first declared_ in the document — since this stylesheet is injected after Tailwind's own `@layer theme, base, components, utilities` declaration, `astro.images` ranks **above even `utilities`**, regardless of any rule's specificity inside it. Its `:where([data-astro-image]) { height: auto }` rule is unconditional (matches every layout value, not just `full-width`), so it silently outranked `WorkCard.astro`'s `h-full` utility on its own `layout="constrained"` cover image — confirmed via a real computed-style measurement showing a sub-pixel height mismatch between the image and its parent, invisible today only by coincidence (the parent's `overflow-hidden` masks it, and the Sharp-cropped cover's aspect ratio happens to already match the card's own). Reverted in favor of the narrow, hand-written rule in `global.css` (next bullet) instead of the whole flag.
    - **`content-image-sizing.ts`'s `FigureSizing` interface carries a `layout: 'full-width' | 'constrained'` field, and it isn't optional — every sizing helper must pick one deliberately.** `full-width` (via the hand-written CSS rule above) means the image always fills its actual current container at every breakpoint; `constrained` means it scales down but never grows past its own `width` value, matching Astro's real semantics for that layout (confirmed in `node_modules/astro/dist/assets/layout.js`). This distinction is what issue #274 was about: `responsiveGridFigureSizing`/`gridFigureSizing`/`fullWidthFigureSizing` all return `layout: 'full-width'`, since a grid figure's real available width changes across breakpoints as the grid's own column count changes — with `constrained` (the only mode this codebase used before #274), the figure's `width`/`height` HTML attributes reflected the widest (desktop-capped) tier, which then became a hard ceiling the image could never exceed even once the grid had collapsed to one column on mobile and far more space was available; the `sizes` attribute correctly described the wider mobile box for _source selection_, but the rendered CSS box size silently stayed frozen at the desktop value. `fixedWidthFigureSizing` (`storyblok-migration.mdx`'s 430px mobile-nav figure) is the one helper that still returns `layout: 'constrained'` deliberately — a figure narrower than its column by design at every viewport including mobile, which must never stretch to fill it. `ResponsiveImage.astro` passes `sizing.layout` straight through to Astro's `<Image>` rather than hardcoding one value, and `workCardCoverSizing()` (WorkCard.astro's cover, a sibling function returning `Pick<FigureSizing, 'sizes' | 'widths'>` only) is unaffected — `WorkCard.astro` calls `<Image>` directly with its own hardcoded `layout="constrained"`, a separate, out-of-scope-for-#274 case that may have the same underlying gap (untouched; if fixed, do it the same way). **Whenever a grid's Tailwind classes change (columns added/removed, a breakpoint prefix added), the paired sizing-helper call in the same MDX file must be checked too** — issue #274 itself shipped with exactly this drift on its first pass (two files' `grid-cols-2` → `grid-cols-1 sm:grid-cols-2` edits landed without updating their `gridFigureSizing(2)` calls to `responsiveGridFigureSizing(TWO_COLUMN_RESPONSIVE_TIERS)`, caught by `self-review`), the same class of bug this file's own "duplicated grid/sizing-call pair" bullet above already warns about.
    - **`ResponsiveFigure.astro` generates a `data-lightbox-src` (via `getImage({ src, format: 'webp', width: Math.min(src.width, 2560) })`) and forwards it to `ResponsiveImage` as a plain prop, separate from the deliberately-downscaled inline `src`/`srcset`.** The 2560px cap (`LIGHTBOX_MAX_WIDTH`, matching Astro's own largest built-in responsive-image breakpoint) was added by a `code-review` pass after the uncapped version shipped: with no `width` at all, `getImage()` re-encoded every one of the ~45 figures at full native resolution unconditionally at build time — several sources are 2000–4000px+ — regardless of whether that particular screenshot is ever opened in the lightbox. That's build-time cost, not visitor bytes (the lightbox `<img>` is only created/fetched lazily when opened, per the paragraph below), but it's real, avoidable Sharp/libvips work with no user-facing benefit, since nothing in a `max-h-full max-w-full` lightbox display can show more detail than ~2560px provides. Caught by `self-review`, not the initial implementation: `ImageLightbox.astro`'s gallery (dialog literally labeled "Enlarged screenshot") originally read each slide's image straight from the inline `<img>`'s `.src` DOM property — once the inline image started being served at its small container-sized width, that made "enlarge" show a blurry, upscaled version of an already-downscaled image instead of the sharp original. `ImageLightbox.astro`'s `describe()` now reads `img?.dataset.lightboxSrc || img?.src`, preferring the full-resolution variant when present. This is a deliberate, on-demand exception to the whole point of this issue: the byte-savings problem is about every screenshot loading unasked-for on page scroll, not about the one image a visitor explicitly clicks to inspect closely — `ImageLightbox.astro` already only builds slide `<img>` elements with `loading="lazy"`, so the full-resolution fetch only happens for images a visitor actually opens (or scrolls near, within the lightbox's own horizontal track). `e2e/lightbox.spec.ts`'s "the enlarged image is a full-resolution source, not the downscaled inline one" test guards this — a `.prose figure img`'s inline `src` and its `data-lightbox-src` must differ, and the opened lightbox slide must use the latter. `ResponsiveImage` itself doesn't know what a lightbox is — `data-lightbox-src` is declared as a plain optional pass-through prop on its `Props` type and handed straight to the underlying `<Image>` unexamined, which works because `service.js`'s `getHTMLAttributes()` only strips a known set of image-specific option keys and spreads everything else onto the rendered `<img>` — confirmed by inspecting a real build's output, not assumed from the types.
    - **`ImageLightbox.astro` builds every slide into the DOM up front, and only `aria-hidden` (toggled in `updateCaption()`) keeps the inactive ones out of the accessibility tree — horizontal scroll-snap alone only keeps them visually offscreen.** Confirmed via Chrome DevTools Protocol accessibility-tree inspection (issue #190): before this fix, every slide's image was exposed as a non-ignored node regardless of `currentIndex`, so a screen reader user linearly browsing the open `role="dialog"` would hear every image described consecutively, ahead of the caption/counter live region that's supposed to announce the current one. `updateCaption()` already runs on every `goTo()`/`syncFromScroll()` call, so the fix piggybacks on it: a `slideElements: HTMLDivElement[]` array (populated alongside the existing slide-building loop) gets `aria-hidden="true"` set on every index but `currentIndex`, which is `removeAttribute`'d instead. Deliberately `aria-hidden`, not `inert` — the suggested alternative — since these slide wrappers have no focusable content of their own (only the original in-prose trigger `<img>` is keyboard-reachable, via `tabIndex={0}`/`role="button"`), so there's no focus-trapping benefit `inert` would add, and `aria-hidden` alone avoids any risk of interacting with the dialog's own click-outside-to-close handler.
    - **`densities` and `sizes`+`widths` are mutually exclusive on one shared union type, `ResponsiveImage.astro`'s exported `ResponsiveImageSizing`, not hand-copied between the two components.** `ResponsiveImage`'s own `Props` intersects it with `src`/`alt`/`width`/`class`/`data-lightbox-src`; `ResponsiveFigure`'s `Props` intersects the same imported type with its figure-only fields (`caption`/`captionClass`/`imgClass`) instead of re-declaring the union. `.astro` files can't `export` values (`eslint-plugin-astro`'s `no-exports-from-components` rule, confirmed by a throwaway test file — `export const foo = 1` fails lint, `export type Foo = {...}` doesn't, since a type export isn't a component export at runtime), so this works as a type-only export, no separate `.ts` module needed. Extracted after a `code-review` pass flagged the duplicated union as a real drift risk: earlier versions of this file had two independent copies, and the exact `widths?: never` fix two bullets above already had to be applied to both by hand once — a future third field would carry the same risk without a shared source. Both components destructure `Astro.props` with a rest pattern (`const { src, alt, width, class: className, 'data-lightbox-src': lightboxSrc, ...sizing } = Astro.props`) rather than pulling `densities`/`sizes`/`widths` out individually — since every named key comes from the shared (non-union) part of `Props`, TypeScript keeps the `...sizing` rest correctly typed as the full `ResponsiveImageSizing` union instead of collapsing it into three independently-optional fields. `ResponsiveFigure` spreads `{...sizing}` onto `<ResponsiveImage>` completely unexamined — no reconstruction needed, since `sizing` is already exactly the right shape. `ResponsiveImage` still branches once (`sizing.sizes ? { ...sizing, layout: 'constrained' } : { densities: sizing.densities ?? [1, 2, 3] }`), since it alone needs to add `layout`/the `densities` default — but that's now the only such branch in either file, down from one duplicated in both, addressing a `code-review` finding that the old per-file reconstruction ternaries would have to be updated in two places by hand for any future third field.
    - **`content-image-sizing.ts`'s `buildSizesAttr(tiers, fallbackExpr)` is the one place a `sizes` attribute string gets assembled from `{minWidth, expr}` conditions — `gridFigureSizing`, `responsiveGridFigureSizing`, and `fixedWidthFigureSizing` all call it rather than each independently joining strings.** It sorts `tiers` by `minWidth` descending itself before joining, rather than trusting callers to pass them pre-sorted — a `code-review` pass found `responsiveGridFigureSizing` trusted caller order (docstring-only, unenforced) while `fixedWidthFigureSizing` built and sorted its own local list, two different reliability guarantees for the same "ordered conditions plus fallback" shape with nothing forcing them to stay consistent. A wrong order is a real, silent bug: `sizes` matches its first satisfied condition, so a transposed pair changes which value wins at a given viewport with no error anywhere.
    - **`responsiveGridFigureSizing`'s fallback (`columns: 1`, no `minWidth`) tier caps its own `widths` ladder at the narrowest real tier's `minWidth` minus the container padding, not at `columnWidth(1)` (720px, the desktop-capped value).** The fallback's `sizes` condition only ever wins below the narrowest real tier's breakpoint (640px for every current 2-/3-tier grid), where the container is fluid and never reaches 720px — a `code-review` pass found the ladder was generating 2x/3x candidates off 720px (1440/2160, clamped to 2000 by Astro's own native-width fallback) that no browser in that tier's actual active viewport range could ever request, confirmed against real build output (`dist/work/voices-conference-website/index.html` shipped unreachable 1440w/2000w candidates before this fix). Capped to `640 − 48 = 592` instead, so the 2x/3x extensions (1184/1776) are proportional to the width a device in that range can actually need. **This cap's "narrowest real tier" is computed with `Math.min()` over every real tier's `minWidth`, not by reading the last array element** — a later `code-review` pass (independently confirmed by two separate finder passes) found the original version trusted `realTiers[realTiers.length - 1]` to be the narrowest, which only holds if `tiers` happens to be listed in strict descending order; `ResponsiveGridTiers`' tuple type enforces shape, not that ordering, and `buildSizesAttr` (a few lines away in the same file) already treats the ordering as a courtesy rather than a guarantee by re-sorting for itself — an inconsistency that was itself a sign the assumption wasn't safe. Every current tier constant (`TWO_COLUMN_RESPONSIVE_TIERS` etc.) happens to already be correctly ordered, so this was a latent bug with no live symptom yet, not a rendering regression — `Math.min()` costs nothing and removes the ordering assumption entirely rather than just documenting it more forcefully.
    - **`responsiveGridFigureSizing`'s returned `width` field is computed from the real tier with the largest `minWidth`, not from `tiers[0]`.** The same ordering-trust gap `Math.min()` (above) and `buildSizesAttr`'s own re-sort already closed for `widths`/`sizes` was still open for `width` — a later `code-review` pass caught that `width: columnWidth(tiers[0].columns)` was the one field in this function's return value still trusting array position. Fixed with `realTiers.reduce((widest, tier) => tier.minWidth > widest.minWidth ? tier : widest)` rather than a fourth independent "find the narrowest/widest" implementation. Every current tier constant already lists its widest tier first, so — like the `widths`-ladder fix above — this had no live rendering symptom (confirmed: the `width="352"`/`width="229"` attributes in a real build's HTML are byte-identical before and after), it just removes the last place this file's `ResponsiveGridTiers` tuple type's "shape enforced, order not" gap could bite silently.
    - **`mergeCloseWidths`'s own comment previously overclaimed "never removes a genuinely distinct tier's own size"** — a `code-review` pass pointed out it can and does drop a tier's own exact candidate in favor of a close neighbor from a different tier (e.g. a tablet tier's 2x candidate merged away in favor of a nearby desktop-tier candidate), which is fine given the 24px threshold is well under any perceptible quality difference, but the comment's guarantee was simply inaccurate. Reworded rather than changed behavior — this one was a documentation fix, not a bug fix.
    - **`voices-conference-website.mdx` imports its three distinct grid-tier shapes (`TWO_COLUMN_RESPONSIVE_TIERS`/`THREE_COLUMN_RESPONSIVE_TIERS`/`REGIONAL_RESPONSIVE_TIERS`, exported from `content-image-sizing.ts`, `: ResponsiveGridTiers` typed) instead of repeating the tier array literal at each of the file's 11 `responsiveGridFigureSizing` call sites** (`THREE_COLUMN_RESPONSIVE_TIERS` alone would otherwise be retyped verbatim 6 times) — extracted after a `code-review` pass flagged the repetition as past the "4th identical copy" threshold CLAUDE.md's own `WorkGrid.astro`/`SectionHeader.astro`/`PageHeader.astro` precedents use. Originally defined as local `export const`s inside the MDX file itself; moved into `content-image-sizing.ts` once CLAUDE.md's "MDX bodies aren't real TypeScript" bullet was discovered — see that bullet for why.
    - **`ResponsiveFigure.astro`'s `captionClass` composes with its default (`'mt-2 text-sm text-muted'`) via `class:list`, the same additive pattern `imgClass` already used — it doesn't replace the default outright.** An earlier version had a plain default-parameter fallback (`captionClass = 'mt-2 text-sm text-muted'`) that a passed-in `captionClass` fully overwrote, so the two `max-w-xs` mobile-screenshot call sites needing centered captions had to retype the entire default string plus `text-center` by hand — a `code-review` pass flagged this as silently drifting the moment the component's own default ever changed, since those two call sites' hardcoded copies wouldn't follow. Both now just pass `captionClass="text-center"`.
    - **`CaseStudyLayout.astro`'s container `<div class="mx-auto max-w-3xl px-6 py-24">` carries a `{/* */}` comment pointing at `content-image-sizing.ts`, and that file's own top comment points back** — a `code-review` pass flagged the pixel constants (`CONTAINER_CAP_PX`/`CONTAINER_CAP_BREAKPOINT`/`CONTAINER_PADDING_PX`) as connected to this exact class string only by one-directional prose, the same magic-number-sync risk CLAUDE.md's favicon bullet already documents for `--color-accent`'s three hardcoded copies. Neither file enforces the link programmatically (there's no shared constant to import — Tailwind classes aren't JS values), so this is a documentation-only guard: if this class ever changes, grep for both comments, not just one. **This same unenforced-duplication shape recurs twice more in this file, both accepted for the same reason: no mechanism in this codebase reads a Tailwind utility class's value back into JS/TS.** `GRID_GAP_PX = 16` duplicates every case-study grid's `gap-4` class, and each `gridFigureSizing`/`responsiveGridFigureSizing` call site's `columns`/`tiers` argument duplicates its sibling `<div>`'s `grid-cols-N`/`sm:`/`lg:` classes two lines above it in the same MDX file — a `code-review` pass flagged both as real drift risk (editing a grid's Tailwind classes without updating the matching call, or vice versa, produces a silently-wrong `sizes` value with nothing to catch it). Separately, `responsiveGridFigureSizing`'s tier `minWidth` values (640/1024) duplicate Tailwind's stock `sm`/`lg` breakpoints, unsourced from any token — lower risk since `global.css`'s `@theme` block defines no `--breakpoint-*` override today, but would silently desync if one were ever added. All three are left as-is: fixing them for real would mean either parsing Tailwind's generated CSS at build time to extract real values (a new build-time dependency for a handful of numbers) or moving the grid definition itself into a shared component that owns both the markup and the sizing call together (the `ResponsiveFigureGrid.astro` shape a `code-review` pass floated) — real architectural options, but disproportionate to three numbers that in practice change rarely and are each covered by an explicit pointer in this skill for whoever does change them. **This finding was re-raised again in a later `code-review` round** (this time framed as "50 call sites," not "three numbers," and paired with a proposed `ResponsiveFigureGrid.astro`/`GridFigureRow.astro` wrapper citing `InterlinkRow.astro` as precedent) — still declined, and this is the final word on it, not a reopening: `InterlinkRow.astro`'s extraction was triggered by 4 _identical_ copies of one fixed grid shape (see the "Nth copy" convention documented throughout CLAUDE.md); this codebase's case-study grids are not that — column counts, tier shapes, and even the wrapper `<div>`'s own classes (`my-8`/`my-6`, `gap-4`, `flex flex-col sm:flex-row` for the fixed-width pairs vs. `grid grid-cols-N` for the rest) vary per call site, so a wrapper component would need enough configuration surface to cover that variance that it stops being meaningfully simpler than "a `<div>` plus a sizing-helper call," while adding a new component, new MDX migration across 4 files, and new tests — exactly the kind of large late-stage swing this PR's review cycle was asked to stop making. Reopen only alongside a concrete new case study that would make the duplication's shape genuinely uniform, not as a standalone refactor.
    - **`responsiveWidths`'s merged candidate list gets one extra "bridge" width where the fallback tier's ladder and a real tier's ladder meet, when — and only when — that meeting point is a genuine gap** (issue #225): a real Lighthouse run flagged `TWO_COLUMN_RESPONSIVE_TIERS`'s two figures overfetching ~29KB combined, traced to a real, common mobile scenario (a sub-640px viewport at a non-integer DPR like 1.75, needing roughly 616–637 device px) landing in the 112px gap between the fallback ladder's own 1x (592) and the real tier's own 2x (704) — neither ladder's own `[1x, 2x, 3x]` multiples land _between_ two different tiers' anchors, since that gap is a property of the two anchors' relationship, not either ladder's internal spacing, so densifying either ladder alone (the issue's own suggested fix, a `1.5x` step) provably doesn't close it — confirmed by hand-computing every multiple of both 352 and 592 and finding none fall in (592, 704). Fixed instead by computing `nextRealAboveFallback` (the smallest real-tier candidate above `fallbackBase`) and inserting `Math.round(Math.sqrt(fallbackBase * nextRealAboveFallback))` (592×704 → 646) directly into the candidate list before the existing `mergeCloseWidths` call — geometric, not arithmetic, mean, since DPR/resolution steps are multiplicative. Verified against real build output, not just hand math: `voices-2020`'s and `voices-2020-pre-eleventy`'s `widths` both gained exactly `646` (`dist/work/voices-conference-website/index.html`), and at the issue's own 412px/DPR-1.75 scenario the selected candidate drops from 704 to 646 — reducing area-scaled overfetch from ~32% to ~11% against Lighthouse's own reported 613px-wide need (`(704/613)² ≈ 1.32` vs `(646/613)² ≈ 1.11`), an estimated ~19KB of the original ~29KB flagged waste recovered across both images. **The bridge is guarded to fire only when `fallbackBase` doesn't already coincide with one of the real tiers' own bases** (`!realBases.includes(fallbackBase)`) — caught by a `self-review` pass on the first version, which had no such guard and found it firing on every `gridFigureSizing()`/`fullWidthFigureSizing()` call site too (these build a synthetic fallback tier with the _same_ column count as their one real tier, so `fallbackBase` there already equals that real tier's own base and there's no seam at all to bridge), silently adding one spurious Sharp-encoded variant to ~30 unrelated figures across every case study with no quality benefit — confirmed fixed by rebuilding and diffing `dist/work/brand-evolution/index.html`'s `widths` back to their pre-change values. The same pass also added a `fallbackBase > 0` guard against a hypothetical future tier list producing a negative base, which would otherwise make `Math.sqrt` return a silent `NaN` that `astro check` doesn't catch (`Number.isFinite`'s existing check only guards `nextRealAboveFallback`, not `fallbackBase`) — the same class of build-time-silent bug CLAUDE.md's own "MDX bodies aren't real TypeScript" bullet already warns about, just from a different source. Out of scope, per the issue's own scope note: a separate ~14KB WebP compression-factor flag on the same two images — untouched.
    - **Declined: an e2e test asserting real rendered `getBoundingClientRect()` geometry against `content-image-sizing.ts`'s pixel constants**, proposed as a "cheaper middle option" between the doc-comment-only sync guard above and doing nothing. Not pursued: this repo's e2e suite has no existing precedent for asserting computed layout geometry (as opposed to DOM structure, text content, `href`s, or `aria-*` state) anywhere else, and Playwright's viewport/font-rendering environment can shift a pixel-perfect assertion for reasons unrelated to a real regression (subpixel rounding, a webfont substitution during a slow CI run) — introducing that whole new _class_ of flaky-test risk to guard three rarely-changed constants is a worse trade than the doc-comment already in place. Revisit only if this class of pixel-sync bug actually recurs in practice, not preemptively.
    - **Declined: parallelizing `ResponsiveFigure.astro`'s lightbox `getImage()` call with `ResponsiveImage`'s own internal one.** A `code-review` pass correctly noted these two Sharp encode passes per figure run sequentially, not concurrently — Astro's frontmatter script runs to completion (including any `await`) before the template below it (and any child component it renders, like `<ResponsiveImage>`) starts, and a child component's own internal `getImage()` call isn't exposed as an externally-awaitable promise the parent could `Promise.all` alongside its own. Fixing this for real would mean either merging `ResponsiveImage` back into `ResponsiveFigure` (undoing the split documented above) or having `ResponsiveFigure` call Astro's `getImage()`/`getSrcSet()` directly for both variants and render a raw `<img>` itself instead of delegating to `<Image>` — real restructuring, not a local tweak. Left as-is because the measured cost doesn't justify either: real `npm run build` runs in this repo complete all image transforms (currently ~230+ variants across 4 case studies) in roughly 1–3 seconds total, so the actual sequential-vs-parallel difference per figure is on the order of tens of milliseconds, not a build-time problem worth the added architectural risk. Revisit only if a future case study's image count grows enough to make build time itself a real complaint.

## Principle (`src/content/principles/`)

1. Create `src/content/principles/NN-slug.md` — list existing files, take the highest two-digit prefix, increment it, zero-pad. Order comes **only** from this filename prefix; there is no `order` field in the schema. Renaming the file later reorders it.
2. Frontmatter: just `title` and `description`.
3. Update tests:
    - `e2e/principles.spec.ts` — bump the `toHaveCount(N)` assertion in `shows all principles`, and the literal number string in `last principle is numbered N`.
    - `e2e/home.spec.ts`'s `shows N principle cards` test does **NOT** need to change. `PrinciplesSection.astro` always shows exactly the first 6 principles sorted by filename (`.slice(0, 6)`), regardless of how many exist in total — only the `/principles/` page shows the full list. The homepage count only shifts if you insert a new principle with a prefix _lower_ than 06, which displaces one of the current top 6 (rare — new principles are normally appended at the end).

## Blog post (`src/content/blog/`)

1. Copy `src/content/blog/_template.md` to `src/content/blog/<slug>.md` and fill it in — it already has the right frontmatter shape and a reminder note at the bottom.
2. Frontmatter: `title`, `description`, `date`, `tags: [...]` — at least one tag required, there's no default so it can't be omitted. `draft` defaults to `true` in the schema.
3. **Never set `draft: false` on your own initiative** — leave new posts as drafts unless the user explicitly asks you to publish this one. This is a standing project rule, not a one-off judgment call.
4. No e2e test currently asserts anything about blog post count or content — nothing else to update.
