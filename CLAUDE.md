## What this is

Personal portfolio site for Philipp Storl — Astro v7, Tailwind v4, a couple of React islands, deployed on Netlify. Content (case studies, principles, blog posts) lives in `src/content/` as Markdown/MDX with zod-validated frontmatter.

## Stack facts that shape how to make changes

- **Astro-first, React only where needed.** The only React components are `src/components/ui/ContactForm.tsx` and `src/components/ui/ThemeToggle.tsx`. Everything else is `.astro`. Don't reach for React for new components unless there's real interactivity that needs it.
- **Tailwind v4 is CSS-first** — there is no `tailwind.config.js`. Theme tokens (fonts, colors, animations) live in the `@theme` block in `src/styles/global.css`. **Do not put infinite animation tokens in `@theme`** (e.g. `--animate-foo: foo 2s infinite`): Tailwind v4 auto-generates an unconditional `.animate-foo` utility class from every `--animate-*` token, which overrides any media-query-guarded manual class definition and silently breaks `prefers-reduced-motion` gating. Define infinite animations only as a `@keyframes` + `.animate-foo { animation: ... }` class, both inside the `@media (prefers-reduced-motion: no-preference)` block — no `@theme` token.
- **TypeScript strict mode** (`astro/tsconfigs/strict.json`), path alias `@/*` → `src/*` (see `tsconfig.json`).
- **Node 26** is pinned in both `netlify.toml` and CI — match it locally.

## Conventions to respect

- **Trailing slashes are mandatory** on every internal route (`trailingSlash: 'always'` in `astro.config.mjs`). Every `href`, `page.goto()`, and `toHaveURL()` must end in `/`. This is enforced in CI by `npm run check:trailing-slashes` (`scripts/check-trailing-slashes.js`) — run it locally after touching any route/link, since a missing slash fails the build job, not just lint. The script derives which routes to check by scanning `src/pages/` itself (each top-level `.astro` file, and each subdirectory with an `index.astro`, becomes a checked static route; a subdirectory that also has a `[slug].astro`/`[...slug].astro` becomes a checked dynamic prefix) rather than hand-listing routes, so a new page or collection route is covered automatically without editing the script. It checks both a literal quoted href (`href="/work/foo/"`) and a computed one — either inline (``href={`/work/${slug}/`}``) or, matching the established convention of extracting the href into a named `const` before use (see `WorkCard.astro`), a `const`/`let` assignment (`` const href = `/work/${slug}/` ``) — by requiring the template literal not end immediately after an interpolation with no trailing `/` literal after it.
- **The `/404` route is the one deliberate exception to trailing slashes, and it's load-bearing for `netlify.toml`'s catch-all redirect.** Despite `trailingSlash: 'always'`, Astro's build internals force `dist/404.html` (and `/500`) to stay flat at the output root rather than `dist/404/index.html` — `node_modules/astro/dist/core/output-filename.js`'s `STATUS_CODE_PAGES` set special-cases just those two routes, unconditionally, regardless of the `trailingSlash`/`build.format` config. `netlify.toml`'s `[[redirects]]` rule targets `/404` (no slash) specifically because of this, and `scripts/check-trailing-slashes.js` excludes `404` from its checked routes (`excludedStaticPageNames`) for the same reason — both are documented inline at their respective locations. This is undocumented, version-specific Astro behavior, not a guaranteed contract: re-verify `dist/404.html` still exists at the build root (`ls dist/404.html`) after any Astro major-version bump, since a change here would silently break the redirect with nothing in CI to catch it.
- **Content collections** (`src/content.config.ts`) define three collections with different ordering rules — easy to mix up:
    - `work/` — order comes from a frontmatter `order` field (filenames become URL slugs, so they can't encode order). `coverImage` is optional (uses the `image()` schema helper, not a plain string) — the home page card falls back to its text-only layout when absent.
    - `principles/` — order comes from the filename prefix (`01-`, `02-`, …); there's no `order` field. Renaming a file reorders it.
    - `blog/` — posts default to `draft: true`; never flip to `false` unless asked to publish.
- **The homepage About section (`AboutSection.astro`) and the dedicated `/about/` page (`src/pages/about.astro`) render the same `about.ts` bio in full** — unlike `PrinciplesSection.astro`'s `.slice(0, 6)` teaser, About is deliberately not trimmed on the homepage (both paragraphs + the facts `<dl>` appear in both places). `AboutSection.astro` adds only a "Read more about me" CTA (same `ArrowRight`-icon link idiom as `PrinciplesSection.astro`'s "Read all N principles") pointing at `/about/`, whose extra content is a "How this site is built" section backed by `src/data/stack.ts` (the site's own Astro/Tailwind/React/TypeScript/Netlify stack, distinct from `about.ts`'s facts about Philipp's professional stack — don't conflate the two). On the homepage, `AboutSection` sits right after `WorkSection` and before `PrinciplesSection`/`RecommendationsSection` (`src/pages/index.astro`, `src/data/navigation.ts` follows the same order) — Work still leads for anyone skimming for proof, but personal context comes before the more granular Principles/Recommendations sections, and Recommendations (external social proof) stays the section immediately before Contact.
- **The homepage Work section (`WorkSection.astro`) and the dedicated `/work/` page (`src/pages/work/index.astro`) share their collection-fetch-and-grid logic via `WorkGrid.astro`** (`src/components/work/`), rather than each re-querying and re-rendering it — the same "one shared source, not two copies" principle as `about.ts` above, applied to a fetch+markup fragment instead of static prose. `WorkGrid.astro` queries the `work` collection, sorts by `order`, and renders the `[featured, ...rest]` grid using `WorkCard.astro` (also relocated to `src/components/work/`, since it's no longer home-page-exclusive once both call sites use it); each call site just wraps `<WorkGrid />` in its own layout div. Unlike About, Work isn't trimmed for the homepage teaser — both places show the same full 4-card set — so `WorkSection.astro` adds only a "See all work" CTA (same idiom as `AboutSection.astro`'s "Read more about me") pointing at `/work/`. Case study back-links in `CaseStudyLayout.astro` ("← All work" / "← Back to all work") point at `/work/`, not a `/#work` homepage anchor — `navigation.ts`'s `Work` nav item does too, matching how `About` already points at `/about/` rather than `/#about` despite `AboutSection` also living on the homepage.
- **All four homepage teaser sections (`AboutSection.astro`, `PrinciplesSection.astro`, `RecommendationsSection.astro`, `WorkSection.astro`) share their heading+CTA row via `SectionHeader.astro`** (`src/components/home/`, `headingId`/`heading`/`href`/`label` props — the `href`/`label` naming deliberately matches `InterlinkCard.astro`'s link-prop vocabulary below) instead of each repeating the same `h2` + `ArrowRight`-icon CTA link markup — the 4th byte-identical copy (added when `WorkSection.astro` got its own CTA row) is what prompted the extraction (issue #97). It only owns the `mb-12 flex ...` wrapper `<div>`; the parent `<section id=... aria-labelledby=...>` landmark stays in each call site. Each call site derives a single `const headingId = '...-heading'` in its frontmatter and passes that same variable to both `aria-labelledby` and `<SectionHeader headingId={headingId}>`, rather than repeating the literal string twice, so the two can't drift out of sync. `PrinciplesSection.astro`/`RecommendationsSection.astro` compose their dynamic `Read all {totalCount} …` label as a template literal before passing it in — the component takes the final `label` string, not a count. Adding a 5th homepage teaser section should reuse this rather than re-inlining the heading+CTA block; it's a `home/`-scoped pattern distinct from `InterlinkCard.astro` below, which is used across dedicated pages rather than homepage sections.
- **`/about/`, `/principles/`, `/recommendations/`, and `/work/` fully interlink each other** via `src/components/ui/InterlinkCard.astro` (`href`/`eyebrow`/`label` props) rendered as a 3-up grid through `src/components/ui/InterlinkRow.astro`, which takes an `items: Array<{ href, eyebrow, label }>` prop and maps it into `InterlinkCard`s inside the shared `grid grid-cols-1 gap-4 sm:grid-cols-3` wrapper — extracted once this grid became the 4th byte-identical copy across these pages (issue #99), the same "Nth copy" trigger as `SectionHeader.astro`/`WorkGrid.astro`/`PageHeader.astro` above/below. `InterlinkRow.astro` deliberately renders only the grid row, not an outer positioning wrapper, because the row's _position_ differs per page: `principles.astro`/`recommendations.astro`/`work/index.astro` give it its own `mx-auto max-w-3xl px-6 pb-32` div right before `<Footer />`, while `about.astro` nests it inside the existing `pb-24` div right after the facts `<dl>` with `mt-10` spacing instead — passed via `InterlinkRow.astro`'s optional `class` prop (`class:list`-merged, the same class-forwarding convention `Main.astro`/`InitialsAvatar.astro` use) rather than baking a second wrapper div into `about.astro`. Each page links to the other three — About → Work/Principles/Recommendations, Principles → About/Work/Recommendations, Recommendations → About/Principles/Work, Work → About/Principles/Recommendations — so adding a fifth page to this square means adding one more `items` entry to each of the four existing pages' arrays, not just the new one (and widening `InterlinkRow.astro`'s grid past `sm:grid-cols-3`). The `eyebrow` copy is written per-direction (e.g. "See these principles in practice" from Recommendations vs. "See how this plays out" from About) rather than reused verbatim, since the same destination reads differently depending on where you're coming from.
- **`/about/`, `/principles/`, `/recommendations/`, and `/work/` also share their page-header block via `src/components/ui/PageHeader.astro`** (`eyebrow`/`title` props, intro paragraph as a default `<slot />`), instead of each repeating the same eyebrow `<p>` + `<h1>` (with its `font-variation-settings: 'opsz' 72`) + intro `<p>` wrapped in `mx-auto max-w-3xl px-6 pt-24 pb-16 md:pt-32` — the 4th byte-identical copy (added when `/work/` got its own header, #96) is what prompted the extraction (issue #98), the same pattern as `SectionHeader.astro`'s and `WorkGrid.astro`'s extractions above. It lives in `ui/`, not `home/` or `layout/`, matching `InterlinkCard.astro`'s placement immediately above as "used across dedicated pages rather than homepage sections" — distinct from `Header`/`Main`/`Footer`, which are site-wide chrome on every page. The component owns the wrapping intro `<p class="text-lg leading-relaxed text-muted">`; call sites only supply its contents via the slot, which is why `recommendations.astro`'s intro (a LinkedIn link mid-sentence) still works unchanged through the slot rather than needing its own prop.
- **Clickable cards that sit next to static/non-interactive tiles need a visibly different resting state, not just a hover change.** `InterlinkCard.astro` (`src/components/ui/`) originally shared the same `border-border bg-card` treatment as the About page's facts `<dl>` tiles directly above it, and read as more static content rather than a link. Fixed by giving it an always-on accent tint at rest (`border-accent/40 bg-accent/10`, the same `accent/10`-`accent/40` vocabulary `InitialsAvatar.astro`'s badge and the theme toggle's active-state pill already use) so it's visually distinct from neutral bordered tiles before any interaction, then deepening that same tint further on hover (`hover:border-accent/70 hover:bg-accent/15`) plus the site's existing `group-hover:text-accent` heading color and `group-hover:translate-x-0.5` arrow shift — the same hover vocabulary `WorkCard.astro` and `PrinciplesSection.astro`'s CTA link already use, just one step deeper from an already-tinted rest state. A `ring`/`ring-offset` treatment was tried and rejected — visually disconnected from the card against the page background and out of place next to the site's flat, border-only aesthetic (confirmed by user feedback, not just a hunch). Also deliberately not a `shadow-*`/elevation treatment, since the site has zero `box-shadow` usage anywhere. Reuse accent-tint-at-rest + deeper-tint-on-hover for any future card-shaped link that sits near non-interactive content — don't reach for `ring` or shadow.
- **Not every content set needs a content collection.** `work`/`principles`/`blog` all have long-form Markdown/MDX bodies, which is what the `glob()` loader + zod schema in `content.config.ts` is for. `src/data/recommendations.ts` (LinkedIn recommendations — name, title, date, relationship, quote) has none of that: each entry is a short structured record with no rich body, so it follows the plain `interface` + exported `const` array pattern already used by `about.ts`/`hero.ts` instead. Reach for a collection only when entries need Markdown rendering, `getCollection()`-style filtering/`render()`, or per-entry `.md`/`.mdx` files; otherwise a typed data file is less machinery for the same result. `recommendations.ts` uses a `featured: boolean` field (same name as `work`'s) to mark the 6 shown in the homepage teaser — `RecommendationsSection.astro` still `.slice(0, 6)`s the filtered result, mirroring `PrinciplesSection.astro`'s `.slice(0, 6)` cap, so a future `featured: true` addition can't silently grow the homepage section. Adding or removing an entry also requires bumping the hardcoded `toHaveCount(n)` in `e2e/recommendations.spec.ts`'s "shows all recommendations" test — it asserts an exact `<li>` count against `recommendations.length`, so it's a stale-count failure waiting to happen if skipped (caught by `self-review`, not CI, the first time).
- **`InitialsAvatar.astro`** (`src/components/ui/`) is the only avatar/photo-placeholder pattern in the codebase — a circular initials badge (`bg-accent/10`/`border-accent/20`/`text-accent`, same token set as `CategoryBadge.astro`), used because the recommendations feature intentionally omits LinkedIn profile photos. It strips a leading `Dr.`/`Mr.`/`Mrs.`/`Ms.` before computing initials so a title prefix doesn't eat one of the two letters. If a future feature needs a person's photo or avatar, use this component for the no-photo case rather than inventing a second pattern.
- **OG image generation** (`src/utils/og-image.ts`) intentionally uses `@fontsource/fraunces` (non-variable) alongside the variable font used by the site, because Satori can read WOFF/TTF/OTF but not WOFF2, and the variable font only ships WOFF2. Don't consolidate these to "simplify" — it'll break OG images.
- **`public/favicon.svg` renders in a standalone context with no access to the site's webfonts.** A `<link rel="icon">` SVG doesn't get the page's `@font-face`/`@fontsource` setup (`Fraunces Variable`, `DM Sans`), so any `font-family` there falls back to whatever's installed on the visitor's OS — referencing the site's display font does nothing. At real favicon scale (16-32px) a serif face also reads noticeably worse than a bold sans-serif, so use a system sans-serif stack (`'Helvetica Neue', Arial, sans-serif`) instead. The icon is a solid opaque fill by design, not a `prefers-color-scheme`-aware asset like `BaseLayout.astro`'s `theme-color` meta tags — being opaque, it doesn't need to adapt to browser-chrome light/dark themes the way a transparent icon would, so don't add a light/dark split unless asked. Its `rect fill` is also a third hardcoded hex approximation of `--color-accent`, alongside `og-image.ts`'s `colors.accent` — a standalone `/self-review` run (2026-08-10) caught that a `--color-accent` token change had updated the latter but missed this one, since it isn't mentioned by the "kept in sync by comment" convention documented on the category-badge bullet below. Update all three together when `--color-accent`'s light-mode value changes.
- **A case study with a `coverImage` gets an inset screenshot panel on its OG image**, not just title/category text. Since `entry.data.coverImage` only exposes the Astro-optimized public URL (which isn't guaranteed to exist on disk yet during the same build pass that generates OG images), `src/pages/og/[...slug].png.ts` re-reads the raw frontmatter directly via `entry.filePath` to resolve the original source file, then crops it with Sharp to the same 16:10 ratio and top-anchored position as `WorkCard.astro`'s cover (a 1:1 crop looked broken rather than like a real preview) before embedding it in the Satori template. Don't try to wire this through `entry.data.coverImage`'s `src` — that's a build-order race.
- **Category badge markup and color are centralized, not duplicated per usage site.** `src/components/ui/CategoryBadge.astro` renders the pill (`rounded-full border px-2.5 py-0.5 text-xs font-medium` + per-category border/text color) and is used by both `WorkCard.astro` and `CaseStudyLayout.astro` — don't reintroduce the `<span>` markup inline at a new call site, use the component. Its colors come from `src/utils/category-colors.ts`'s `getCategoryBadgeClass()`. `og-image.ts` can't consume Tailwind classes or the component (Satori renders plain style objects), so it separately imports `CATEGORY_HEX_COLORS` from the same file, a hand-maintained hex approximation of the same three colors, kept in sync by comment only — update both exports together when adding a category or changing a color. OG images only ever render against the light background (there's no per-request dark-mode toggle at build time), so `CATEGORY_HEX_COLORS` intentionally has no dark-mode variant. In `og-image.ts`, the top-of-card "label" slot is two different things depending on the page: a plain-text `label` string for home/principles (`'How I work'`, the years-of-experience blurb), or the pill-badge `category` for case studies — `generateOgImage`/`buildTemplate` take both as separate optional params rather than overloading one, so a future non-category label on a work page doesn't have to fight the badge styling. None of the three category colors reuse `--color-accent` — Engineering (`rose-700`/`rose-400`) and Leadership (`yellow-800`/`amber-400`) each use a standard Tailwind swatch in `CATEGORY_BADGE_CLASSES`, chosen deliberately spread across the hue wheel (issue #62) rather than the nearest-looking default: a color dark enough to clear 4.5:1 text contrast on the near-white `--color-background` loses most of its available chroma, so any two badge hues within ~30-40° of each other on the _warm_ side (red through amber, roughly hue 0-95 in OKLCH) read as the same muted rust-brown regardless of exact hue — Engineering and Leadership only became visually distinct once spread to hue ~17 (`rose-700`, a true red) and hue ~62 (`yellow-800`, a true gold) respectively. If a fourth category is ever added, don't just pick "a Tailwind color that's technically a different hue" — check it against the others at real badge lightness/contrast on its actual rendering background (`bg-card`, not just `bg-background` — the two differ enough in lightness to flip a borderline color between pass and fail), not as a large swatch, since the muddiness only shows up at accessible-contrast darkness. Leadership was originally `yellow-700`, which measured 4.01:1 against `bg-card` (below the 4.5:1 AA minimum for text) despite reading as compliant against `bg-background` (4.65:1) — bumped to `yellow-800` (5.55:1 on `bg-card`) once verified by ground-truth contrast measurement rather than assumed from the swatch name alone.
- **Years-of-experience figures are computed in `src/utils/experience.ts`, never hardcoded as a number.** Two distinct figures, both used as digits ("16 years", not "Sixteen years") for readability:
    - `getYearsOfExperience()` — total career length, measured from a fixed start constant (`2010-02-01`) to `now`. Used in `src/data/hero.ts`, `src/data/about.ts`, `src/pages/about.astro` and `src/pages/index.astro` (both meta `description`s), `src/pages/principles.astro`, `src/pages/404.astro`. Like the footer's copyright year, this evaluates at build time (the site has no `output` override, so it's static) — it updates on the next deploy after each anniversary, not live in the browser.
    - `getStaffbaseTenureYears()` — the Staffbase-specific tenure, used in `src/data/hero.ts`'s `description`, `src/data/about.ts`'s first bio paragraph, `src/pages/about.astro` and `src/pages/index.astro`'s meta `description`s, and inline (via a body-level `import { getStaffbaseTenureYears } from '@/utils/experience'`, the same pattern `voices-conference-website.mdx` already uses for image imports) in the prose of `brand-evolution.mdx` and `storyblok-migration.mdx`. This one is computed between two **fixed** dates (start and last day, both already in the past), not against `now` — that tenure is over, so it must never grow past its true length in a later build.
    - The only places it's still a plain hardcoded `8` are case study **frontmatter** (`title`/`description` — these are validated as plain zod strings before any component renders, so they can't execute JS) and the plain-Markdown principles essays (`06-embrace-change.md`, `15-leave-it-better.md` — `.md` has no JSX support at all, unlike `.mdx`). If either constant date ever changes, grep for `8 years`/`eight years` across `src/content/` **and `e2e/work.spec.ts`** (which separately hardcodes the case study title for its own assertion) and update those literals by hand.
- **CSP lives in `netlify.toml`**, not just in markup. If you add any third-party script (analytics, embeds, etc.), update the `Content-Security-Policy` header there too — there's a `TODO` already marking where Plausible will go.
- **`netlify.toml` is formatted by `prettier-plugin-toml`**, with `indentEntries`/`indentTables`/`alignEntries` enabled in `.prettierrc.json` specifically to preserve its indentation and column-aligned `=` signs (the plugin's defaults flatten both). Run `npm run format` rather than hand-tuning spacing there.
- **Dark mode** is a manual `.dark` class on `<html>`, set by an inline pre-paint script in `src/layouts/BaseLayout.astro` and toggled by `ThemeToggle.tsx` via `localStorage`. Don't introduce a theming library for this.
- **View Transitions** (`<ClientRouter />` in `BaseLayout.astro`) swap page content client-side instead of doing a full reload. A `<script>` module's top-level code only runs once per browser session — so any interactive component that isn't `transition:persist`-ed (unlike `Header.astro`, which is) must wrap its setup in a function and register it on `document.addEventListener('astro:page-load', setup)`, or it silently stops working the second time a user soft-navigates to that page. See `ImageLightbox.astro` for the pattern; the bug it fixes is easy to miss because a hard page reload (or `page.goto()` in tests) always works fine.
- **Desktop and mobile nav links share one `NavLink.astro` component** (`src/components/layout/`, `href`/`label`/`pathname`/`variant` props, `variant: 'desktop' | 'mobile'`), rather than `Header.astro` repeating near-identical `navItems.map()` loops per breakpoint. This follows the same "one shared source, not two copies" precedent as `WorkGrid.astro`/`about.ts` above — extracted at its 2 call sites rather than waiting for the "4th identical copy" threshold `SectionHeader.astro`/`PageHeader.astro`/`InterlinkRow.astro` used: that threshold exists to avoid premature abstraction for speculative _future_ duplication, which doesn't apply here since desktop/mobile nav is a fixed, closed set (there will _never_ be a 3rd or 4th variant). The two variants still differ visually — desktop gets the `relative`/`after:*` underline-on-hover treatment, mobile gets `block py-3` stacked spacing with no underline (mobile links aren't `relative`-positioned for one) — controlled by a single `isDesktop` branch inside `class:list`, not two separate templates. Each rendered `<a>` also carries `data-nav-variant={variant}`, purely so the client-side script below can tell which treatment a link needs without re-deriving it from which container the link lives in.
- **`src/utils/nav-active.ts` is the single source of truth for both "is this nav link active" and "what does active look like"**, imported by both `NavLink.astro`'s server-side render and `Header.astro`'s client-side `updateActiveNav()` script (confirmed working: `astro`'s Vite pipeline resolves the `@/*` tsconfig alias inside a plain, non-`is:inline` `<script>` tag same as it does in frontmatter). `isNavLinkActive(pathname, href)` excludes anchor-only hrefs (`/#contact`) and special-cases `href === '/'` to require an exact match rather than a prefix match (every pathname starts with `/`, so an unguarded `startsWith` would mark a future home-page nav item permanently active). `NAV_LINK_ACTIVE_CLASS`/`NAV_LINK_INACTIVE_CLASSES`/`NAV_LINK_DESKTOP_UNDERLINE_ACTIVE_CLASS` are the shared class-name constants both sides toggle — extracted after an early version of this file hardcoded the same class strings independently in `NavLink.astro`'s `class:list` and in the client script's `classList.toggle` calls, which would have silently drifted the next time either side's active-state styling changed without the other.
- **The flip side of `transition:persist`: a persisted element also keeps stale server-rendered state across soft navigations, not just its JS listeners.** `Header.astro`'s nav links compute their "active" state (`isNavLinkActive`, `class:list`, `aria-current`) from `Astro.url.pathname` at render time — correct on a hard load or `page.goto()`, but since `<header>` is `transition:persist`-ed, a client-side nav (e.g. clicking a nav link) swaps the page body while leaving the _old_ header DOM in place, so the active-link styling stays pointed at whichever page was current before the navigation. Fixed with an `updateActiveNav()` function in `Header.astro`'s script that re-derives active state from `window.location.pathname` and toggles the same classes/`aria-current` imperatively for both nav lists (desktop's `after:w-full` underline toggle is desktop-only), run once on load and again on every `astro:page-load` — the same event `ImageLightbox.astro` uses, but here re-running a state update rather than re-attaching listeners. `e2e/navigation.spec.ts`'s "active nav link updates after client-side navigation" test covers both navs; a `page.goto()`-only test wouldn't catch it; a click-through navigation test is required.
- **Every page uses `<Main>` (`src/components/layout/Main.astro`), not a bare `<main>`.** `BaseLayout.astro` renders a "Skip to main content" link (`href="#main-content"`, visually hidden until focused via `sr-only focus:not-sr-only`) as the first element in `<body>`, before `<slot />`, so it's the first focusable element on every page regardless of what that page renders. `Main.astro` is the link's target — it hardcodes `id="main-content"` and `tabindex="-1"` (without the latter, `<main>` isn't natively focusable, so activating the link scrolls the viewport there but leaves DOM focus on `<body>` — caught by `self-review`, not the initial implementation, which repeated both attributes inline across all 8 pages before this component existed to centralize them) and forwards a `class` prop the same way `InitialsAvatar.astro` does, so each page's own layout classes (e.g. `blog/index.astro`'s `mx-auto max-w-3xl px-6 py-24 md:py-32`) still apply. A new page needs to import and use `<Main>` in place of `<main>` to stay covered — forgetting it silently breaks the skip link for that one page without erroring anywhere. Header.astro's own `z-50` sticky positioning means the skip link itself needs a higher `z-[60]` to render above it when focused, and a `bg-card` (not `bg-background`) fill to be visually distinct from the page behind it — both discovered by screenshotting the focused state, not by reading the code. `e2e/navigation.spec.ts`'s "skip link moves keyboard focus to main content" test covers this.
- **Case study screenshots get a lightbox automatically.** Any `<Image>` inside a `<figure>` within a case study's MDX body is picked up by `ImageLightbox.astro` (mounted once in `CaseStudyLayout.astro`) — click/tap to enlarge, with gallery navigation across the whole article. No per-image markup or setup needed; don't reach for a library or React for this.
- **A `coverImage` taller than the home card's `aspect-[16/10]` container needs `position="top"` on the `<Image>` in `WorkCard.astro`, not a CSS `object-position` class.** When `<Image>` is given explicit `width`/`height` that don't match the source aspect ratio, Astro's image service (Sharp) crops server-side at generation time, before the browser ever sees it — so the served file is already exactly 640×400 and a CSS `object-cover`/`object-top` class on the `<img>` has nothing left to crop. Use the `<Image>` component's own `position` prop (maps to Sharp's crop anchor, same syntax as `object-position`) to control which part of a full-page screenshot survives the crop.
- **`WorkCard.astro` takes a `showCover` prop (default `true`) that `WorkSection.astro` sets to `false` only for the featured card.** It doesn't hide the cover outright — it adds `md:hidden` to the cover `<div>`, so the featured card's screenshot still shows on mobile but is suppressed on `md:`+ viewports, where the card spans all 3 grid columns and a full-width screenshot would otherwise dominate the row. The `<img>` is still present in the DOM either way (just CSS-hidden on desktop), so Playwright's `toHaveCount()` against it doesn't reflect visibility — use `toBeVisible()`/viewport-specific assertions instead if a test needs to distinguish the two cases.
- **Screenshot-heavy case studies get a sibling `<slug>.sources.txt`** next to the `.mdx` file (e.g. `brand-evolution.sources.txt`, `voices-conference-website.sources.txt`) — a plain-text provenance log mapping each screenshot to its source URL (Wayback Machine snapshot or live capture), exact capture date, and any correction history. It's not loaded by the site or referenced in code; it exists so a caption's date claim is traceable and so corrections (e.g. a mislabeled date) are documented rather than silently fixed. Add one when a case study's screenshots come from archived/external sources, and check it before trusting an existing screenshot's caption date.
- **A `<figcaption>` (or any JSX element) whose text content lands on its own line gets silently wrapped in a `<p>` by MDX's markdown processor** — text immediately adjacent to the opening tag is parsed as inline phrasing, but text separated by a newline is parsed as a block-level paragraph. Since Prettier breaks long lines onto their own line once they exceed its print width, this means a caption's rendered markup can flip between plain text and `<p>`-wrapped purely based on string length, with no explicit `<p>` anywhere in the source. Fix by wrapping the caption text in a JS string expression instead of plain JSX children, e.g. `<figcaption>{'March 2021 — Bananatag merger announcement'}</figcaption>` — a `{}` expression is parsed as JS, not markdown, so it's never subject to this rule regardless of how Prettier wraps it.
- **In plain `.astro` templates (not MDX), text that ends a line with only a line break before the next inline tag compiles to zero whitespace, not one space.** Unlike JSX's line-join behavior, `from\n<a>LinkedIn</a>` in `.astro` markup rendered as `fromLinkedIn` in the built HTML with no space at all — confirmed by grepping `dist/*.astro`'s compiled output, not just eyeballing the source (see `recommendations.astro`'s LinkedIn link). Fix with an explicit `{' '}` expression between the text and the tag when they need to stay on separate lines. A different mechanism from the MDX figcaption issue below (Astro's own compiler vs. MDX's markdown processor), but the same category of gotcha — verify in the built output whenever text sits on its own line next to a tag.
- **Multi-line `{/* */}` JSX comments in `.mdx` files get corrupted by Prettier's MDX printer** — it reformats the comment body as markdown and mangles the `*/` delimiters, which breaks the build. Keep MDX comments to one `{/* ... */}` per line instead of a single multi-line block; see the commented-out import block in `brand-evolution.mdx` for the pattern.
- **Color tokens** in `src/styles/global.css` (`--color-muted`, `--color-accent`, etc.) have been tuned to meet WCAG AA/AAA contrast against their usage context. Treat color value changes as accessibility-sensitive, not pure style edits — check contrast ratios before adjusting them.
- **Prefer a named Tailwind palette swatch (`rose-700`, `blue-800`, …) over an arbitrary-value color (`text-[#c70036]`) when picking a one-off UI color**, e.g. a new category badge. A hand-picked hex is harder to grep for, harder to reason about relative to the rest of the palette, and easy to get subtly wrong on contrast/hue-separation math without actually rendering it — see `category-colors.ts`'s `CATEGORY_BADGE_CLASSES` (issue #62), which went through exactly that arbitrary-hex detour before landing on `rose-700`/`yellow-800`, chosen because they were close enough to the hand-tuned values to be visually equivalent. Only reach for an arbitrary value if no swatch in Tailwind's default palette is close enough — check by comparing rendered badges/elements side by side, not by eyeballing a large color swatch or comparing raw hex codes.
- **Tailwind v4's preflight deliberately leaves `<button>` at the browser's native cursor (`default`), not `pointer`** — fixed globally via a `button:not(:disabled)`/`button:disabled` rule in `src/styles/global.css`, rather than adding `cursor-pointer` per component. New custom rules in that file that target elements which might also get a Tailwind utility class (cursor, color, etc.) should go inside `@layer base` so a future utility class still wins — Tailwind's layer order is `theme, base, components, utilities` (see `node_modules/tailwindcss/index.css`), and **unlayered** CSS always beats **any** layered utility regardless of specificity. The pre-existing unlayered rules above it (`:focus-visible`, `html:has(dialog[open])`) are fine left as-is since nothing competes with them on the same elements.
- **American English spelling** throughout — color not colour, organization not organisation, behavior not behaviour, prioritize not prioritise, etc. Applies to prose (content, README, comments) and extends to direct quotes attributed to other people, where spelling consistency takes priority over verbatim preservation. Doesn't apply to spec-defined identifiers that happen to contain similar substrings (e.g. `aria-labelledby`).
- **No em dashes (—, U+2014) in site copy** — they read as an AI-generated tell. Applies to prose in `src/content/**`, `src/data/**`, and page/component copy in `src/pages/**`/`src/components/**`; does not apply to code comments (`//`, `{/* */}`) or Playwright test titles/descriptions in `e2e/*.spec.ts`, which are developer-facing, not site copy. Two established exceptions where a dash is deliberately kept rather than removed: quoted testimonials in `src/data/recommendations.ts` (verbatim quotes from real people — the American-English-spelling rule above governs spelling in quotes, not restructuring someone's actual punctuation) and citation-style attribution dashes before a name after a blockquote (e.g. `— Jürgen Klopp` in `15-leave-it-better.md`) which are a distinct, standard convention from a mid-sentence em dash. Two repeating structural patterns get a **plain hyphen** (`-`) rather than a reworded sentence: case-study section headings (`## 2018 - The blank page`) and short label:value image captions (`"Before - April 2020, plain HTML, agency-maintained"`, `"2022 - first rebrand"`) in `src/content/work/*.mdx`, and principle frontmatter `title`/`description` fields following a "Main phrase - clarifying phrase" shape in `src/content/principles/*.md` — these are label:value pairs, not prose sentences, so a hyphen swap keeps the pattern intact instead of forcing an awkward rewrite. (All of these hyphens, in captions and principle frontmatter alike, originated as a mechanical em-dash-to-hyphen substitution in commit `ade731dc` — the label:value shape is what makes the hyphen read fine regardless of that origin, not evidence it was a deliberate choice at the time.) It's the pair's _shape_ going forward, not blanket file-wide consistency, that decides the punctuation: a caption or frontmatter field that reads as a full descriptive sentence rather than a short label:value pair gets a colon or comma instead, as in `storyblok-migration.mdx`'s four descriptive-sentence captions (`"Japanese locale at launch: the most immediately legible proof..."`) and principles 05 (title) and 06 (description), edited on a case-by-case basis even though structurally similar principle titles (07, 08, 09, 10, 13, 14, 15) still keep their hyphen. Any other em dash (ordinary body prose) should be reworded using a comma, period, colon, semicolon, or parenthetical, whichever reads most naturally — not a mechanical find-replace.
- **Quote style differs by file type.** Prettier uses single quotes everywhere except `*.css`, `*.md`, `*.mdx`, `*.yml`, and `*.yaml`, which stay double-quoted (see the `overrides` in `.prettierrc.json`) — so double-quoted frontmatter and CSS strings are intentional, not an inconsistency to "fix".
- **`.astro` template markup gets the same low-comment bar as everywhere else in this repo: only comment where the WHY is non-obvious, and never use `<!-- -->`.** Issue #64 found ~40 `<!-- -->` dev annotations (e.g. "Order number", "Two-column: bio text") rendering straight into production HTML — Astro compiles standard `<!-- -->` comments into the build (they ship to every visitor's "View Source"), and `compressHTML` (on by default) only collapses whitespace, it doesn't strip comments of either kind. Almost all of those were pure "what" labels restating the next line (or, in one case, restating the Tailwind classes two lines below), so the fix was deleting them, not relocating them. The handful that survived explain a genuinely non-obvious WHY and are written as `{/* ... */}` — JS-style comments that Astro's compiler drops from the build entirely, verified directly against `@astrojs/compiler`'s `transform()`: the stretched-link-pattern rationale (`WorkCard.astro`, with `PrincipleCard.astro` pointing back to it rather than repeating it — don't let that copy drift back into a full duplicate), the Netlify hidden-form requirement in `ContactSection.astro`, the dark-mode flash-prevention timing in `BaseLayout.astro`, and the decorative-404 `aria-hidden` reasoning in `404.astro`. Astro's own runtime-generated markers (e.g. `<!--astro:end-->`, used by `astro-island` for hydration-boundary detection) are unaffected either way, since those are emitted by the framework at render time, not written as literal source comments. This is lint-enforced, not just convention: `eslint.config.mjs` has a `no-restricted-syntax` rule on the `AstroHTMLComment` AST node (as produced by `astro-eslint-parser`, scoped to `**/*.astro`) that fails `npm run lint`/CI on any new `<!-- -->` in template markup — mirroring the existing `check:trailing-slashes` precedent of turning a convention into a script-enforced check rather than relying on prose alone.

## Commands Claude should run

After any non-trivial change, in this order:

```bash
npm run format:check              # or `npm run format` to auto-fix
npm run lint
npm run typecheck
npm run check:trailing-slashes   # if routes/links/tests changed
npm run build
npm test                          # if components/pages/content changed
```

These mirror the CI jobs in `.github/workflows/ci.yml` (repository-hygiene, format, lint, typecheck, build, test) — if these pass locally, CI should pass.

For non-trivial feature, fix, or refactor work, follow these with the `self-review` skill before considering the change done. It forks an independent subagent with no memory of this conversation to review the diff — reviewing your own just-written code in the same context that wrote it tends to rubber-stamp it. Fix high-confidence bugs it reports directly; surface debatable or stylistic findings instead of changing them unasked. Re-run the relevant steps above if the fixes touched anything they cover.

This only closes the loop when _you_ invoke `self-review` mid-task and stay in the same turn to act on its findings. If a human runs `/self-review` directly as a standalone command, the findings are returned as plain output with nothing to automatically continue the loop — fixing them then requires an explicit follow-up turn.

## Testing

- E2E only, via Playwright, in `e2e/`. Tests run against the plain Astro dev server (`astro dev`, port 4321) — not `netlify dev` — started automatically by `playwright.config.ts`.
- Projects run on Desktop Chrome and Pixel 5; update the relevant `e2e/*.spec.ts` when changing routes, copy, or component structure it asserts on.
- `playwright.config.ts`'s `webServer.env` sets `ASTRO_DEV_BACKGROUND: '1'` — don't remove it. Astro 7 auto-detects agentic CLI environments (e.g. Claude Code, via the `CLAUDECODE` env var) and silently daemonizes `astro dev` in the background instead of blocking in the foreground. Without this override, Playwright loses ownership of that process: the orphaned daemon survives past the test run, and a later `npm run build` can overwrite its shared Vite dependency cache out from under it, breaking React island hydration (`_jsxDEV is not a function`) for every test run that reuses it. See the comment at `playwright.config.ts:37` for the full mechanism.

## Git conventions

This repo follows [Conventional Commits](https://www.conventionalcommits.org/). Format: `type(scope): description`.

- **Type** is required — `feat` and `fix` are the common ones, but any type is fine when it fits better (`docs`, `chore`, `refactor`, `test`, `ci`, `style`, `perf`, …). History so far uses `feat:`, `fix:`, `chore(deps):`, `chore(deps-dev):`, `chore(ci):`.
- **Scope** is optional — a noun in parentheses naming the area touched, e.g. `feat(ci):`, `chore(deps):`. Omit it when the change isn't scoped to one area.
- Dependabot (`.github/dependabot.yml`) handles weekly npm bumps — don't manually bump a dependency version it would otherwise cover.

## Don't

- Don't add a `tailwind.config.js` — config is CSS-first in `global.css`.
- Don't edit `dist/`, `.astro/`, or `.netlify/` — generated/local, gitignored.
- Don't loosen security headers or the CSP in `netlify.toml` without being explicitly asked.
