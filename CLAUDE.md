## Stack facts that shape how to make changes

- **Astro-first, React only where needed.** The only React component is `src/components/ui/ContactForm.tsx`. Everything else is `.astro` — `ThemeToggle.astro` was rewritten off React in issue #187 (see the "Dark mode" bullet below), leaving `ContactForm.tsx` as the sole remaining island. Don't reach for React for new components unless there's real interactivity that needs it.
- **Tailwind v4 is CSS-first** — there is no `tailwind.config.js`. Theme tokens (fonts, colors, animations) live in the `@theme` block in `src/styles/global.css`. **Do not put any `--animate-*` token in `@theme`**, one-shot or infinite (e.g. `--animate-foo: foo 2s infinite` or `--animate-foo: foo 0.5s ease-out both`): Tailwind v4 auto-generates an unconditional `.animate-foo` utility class from every `--animate-*` token regardless of the animation's duration, which overrides any media-query-guarded manual class definition and silently breaks `prefers-reduced-motion` gating. This isn't just a theoretical risk for infinite animations — `--animate-fade-up` (Hero.astro's one-shot entrance fade) shipped with exactly this bug (issue #118's investigation): the guarded copy inside `@media (prefers-reduced-motion: no-preference)` only ever _reapplied_ the animation when motion was fine, while the unconditional `@theme`-generated copy still played it unconditionally, so a `reduce` preference was silently ignored. Define every animation, one-shot or infinite, only as a `@keyframes` + `.animate-foo { animation: ... }` class (with a literal duration, not `var(--animate-foo)`), both inside the `@media (prefers-reduced-motion: no-preference)` block and — matching `.animate-dot-breathe`'s existing pattern — inside `@layer base` too, so a later utility class can't out-cascade it. No `@theme` token, ever, for an `--animate-*` value.
- **`prefers-reduced-motion` gating covers scroll behavior too, not just CSS animations.** `html { scroll-behavior: smooth }` (`src/styles/global.css`) shipped unconditionally for a while — unlike every other animation in this file — so every same-page anchor jump (principle/recommendation card links, the skip link, footer/nav `#contact` links) animated regardless of preference (issue #115). Fixed the same way `.animate-fade-up`/`.animate-dot-breathe` are: nested inside the existing `@media (prefers-reduced-motion: no-preference)` block and wrapped in `@layer base`. A CSS media query can't reach a JS `scrollTo()` call's explicit `behavior` option, though, so `ImageLightbox.astro`'s prev/next navigation (`goTo()`) checks `window.matchMedia('(prefers-reduced-motion: reduce)').matches` at call time (not cached, so a mid-session OS preference change takes effect on the very next scroll) and passes `behavior: 'instant'` instead of `'smooth'` when it matches — the track's Tailwind `scroll-smooth` class was removed entirely since every scroll call now sets `behavior` explicitly, making the CSS-level default redundant. The lightbox's initial open-to-slide jump stays hardcoded `'instant'` regardless of preference on purpose: it's a one-time positioning jump, not a navigation animation, so there's no motion to gate. Any future scroll-triggered UI (another gallery, a scroll-to-anchor feature) needs this same `matchMedia` check on its own JS scroll calls — the global CSS rule only governs native scrolls with no explicit `behavior` option.
- **TypeScript strict mode** (`astro/tsconfigs/strict.json`), path alias `@/*` → `src/*` (see `tsconfig.json`). The `paths` entry is written as `"./src/*"`, not `"src/*"` — `tsconfig.json` has no `baseUrl` (removed, issue #229: it's deprecated since TS 5.0 and would stop working in TS 7.0), and TypeScript requires a `paths` pattern to be explicitly relative (leading `./`) once `baseUrl` is unset, or it fails with `TS5101`/`TS5090` respectively. **`npm run typecheck` (`astro check`) doesn't catch either of those errors** — its diagnostics don't include TypeScript's compiler-option-level diagnostics, confirmed by reproducing both errors with a real `npx tsc --noEmit -p tsconfig.json` while `astro check` stayed clean throughout. Verify any future `tsconfig.json` compiler-option change (not just this one) against plain `tsc --noEmit`, not just `astro check`/`npm run typecheck` — the latter has a blind spot here that cost issue #229 a first, wrong "no-op, safe to remove" conclusion before the real fix (dropping `baseUrl` itself, not just the `ignoreDeprecations` suppressing it) was found. **`noUncheckedIndexedAccess` is also enabled** (issue #227, on top of what `strict.json` alone provides — it's part of `strictest.json`, not `strict.json`), so every array/tuple/`RegExpMatchArray` index access is typed `T | undefined` regardless of a preceding length check the compiler can't correlate with the index. Enabling it flagged 10 sites across 6 files — mostly instances of exactly the "trusted array position" bug class `content-image-sizing.ts`'s own history documents recurring (the `Math.min()`/`.reduce()` fixes, written up in the `add-content` skill), now caught by the type checker instead of relying on review to catch it again. Fix a flagged site with real handling, not a blanket `!`: an early-return/throw guard where the array could genuinely be empty (`ImageLightbox.astro`'s `slides[currentIndex]`, `og/[...slug].png.ts`'s regex match group, `content-image-sizing.ts`'s `merged[merged.length - 1]` and its `ResponsiveGridTiers` fallback tuple access, `verify-netlify-signature.ts`'s JWT-part destructure — all guarded with `if (!x) return`/`throw` rather than asserted away), and a narrow, commented `!` only where a language-level guarantee makes the check genuinely impossible to fail (`schema.ts`'s two `String.split(...)[0]!`, since `split()` always returns at least one element).
- **Node 26** is pinned in `.nvmrc`, `netlify.toml`, and `package.json`'s `engines` field — match it locally. `engines` is strictly enforced, not advisory: a committed root `.npmrc` sets `engine-strict=true` (issue #144), so `npm install`/`npm ci` on a Node version outside `26.x` hard-fails with `EBADENGINE` (exit code 1) instead of warning and proceeding — confirmed against real npm output, not just docs. `.npmrc` is the one deliberate exception to the repository-hygiene CI check's forbidden-tracked-files list (`.github/workflows/ci.yml`'s `repository-hygiene` job) and to `.gitignore`'s local-environment-files block, both of which otherwise treat `.npmrc` as local-only config not meant to be tracked — special-cased in both places specifically so this file can be committed. Every `actions/setup-node` step in `.github/workflows/ci.yml` (pinned to a commit SHA with a version comment, e.g. `actions/setup-node@49933ea5288caeca8642d1e84afbd3f7d6820020 # v4.4.0` — see the Actions-pinning bullet below) reads `node-version-file: ".nvmrc"` rather than its own hardcoded `node-version`, so `.nvmrc` is CI's single source of truth too (issue #145) — bumping the Node version only requires updating `.nvmrc`, `netlify.toml`, and `package.json` by hand, not every CI job. `.nvmrc` holds just the major version (`26`), which `setup-node` resolves to whatever the latest `26.y.z` release is at CI-run time — always inside the `engines` field's `26.x` range, so `engine-strict` can't break CI's own install step as a side effect of a patch release. **Unverified risk worth watching:** Dependabot (`.github/dependabot.yml`) runs its own npm/yarn updater in a sandbox with its own Node runtime, not this repo's `.nvmrc`-pinned one — since Node 26 is very recent (not LTS until Oct 2026), that sandbox may not have it yet, and Dependabot failures don't surface as a GitHub Actions run, so a version mismatch there could silently break automated dependency-update PRs with `EBADENGINE` and nothing in CI to catch it. Confirm the next real Dependabot PR still opens and installs cleanly; if it doesn't, that's the tradeoff this change made.

## Conventions to respect

- **Trailing slashes are mandatory** on every internal route (`trailingSlash: 'always'` in `astro.config.mjs`). Every `href`, `page.goto()`, and `toHaveURL()` must end in `/`. This is enforced in CI by `npm run check:trailing-slashes` (`scripts/check-trailing-slashes.js`) — run it locally after touching any route/link, since a missing slash fails the build job, not just lint. The script derives which routes to check by scanning `src/pages/` itself (each top-level `.astro` file, and each subdirectory with an `index.astro`, becomes a checked static route; a subdirectory that also has a `[slug].astro`/`[...slug].astro` becomes a checked dynamic prefix) rather than hand-listing routes, so a new page or collection route is covered automatically without editing the script. It checks both a literal quoted href (`href="/work/foo/"`) and a computed one — either inline (``href={`/work/${slug}/`}``) or, matching the established convention of extracting the href into a named `const` before use (see `WorkCard.astro`), a `const`/`let` assignment (`` const href = `/work/${slug}/` ``) — by requiring the template literal not end immediately after an interpolation with no trailing `/` literal after it.
- **The `/404` route is the one deliberate exception to trailing slashes, and it's load-bearing for `netlify.toml`'s catch-all redirect.** Despite `trailingSlash: 'always'`, Astro's build internals force `dist/404.html` (and `/500`) to stay flat at the output root rather than `dist/404/index.html` — `node_modules/astro/dist/core/output-filename.js`'s `STATUS_CODE_PAGES` set special-cases just those two routes, unconditionally, regardless of the `trailingSlash`/`build.format` config. `netlify.toml`'s `[[redirects]]` rule targets `/404` (no slash) specifically because of this, and `scripts/check-trailing-slashes.js` excludes `404` from its checked routes (`excludedStaticPageNames`) for the same reason — both are documented inline at their respective locations. This is undocumented, version-specific Astro behavior, not a guaranteed contract: re-verify `dist/404.html` still exists at the build root (`ls dist/404.html`) after any Astro major-version bump, since a change here would silently break the redirect with nothing in CI to catch it.
- **Content collections** (`src/content.config.ts`) define three collections with different ordering rules — easy to mix up:
    - `work/` — order comes from a frontmatter `order` field (filenames become URL slugs, so they can't encode order), validated `.int().nonnegative()`. `coverImage` is optional (uses the `image()` schema helper, not a plain string) — the home page card falls back to its text-only layout when absent. `tags` requires `.min(1)`. **`year` is a `z.string().regex(/^\d{4}(–\d{4})?$/)`** — a plain 4-digit year regex (as issue #120 originally proposed) would have broken every existing case study: all 4 current entries use an en-dash range (`"2018–2026"`, `"2022–2024"`, …) since each spans multiple years of work, not a single-year regex. Check real content before tightening a schema field — a constraint that looks obviously correct from the field name can still be wrong for the field's actual values. **`description` is the single source for the work card teaser, the case-study page's own intro paragraph, JSON-LD, and `BaseLayout`'s meta description/og:description/twitter:description alike — write it at or under ~155 chars so it reads as a good search/social snippet, not just as on-page prose.** `e2e/meta-description-length.spec.ts` guards every page's rendered meta description against that cap. This is a deliberate simplification (issue #183): an earlier version added a separate optional `metaDescription` field so the on-page copy could stay long while only the meta tag got shortened, but the tightened, snippet-length copy read better everywhere it was tried — card teaser and page intro included, not just the meta tag — so the split field was dropped in favor of writing `description` itself short and sharp from the start. The homepage and `/about/` page's own meta descriptions follow the same reasoning one level up: `src/data/site.ts`'s `getDefaultDescription()` is the one shared sentence both pages explicitly pass to `BaseLayout`, replacing two independently hand-written near-duplicates (same facts, reordered). It's also `BaseLayout`'s own fallback `description` default and the RSS feed's channel description — one function for anything that doesn't need its own copy, not a separate always-static `DEFAULT_DESCRIPTION` constant plus a near-duplicate dynamic one; the constant was removed once the two were compared side by side and found to be saying the same thing. **`/work/`'s meta description and `PageHeader` intro shared an identical opening clause the same way (issue #256), but the fix isn't a third `getDefaultDescription()`-style shared function** — that pattern applies when two call sites genuinely want the same sentence (homepage and `/about/` both wanted the identical years/tenure summary); `/work/`'s two strings don't, once fixed: the meta description keeps the years/Staffbase-tenure facts, and the on-page intro now leads with what the page actually contains instead — a case-study count (`(await getPublishedEntries('work')).length`, not hardcoded, matching `PrinciplesSection.astro`'s `totalCount` precedent) and its category spread, with no years/tenure wording at all. A shared function would have forced them back toward saying the same thing; two independently-purposed sentences was the right fix here.
    - `principles/` — order comes from the filename prefix (`01-`, `02-`, …); there's no `order` field. Renaming a file reorders it. Plain `.md` has no components, so a non-English passage (WCAG 3.1.2) is marked with raw inline HTML, e.g. `13-for-conflicts-get-on-a-call.md`'s `<em>"<span lang="de">…</span>"</em>` (issue #286) — don't "tidy" it back to `_…_`, which drops the `lang`.
    - `blog/` — posts default to `draft: true`; never flip to `false` unless asked to publish. `tags` is `z.array(z.string()).min(1)` with **no** `.default([])` — Zod's `.default()` short-circuits `.min(1)` when the field is omitted entirely (only enforcing the minimum when an empty array is passed explicitly), so keeping a default here would have let a post skip tagging outright and defeated the constraint. Every post must specify at least one tag now.
- **The blog has an RSS feed at `/rss.xml` (`src/pages/rss.xml.ts`, issue #122), built with `@astrojs/rss`.** It shares its published-post query — sorted newest-first — with every other blog call site (`blog/index.astro`, `blog/[slug].astro`, and the OG image route) via `src/utils/blog-posts.ts`'s `getPublishedBlogPosts()`, so draft-filtering and sort order can't drift between them the way independent copies could. Feed title/description come from `src/data/site.ts`'s `SITE_NAME`/`getDefaultDescription()`, which `BaseLayout.astro` also imports for its meta tags — that file exists because `.astro` component files can't `export` values (`eslint-plugin-astro`'s `astro/no-exports-from-components` rule blocks it), so they had to live in a plain `.ts` module rather than being exported from `BaseLayout.astro` itself. Each item's `link` is built the same way as everywhere else (`stripContentExtension(post.id)` + trailing slash). `/rss.xml` needs no trailing slash and no entry in `scripts/check-trailing-slashes.js`'s exclusion set — the script only scans top-level `.astro` files when deriving static routes, so a `.xml.ts` endpoint was never in its checked set to begin with. `BaseLayout.astro`'s `<head>` links to it via a standard `<link rel="alternate" type="application/rss+xml">` autodiscovery tag, and `/blog/` has a small "RSS feed" text link next to its `<h1>`. The feed builds successfully and is simply empty (`<channel>` with no `<item>` elements) while every post is still `draft: true` — that's expected, not a bug, and was verified by inspecting the built `dist/rss.xml` directly rather than assumed.
- **`/.well-known/security.txt` (RFC 9116, issue #280) is an Astro endpoint (`src/pages/.well-known/security.txt.ts`), not a static file in `public/`, so its required `Expires` field is recomputed on every build** (build date + 330 days, inside RFC 9116's recommended one-year maximum). A file whose `Expires` has passed is stale per the RFC, and a hand-written static file would get there silently. The endpoint only stays valid if **something deploys to production at least every ~11 months**: Dependabot opens PRs but doesn't merge or deploy them, so a long pause in merges would still let it expire. Its first `Contact` is GitHub's private vulnerability reporting form (enabled in repo settings), matching `SECURITY.md`; keep the two in sync if the reporting channel changes. `e2e/security-txt.spec.ts` guards the fields and the `Expires` window.
- **`src/utils/collections.ts`'s `getPublishedEntries(collection)` is the shared `!data.draft` filter behind both `work` and `blog`** — the two collections whose schema actually has a `draft` field (`principles` doesn't, so it stays on a plain `getCollection('principles')`). `getPublishedBlogPosts()` (`src/utils/blog-posts.ts`, above) is a thin wrapper adding the blog-specific newest-first sort on top; `WorkGrid.astro`, `work/[slug].astro`, and the OG image route's `getStaticPaths` call `getPublishedEntries('work')` directly since none of them need a shared sort order (`WorkGrid.astro` sorts by `order` itself; the other two don't sort at all). Generalized from `getPublishedBlogPosts()` once the identical `getCollection('work', ({ data }) => !data.draft)` predicate reached 3 independent copies across `WorkGrid.astro`, `work/[slug].astro`, and the OG image route — the same "Nth copy" trigger as `stripContentExtension`/`SectionHeader.astro` elsewhere in this file. Keep the generic constrained to `'work' | 'blog'` rather than every `CollectionKey` — a collection without a `draft` field wouldn't type-check against the `!data.draft` filter anyway.
- **`src/utils/slug.ts`'s `stripContentExtension(id)` is the single place that strips a content-collection entry's `.md`/`.mdx` suffix down to its URL slug** — every `work`/`principles`/`blog` call site that builds an href, a `getStaticPaths()` param, or an anchor id from `entry.id`/`post.id` should import it rather than re-inlining `entry.id.replace(/\.mdx?$/, '')`. Extracted after this exact regex reached 8 independent copies across 7 files (issue #112: `WorkCard.astro`, `work/[slug].astro` ×2, `blog/[slug].astro`, `blog/index.astro`, `og/[...slug].png.ts`, plus `PrincipleCard.astro` and `principles.astro` migrated in the same pass) — one of them was missing the trailing slash the others had, which is exactly the drift risk a shared source prevents. `formatBlogDate(date)` (the `toLocaleDateString('en-US', { day: 'numeric', month: 'long', year: 'numeric' })` used by both blog pages) lives in `src/utils/date.ts`, not here — it was briefly colocated in `slug.ts` per the issue's own suggested fix, but split out since it's a date-formatting concern rather than a slug one and this repo's `utils/` files are otherwise one-file-one-concern.
- **The homepage About section (`AboutSection.astro`) and the dedicated `/about/` page (`src/pages/about.astro`) render the same `about.ts` bio in full** — unlike `PrinciplesSection.astro`'s `.slice(0, 6)` teaser, About is deliberately not trimmed on the homepage (both paragraphs + the facts `<dl>` appear in both places). `AboutSection.astro` adds only a "Read more about me" CTA (same `ArrowRight`-icon link idiom as `PrinciplesSection.astro`'s "Read all N principles") pointing at `/about/`, whose extra content is a "How this site is built" section backed by `src/data/stack.ts` (the site's own Astro/Tailwind/React/TypeScript/Netlify stack, distinct from `about.ts`'s facts about Philipp's professional stack — don't conflate the two). On the homepage, `AboutSection` sits right after `WorkSection` and before `PrinciplesSection`/`RecommendationsSection` (`src/pages/index.astro`, `src/data/navigation.ts` follows the same order) — Work still leads for anyone skimming for proof, but personal context comes before the more granular Principles/Recommendations sections, and Recommendations (external social proof) stays the section immediately before Contact. **`stack.ts` is a plain `string[]` of names, not `{ name, role }` pairs** (issue #178) — each pill used to carry a one-sentence "why this tool" description exposed only via a `title` attribute, a WCAG hover-only-content anti-pattern invisible to keyboard-only and touch users. The fix was a deliberate call, not the issue's own first-suggested option: rather than surface that text visibly (e.g. a `<dl>` reusing the facts-section card pattern above it on the same page) or via an `sr-only` span, the user judged the descriptions themselves not worth keeping — most visitors already know why a tool like React or Tailwind gets chosen — so they were dropped entirely instead of worked around. Don't reintroduce a per-item description for this list without that same judgment call being revisited first.
- **The homepage Work section (`WorkSection.astro`) and the dedicated `/work/` page (`src/pages/work/index.astro`) share their collection-fetch-and-grid logic via `WorkGrid.astro`** (`src/components/work/`), rather than each re-querying and re-rendering it — the same "one shared source, not two copies" principle as `about.ts` above, applied to a fetch+markup fragment instead of static prose. `WorkGrid.astro` queries the `work` collection, sorts by `order`, and renders the `[featured, ...rest]` grid using `WorkCard.astro` (also relocated to `src/components/work/`, since it's no longer home-page-exclusive once both call sites use it); each call site just wraps `<WorkGrid />` in its own layout div. Unlike About, Work isn't trimmed for the homepage teaser — both places show the same full 4-card set — so `WorkSection.astro` adds only a "See all work" CTA (same idiom as `AboutSection.astro`'s "Read more about me") pointing at `/work/`. Case study back-links in `CaseStudyLayout.astro` ("← All work" / "← Back to all work") point at `/work/`, not a `/#work` homepage anchor — `navigation.ts`'s `Work` nav item does too, matching how `About` already points at `/about/` rather than `/#about` despite `AboutSection` also living on the homepage.
- **`WorkGrid.astro` takes an `eagerLoadFirst?: boolean` prop, passed only from `work/index.astro`, that eagerly loads two cover images at once rather than one — a deliberate, documented tradeoff, not an oversight.** The true LCP candidate on `/work/` differs by viewport: the featured card's cover on mobile (visible below `PageHeader`), the first non-featured card's cover on desktop (the featured cover is CSS-hidden there via `showCover={false}`/`md:hidden`). Static HTML's `loading`/`fetchpriority` attributes can't be conditioned on a media query, so there's no way to eagerly load only the viewport-correct one without adding a client script — judged disproportionate for this issue's severity, and not what its own suggested fix asked for. `WorkCard.astro`'s `priority` prop sets both unconditionally instead, meaning one of the two eager fetches is always for an image CSS-hides on the current viewport — accepted since both are small, already-optimized WebP covers, not a real bandwidth concern. `WorkSection.astro`'s homepage usage doesn't pass `eagerLoadFirst` at all (defaults `false`, every card stays lazy) since the homepage's LCP element is `Hero.astro`'s `<h1>` text, not an image — eager-loading a work-card cover there would only compete for bandwidth with no LCP benefit. Uses `<Image priority>` (Astro's own prop, confirmed against `astro/dist/assets/internal.js` to set `loading="eager"` + `decoding="sync"` + `fetchpriority="high"` together), not hand-rolled `loading`/`fetchpriority` attributes — a first version set only the latter two, silently leaving `decoding` at the lazy default `"async"` and weakening the optimization; caught by `self-review`, not the initial implementation.
- **`WorkCard.astro` takes a `headingLevel?: 'h2' | 'h3'` prop (default `'h3'`), forwarded through `WorkGrid.astro`, that controls what tag its card title renders as** (issue #176) — `work/index.astro` passes `headingLevel="h2"` so each of the 4 case study titles renders as a real `<h2>` directly under `PageHeader`'s `<h1>`, fixing a WCAG 1.3.1 heading-order jump (`<h1>` straight to `<h3>`, no `<h2>` anywhere on the page). `WorkSection.astro`'s homepage usage doesn't pass it, so cards stay `<h3>` there, correctly nested under that section's own `SectionHeader`-rendered `<h2>` ("Selected work"). A first version of this fix added an invisible `<h2 class="sr-only">Case studies</h2>` before `<WorkGrid />` instead — smaller, and didn't touch the shared card component — but the user rejected it: it satisfies the automated heading-order check while giving sighted and screen-reader users two different document structures, with a heading label ("Case studies") that has no visible on-page referent. The heading-level prop is more work (one prop threaded through both components) but is honest structure — each case study genuinely is a top-level section of `/work/`, not a subsection of an invented umbrella heading, so making its own title the `<h2>` reflects the page's real information architecture rather than gaming the rule. `WorkCard.astro` renders the title via a dynamic tag (`const HeadingTag = headingLevel`, then `<HeadingTag>`) — Astro's supported way to pick an element name from a variable at render time.
- **All five homepage teaser sections (`AboutSection.astro`, `ContactSection.astro`, `PrinciplesSection.astro`, `RecommendationsSection.astro`, `WorkSection.astro`) share their heading+CTA row via `SectionHeader.astro`** (`src/components/home/`, `headingId`/`heading`/`href`/`label` props — the `href`/`label` naming deliberately matches `InterlinkCard.astro`'s link-prop vocabulary below) instead of each repeating the same `h2` + `ArrowRight`-icon CTA link markup — the 4th byte-identical copy (added when `WorkSection.astro` got its own CTA row) is what prompted the extraction (issue #97); `ContactSection.astro` became the 5th call site once Contact got its own dedicated `/contact/` page and the homepage section was trimmed down to a teaser (issue #148). It only owns the `mb-12 flex ...` wrapper `<div>`; the parent `<section id=... aria-labelledby=...>` landmark stays in each call site. Each call site derives a single `const headingId = '...-heading'` in its frontmatter and passes that same variable to both `aria-labelledby` and `<SectionHeader headingId={headingId}>`, rather than repeating the literal string twice, so the two can't drift out of sync. `PrinciplesSection.astro`/`RecommendationsSection.astro` each compose their own dynamic `… {totalCount} …` label (`"Browse all N principles"` / `"Read all N recommendations"` — deliberately different verbs, issue #270) as a template literal before passing it in — the component takes the final `label` string, not a count. - **A `<figcaption>` (or any JSX element) whose text content lands on its own line gets silently wrapped in a `<p>` by MDX's markdown processor** — text immediately adjacent to the opening tag is parsed as inline phrasing, but text separated by a newline is parsed as a block-level paragraph. - **`.mdx` file bodies are not real TypeScript, in two separate, independently-discovered ways — prefer defining any non-trivial constant in a `.ts` module and importing it, rather than declaring it directly in an MDX file's body.** (1) A blank line between an MDX file's `import` block and a subsequent top-level statement ends MDX's "ESM block" parsing — anything after that blank line, even `export const x = 1`, gets swept into MDX's general body/JSX parsing instead of being handled as plain JS, and a `{ key: value }` object literal in that content gets misread as an attempted JSX expression container, failing the build with an oxc parse error at the object's own `:` (e.g. `Could not parse expression with oxc: Expected ',' or ')' but found ':'`). A bare `const` (not `export const`) fails even with no blank line at all — only `import`/`export` statements are recognized as ESM-block content in the first place. (2) Separately and more seriously: `astro check` does not type-check expressions inside an MDX file's body at all, confirmed by intentionally breaking a tier object's shape in an MDX-local `export const` array literal (dropping a required `columns` field) — it passed `npm run typecheck` **and** `npm run build` with zero errors either way, then silently shipped a broken `sizes="...calc((100vw - NaNpx) / undefined)..."` straight into production HTML, caught only by inspecting the built output by hand. Whenever a future case study needs a similarly-reused constant, define it in a `.ts` file and import it — don't reintroduce a local MDX `export const` for anything more structured than a primitive, since neither the build nor the type-checker will catch a mistake in it.

- **`InterlinkCard.astro`'s label text (`Work` / `Principles` / `Recommendations` / `About`) is bold and a darker shade of the accent hue at rest in light mode, but stays plain `text-accent` at rest in dark mode — the two themes are deliberately asymmetric, not a missed case.** Requested as a follow-up to the plum accent change above: the resting label previously used `text-foreground` (neutral, same weight as everything else), which read as flat next to the card's own accent-tinted border/background. Applying that same 75%-toward-black mix to dark mode's accent value (already tuned lighter, `oklch(72% ...)`, specifically so it reads on a near-black page) collapses contrast fast — hand-verified with the same OKLCH→sRGB/WCAG math the accent-color study above used: even a mild 15% darken measured ~4.8:1 against the dark card background, dropping below AA well before a "clearly darker" difference would be visible. So dark mode keeps the plain `text-accent` value at rest instead (the same color `group-hover:text-accent` already used) — still bold and purple, just not literally darker, since darker is the wrong direction for legibility on a dark background. One side effect: in dark mode, hovering no longer changes the label's text color (the border/background tint and arrow shift still animate) since rest and hover now resolve to the same value there — accepted as a minor, harmless asymmetry rather than inventing a third unverified color to preserve a hover transition neither theme strictly needs.
- **`InitialsAvatar.astro`'s initials are bold, and `SectionHeader.astro`'s "See all X"/"Read all N…" CTA link (and its arrow, which inherits `currentColor`) is `text-accent` at rest, not `text-muted`** — both requested in the same follow-up as the `InterlinkCard` bullet above. The two needed different contrast justifications, not one shared one: `SectionHeader.astro`'s link sits directly on the plain page background (`--color-background`), where plain `text-accent` already clears AAA in both themes (the same ≈7.6–7.7:1 figures the accent-color study above computed against page background) — but `InitialsAvatar.astro`'s badge is `bg-accent/10` composited over its parent card's `bg-card` (both its call sites, `RecommendationCard.astro` and `recommendations.astro`, render it inside a `bg-card` container), not the plain page background. Against that actual blended background, `text-accent` measures ≈5.6:1 light / ≈6.7:1 dark — both comfortably clear WCAG AA (4.5:1) but not AAA, a real gap from what an earlier draft of this bullet claimed (caught by an independent `self-review` pass, not the initial implementation, which had assumed the same page-background math applied to both components without checking each one's actual rendering context). `SectionHeader.astro`'s link and `CaseStudyLayout.astro`/`blog/[slug].astro`'s back-links (below) all dropped their now-dead `transition-colors duration-150` along with the redundant `hover:text-accent` — with no hover state left to transition into, the class no longer does anything on those elements (unlike `InterlinkCard`'s dark-mode case, where the wrapping card still animates other color properties on hover, so its own now-redundant transition stays legitimately harmless rather than fully inert). This is the shared CTA row used by all 5 homepage teaser sections (`AboutSection`/`ContactSection`/`PrinciplesSection`/`RecommendationsSection`/`WorkSection`, see the `SectionHeader.astro` bullet below), so the change applies everywhere at once, not per-section. The identical `text-muted`/`hover:text-accent` pattern also existed on `CaseStudyLayout.astro`'s two "← All work"/"← Back to all work" back-links and `blog/[slug].astro`'s two "← All posts" back-links — a plain small text link with no arrow-icon component, just an inline `←`, but visually the same "quiet link, purple on hover" convention — so all four were switched to plain `text-accent` at rest too, for the same consistency reason, rather than left the only remaining instance of the old pattern next to now-purple CTAs everywhere else. `blog/index.astro`'s "RSS feed" link (a smaller, lower-emphasis underlined utility link, not a navigational CTA) was deliberately left alone — it's a different enough affordance that matching it wasn't judged worth doing automatically; revisit only if it reads inconsistently in practice. Card-title hover patterns (`WorkCard`/`PrincipleCard`/`RecommendationCard`/`blog/index.astro`'s `group-hover:text-accent` on the title, `Header.astro`'s logo) were left untouched on purpose — a headline going neutral-to-accent only on hover is a distinct, deliberate convention from a small link being accent-colored at rest, not a copy of the same pattern that drifted.
- **The mobile nav (`#mobile-nav` in `Header.astro`) is an ARIA APG-style disclosure: Escape closes it and returns focus to `#nav-toggle`, and a click/tap anywhere outside both `nav`/`toggle` closes it too** (issue #185) — before this, only the toggle button's own click and a per-link click closed it, so tapping elsewhere on the page (a common mobile gesture) left it stuck open. `openMenu()`/`closeMenu({ focusToggle? })`/`isMenuOpen()` are the shared functions every trigger (toggle click, link click, Escape keydown, outside click) goes through, rather than each duplicating the class/`aria-expanded`/icon toggling inline the way the toggle-click and link-click handlers used to. Outside-click deliberately doesn't refocus the toggle — focus is already wherever the user just clicked, and moving it would be surprising. `isMenuOpen()` checks `getComputedStyle(nav).display !== 'none'`, not just the JS-toggled `hidden` class — `nav` also carries a static `md:hidden`, so a resize/rotation past that breakpoint while the menu was open would otherwise leave the class-only check reporting "open" indefinitely, making the new document-level listeners call `closeMenu()` on every subsequent click/keypress for the rest of the page's session (caught by `self-review`, not the initial implementation — low-severity since every call in that state is an idempotent no-op, but real, unnecessary work on every interaction). The document-level `keydown`/`click` listeners are registered once at module top level, not re-bound on `astro:page-load`, since `<header>` is `transition:persist`ed and `document` itself never changes across client-side navigations.
- **`#mobile-nav` renders as an out-of-flow overlay, not an in-flow panel that pushes page content down** (issue #215) — it used to be a normal block sitting inside `<header>`'s document flow, so opening it grew the sticky header's own height and reflowed every element below by that amount; closing it collapsed the page back. Now `class="absolute inset-x-0 top-full ... bg-background"`, anchored to `<header>`'s own `sticky` positioning (which already qualifies as a containing block for an `absolute` descendant, no extra `relative` needed) — it overlays whatever's beneath rather than displacing it, and needs its own opaque `bg-background` since it no longer shares the header's own box (an `absolute` child doesn't contribute to its ancestor's height, so the header's translucent `bg-background/90` no longer extends down to cover it).
    - **`#mobile-nav-backdrop` is a sibling of `<header>`, not a child of it, despite being Header.astro's own concern** — nesting it inside `<header>` would put it in the header's stacking context, where any explicitly `z-index`ed descendant paints above the header's own normal-flow content (per the CSS stacking spec's paint-order rules), dimming the header bar itself instead of just the page beneath it. As a root-level sibling, its `z-40` compares directly against the header's own `z-50`, so the header bar always paints on top wherever they overlap, while the backdrop still sits above ordinary (non-positioned) page content. It carries its own `transition:persist` (matched by `id`, same as `#site-header`) — without it, a client-side navigation would swap it for an inert copy from the new page and leave the toggle script's `getElementById` reference pointing at a detached node.
    - **The backdrop doubles as the outside-click target, with no dedicated listener** — since it's `fixed inset-0` (full viewport, below the header bar's own `z-50` but above everything else) whenever the menu is open, a click anywhere outside the nav/toggle already lands on the backdrop, which the existing `document.addEventListener('click', ...)` outside-click handler (see the APG disclosure bullet above) already treats as "outside" (`!nav.contains(target) && !toggle.contains(target)`) — no extra wiring needed for it specifically.
    - **The scroll lock (`html:has(#mobile-nav:not(.hidden)) { overflow: hidden }` in `global.css`) is scoped inside `@media (width < 768px)`, matching `#mobile-nav`'s own `md:hidden`** — an earlier version left this unscoped and shipped with exactly the bug `isMenuOpen()`'s own comment already warns about (two bullets up): leaving the menu "open" class-wise while resizing/rotating past `md` makes `md:hidden` visually hide the nav with nothing left to ever remove the `.hidden` class again, which would otherwise strand `overflow: hidden` on `<html>` indefinitely. Caught by `self-review`, not the initial implementation.
    - **The open/close transition is pure CSS, no JS beyond the existing `hidden`-class toggle** — `.animate-mobile-nav-in`/`.animate-mobile-nav-backdrop-in` (both defined the same way as `.animate-fade-up`/`.animate-dot-breathe`: `@keyframes` + `.animate-foo` class, nested inside `@media (prefers-reduced-motion: no-preference)` and `@layer base`, no `@theme` token) stay present in the markup at all times rather than being added/removed by `openMenu()`/`closeMenu()`. A CSS animation doesn't run while `display: none`, and restarts from its `from` state the moment `display` changes to non-`none` — so simply toggling the existing `hidden` class replays the entrance animation on every open, with no JS changes to the toggle functions and no exit animation (closing is still instant, which the issue's own suggestion said was fine to skip).
    - **`openMenu()`/`closeMenu()` toggle the `inert` attribute on `#main-content`/`#site-footer` while the overlay is open** (issue #231) — the backdrop already blocked mouse/touch clicks on background content, but nothing stopped keyboard Tab from walking straight through it into e.g. Hero.astro's LinkedIn button while the nav was still visually open. `inert` removes an element's subtree from both the tab order and the accessibility tree, matching the modal-trap behavior the overlay visually implies. Two gotchas surfaced fixing this, both the same class of bug the scroll-lock bullet above already documents for this component: (1) unlike a CSS-only lock, `inert` is JS-managed state with no media-query fallback, so resizing/rotating past `md` while the menu was marked open would strand `#main-content` permanently inert with no way to undo it — worked around with a `matchMedia('(min-width: 768px)')` `'change'` listener that calls `closeMenu()` whenever the viewport crosses into desktop width. (2) `#main-content`/`#site-footer`, unlike `#mobile-nav-backdrop`, aren't `transition:persist`ed, so `<ClientRouter />` swaps in fresh nodes on every client-side navigation — caching `document.getElementById('main-content')`/`('site-footer')` once at the top of the script (the way `toggle`/`nav`/`backdrop` safely do, since those all live inside the persisted `<header>`) left `openMenu()`/`closeMenu()` toggling `inert` on stale, detached nodes after the first soft nav, with the real visible ones never touched. Fixed by looking them up fresh inside `openMenu()`/`closeMenu()` instead of caching — caught by an independent `self-review` pass, not the initial implementation. `e2e/navigation.spec.ts` covers both the tab-trap itself and the post-navigation stale-reference case.
- **Interactive controls target the WCAG AAA 44×44px touch-target guidance (`size-11`/`h-11 w-11`), not just AA's 24×24px minimum** — `ImageLightbox.astro`'s controls (`h-11 w-11`) were the original example; `ThemeToggle.astro`'s three segment buttons, `Header.astro`'s mobile nav-toggle button, and `Footer.astro`'s social links were all bumped up to match (issue #119), replacing `size-[34px]`/`h-9 w-9`. Use the named `size-11`/`h-11 w-11` scale value, not an arbitrary bracket value, per the arbitrary-vs-named-value preference below. `ThemeToggle.astro`'s inter-segment `gap-[2px]` was widened to `gap-1` at the same time, since three 44px targets packed at the old 2px gap read as cramped even though each one individually cleared the size target. **Growing these controls shrank the mobile header's available width for the "Philipp Storl" logo enough to wrap it onto two lines at a real 320px viewport** (verified with Playwright, not just eyeballed) — `Header.astro`'s inner container padding was changed from a flat `px-6` to responsive `px-4 sm:px-6` to recover the needed room. If a future change grows any header-row control further, re-check the logo at a 320px viewport specifically — neither Playwright project (Desktop Chrome, Pixel 5/393px) covers that width, so nothing in CI would catch a regression here.
- **`ContactForm.tsx` fires one shared assertive summary alert on a failed validation, not a `role="alert"` per field.** An earlier version put `role="alert"` on each of the three per-field error `<p>`s — verified via Chrome DevTools Protocol accessibility-tree inspection (issue #191) that submitting the empty form mounted three simultaneous assertive live regions in the same React commit, competing with each other and with the focus-move announcement that follows a tick later. The per-field `<p>`s are now plain text (still exposed via `aria-describedby` on the focused field); a single `sr-only` `<p role="alert">` announces `"N field(s) need attention."` instead, its count derived from `errors` at render rather than kept in separate state (a first pass duplicated it in an `errorSummary` state variable, flagged by `self-review` as a drift risk). **That summary `<p>` is keyed on a `submitAttempt` counter, bumped on every failed submit** — without it, a second failed attempt with the same error _count_ as the first (even from a different field) produces byte-identical alert text, and React bails on reconciling an unchanged text node, so the region never re-announces. The key forces a remount regardless of whether the text actually changed. `e2e/contact-form.spec.ts` guards both: one test asserts only the summary carries `role="alert"`, another tags the alert's DOM node and confirms it's gone (remounted) after a same-count second attempt.
- **`--color-border` and `--color-border-strong` are two different tokens for two different jobs — don't merge them back into one.** `--color-border` (`oklch(89% 0.006 80)` light / `oklch(21% 0.006 80)` dark) is the default, deliberately subtle border used almost everywhere: dividers, tag pills, filled cards (`bg-card` or similar already gives those an independent, perceivable boundary). `--color-border-strong` (`oklch(60% 0.006 80)` / `oklch(49% 0.006 80)`, clears WCAG 1.4.11's 3:1 non-text-contrast minimum) is reserved for interactive controls that have **no background fill of their own** and would otherwise be genuinely hard to locate at rest — currently `ContactForm.tsx`'s text inputs, `Hero.astro`'s LinkedIn/GitHub buttons, and `404.astro`'s "back home" link, all outline-only pill/field shapes. A first version of this fix (issue #106) darkened `--color-border` globally instead of splitting it, which technically fixed the WCAG finding but visibly over-corrected the site's whole flat aesthetic once live — confirmed by the user reviewing the deployed site, not caught by a screenshot review beforehand. When adding a new bordered interactive element, ask "does this have its own background fill providing a boundary cue, independent of the border?" — if yes, use `border-border`; if it's a bare outline with no fill, use `border-border-strong`.
- **Prefer a named Tailwind palette swatch (`rose-700`, `blue-800`, …) over an arbitrary-value color (`text-[#c70036]`) when picking a one-off UI color**, e.g. a new category badge. A hand-picked hex is harder to grep for, harder to reason about relative to the rest of the palette, and easy to get subtly wrong on contrast/hue-separation math without actually rendering it — see `category-colors.ts`'s `CATEGORY_BADGE_CLASSES` (issue #62), which went through exactly that arbitrary-hex detour before landing on `rose-700`/`yellow-800`, chosen because they were close enough to the hand-tuned values to be visually equivalent. Only reach for an arbitrary value if no swatch in Tailwind's default palette is close enough — check by comparing rendered badges/elements side by side, not by eyeballing a large color swatch or comparing raw hex codes.
- **Tailwind v4's preflight deliberately leaves `<button>` at the browser's native cursor (`default`), not `pointer`** — fixed globally via a `button:not(:disabled)`/`button:disabled` rule in `src/styles/global.css`, rather than adding `cursor-pointer` per component. New custom rules in that file that target elements which might also get a Tailwind utility class (cursor, color, etc.) should go inside `@layer base` so a future utility class still wins — Tailwind's layer order is `theme, base, components, utilities` (see `node_modules/tailwindcss/index.css`), and **unlayered** CSS always beats **any** layered utility regardless of specificity. The pre-existing unlayered rules above it (`:focus-visible`, `html:has(dialog[open])`) are left as-is, but that means a `focus-visible:outline-*` utility can't override the global focus ring: `ImageLightbox.astro`'s `#lightbox-track` (issue #299) sets its white outline in its scoped `<style>` block instead, where the id selector out-specifies `:focus-visible`.
- **American English spelling** throughout — color not colour, organization not organisation, behavior not behaviour, prioritize not prioritise, etc. Applies to prose (content, README, comments) and extends to direct quotes attributed to other people, where spelling consistency takes priority over verbatim preservation. Doesn't apply to spec-defined identifiers that happen to contain similar substrings (e.g. `aria-labelledby`).
- **No em dashes (—, U+2014) in site copy** — they read as an AI-generated tell. Applies to prose in `src/content/**`, `src/data/**`, and page/component copy in `src/pages/**`/`src/components/**`; does not apply to code comments (`//`, `{/* */}`) or Playwright test titles/descriptions in `e2e/*.spec.ts`, which are developer-facing, not site copy. Two established exceptions where a dash is deliberately kept rather than removed: quoted testimonials in `src/data/recommendations.ts` (verbatim quotes from real people — the American-English-spelling rule above governs spelling in quotes, not restructuring someone's actual punctuation) and citation-style attribution dashes before a name after a blockquote (e.g. `— Jürgen Klopp` in `15-leave-it-better.md`) which are a distinct, standard convention from a mid-sentence em dash. Two repeating structural patterns get a **plain hyphen** (`-`) rather than a reworded sentence: case-study section headings (`## 2018 - The blank page`) and short label:value image captions (`"Before - April 2020, plain HTML, agency-maintained"`, `"2022 - first rebrand"`) in `src/content/work/*.mdx`, and principle frontmatter `title`/`description` fields following a "Main phrase - clarifying phrase" shape in `src/content/principles/*.md` — these are label:value pairs, not prose sentences, so a hyphen swap keeps the pattern intact instead of forcing an awkward rewrite. (All of these hyphens, in captions and principle frontmatter alike, originated as a mechanical em-dash-to-hyphen substitution in commit `ade731dc` — the label:value shape is what makes the hyphen read fine regardless of that origin, not evidence it was a deliberate choice at the time.) It's the pair's _shape_ going forward, not blanket file-wide consistency, that decides the punctuation: a caption or frontmatter field that reads as a full descriptive sentence rather than a short label:value pair gets a colon or comma instead, as in `storyblok-migration.mdx`'s four descriptive-sentence captions (`"Japanese locale at launch: the most immediately legible proof..."`) and principles 05 (title) and 06 (description), edited on a case-by-case basis even though structurally similar principle titles (07, 08, 09, 10, 13, 14, 15) still keep their hyphen. Any other em dash (ordinary body prose) should be reworded using a comma, period, colon, semicolon, or parenthetical, whichever reads most naturally — not a mechanical find-replace.
- **Quote style differs by file type.** Prettier uses single quotes everywhere except `*.css`, `*.md`, `*.mdx`, `*.yml`, and `*.yaml`, which stay double-quoted (see the `overrides` in `.prettierrc.json`) — so double-quoted frontmatter and CSS strings are intentional, not an inconsistency to "fix".
- **`.astro` template markup gets the same low-comment bar as everywhere else in this repo: only comment where the WHY is non-obvious, and never use `<!-- -->`.** Issue #64 found ~40 `<!-- -->` dev annotations (e.g. "Order number", "Two-column: bio text") rendering straight into production HTML — Astro compiles standard `<!-- -->` comments into the build (they ship to every visitor's "View Source"), and `compressHTML: true` only collapses whitespace, it doesn't strip comments of either kind. Almost all of those were pure "what" labels restating the next line (or, in one case, restating the Tailwind classes two lines below), so the fix was deleting them, not relocating them. The handful that survived explain a genuinely non-obvious WHY and are written as `{/* ... */}` — JS-style comments that Astro's compiler drops from the build entirely, verified directly against `@astrojs/compiler`'s `transform()`: the stretched-link-pattern rationale (`WorkCard.astro`, with `PrincipleCard.astro` pointing back to it rather than repeating it — don't let that copy drift back into a full duplicate), the Netlify hidden-form requirement in `contact.astro`, the dark-mode flash-prevention timing in `BaseLayout.astro`, and the decorative-404 `aria-hidden` reasoning in `404.astro`. Astro's own runtime-generated markers (e.g. `<!--astro:end-->`, used by `astro-island` for hydration-boundary detection) are unaffected either way, since those are emitted by the framework at render time, not written as literal source comments. This is lint-enforced, not just convention: `eslint.config.mjs` has a `no-restricted-syntax` rule on the `AstroHTMLComment` AST node (as produced by `astro-eslint-parser`, scoped to `**/*.astro`) that fails `npm run lint`/CI on any new `<!-- -->` in template markup — mirroring the existing `check:trailing-slashes` precedent of turning a convention into a script-enforced check rather than relying on prose alone.
- **`eslint-plugin-react-hooks` is deliberately configured with only `rules-of-hooks` (error) and `exhaustive-deps` (warn), not its `recommended-latest` flat config**, scoped to `**/*.tsx` (`ContactForm.tsx`, the sole remaining React island — Astro components don't use hooks). As of v7, `recommended-latest` bundles a much larger, React-Compiler-oriented rule set (`purity`, `set-state-in-effect`, `static-components`, etc.) beyond the classic two hook-correctness rules — confirmed by trying it against the two-island codebase this config was originally scoped for: `react-hooks/set-state-in-effect` immediately flagged `ThemeToggle.tsx`'s mount-only `localStorage` read inside a `useEffect` (that component has since been rewritten off React entirely, issue #187, but the config's own scoping and this reasoning for it are unchanged). Don't widen this to `recommended-latest` "for completeness" without deliberately deciding to also fix whatever it newly flags — it's a different, stricter scope than "catch hook bugs," which is what issue #111 asked for.

## Commands Claude should run

After any non-trivial change, in this order:

```bash
npm run format:check              # or `npm run format` to auto-fix
npm run lint
npm run typecheck
npm run check:trailing-slashes   # if routes/links/tests changed
npm run check:audit              # if package.json/package-lock.json changed
npm run build
npm run check:font-preloads      # after every build (checks dist/)
npm test                          # if components/pages/content changed
```

These mirror the CI jobs in `.github/workflows/ci.yml` (repository-hygiene, lint, format, typecheck, audit, build, test) — if these pass locally, CI should pass. The `contrast` job isn't in this list on purpose: it's report-only and never fails the build (see the bullet above), so it's not part of the "CI should pass" guarantee this sequence gives — run `npm run test:contrast && npm run check:contrast` separately if you want to check it locally after touching page markup or color tokens.

For non-trivial feature, fix, or refactor work, follow these with the `self-review` skill before considering the change done. It forks an independent subagent with no memory of this conversation to review the diff — reviewing your own just-written code in the same context that wrote it tends to rubber-stamp it. Fix high-confidence bugs it reports directly; surface debatable or stylistic findings instead of changing them unasked. Re-run the relevant steps above if the fixes touched anything they cover.

This only closes the loop when _you_ invoke `self-review` mid-task and stay in the same turn to act on its findings. If a human runs `/self-review` directly as a standalone command, the findings are returned as plain output with nothing to automatically continue the loop — fixing them then requires an explicit follow-up turn.

## Testing

- E2E only, via Playwright, in `e2e/`. Tests run against the plain Astro dev server (`astro dev`, port 4321) — not `netlify dev` — started automatically by `playwright.config.ts`.
- Projects run on Desktop Chrome and Pixel 5; update the relevant `e2e/*.spec.ts` when changing routes, copy, or component structure it asserts on.
- `playwright.config.ts`'s `webServer.env` sets `ASTRO_DEV_BACKGROUND: '1'` — don't remove it. Astro 7 auto-detects agentic CLI environments (e.g. Claude Code, via the `CLAUDECODE` env var) and silently daemonizes `astro dev` in the background instead of blocking in the foreground. Without this override, Playwright loses ownership of that process: the orphaned daemon survives past the test run, and a later `npm run build` can overwrite its shared Vite dependency cache out from under it, breaking React island hydration (`_jsxDEV is not a function`) for every test run that reuses it.
    - **The same failure mode also happens from a manually-started dev server, not just Playwright's own — and `pkill -f "astro dev"` isn't reliable cleanup for it.** `npm run dev` is `netlify dev`, which spawns `astro dev` as a child of its own `npm run dev:astro` wrapper process; a `pkill -f "astro dev"` (even with `ASTRO_DEV_BACKGROUND=1` set for the session) can miss that child and leave it bound to port 4321. `npm test` doesn't detect this — Playwright's `webServer` config happily reuses whatever's already listening on the port rather than erroring or starting its own — so a subsequent `npm run build` (e.g. as part of `preflight`) silently corrupts that stray server's Vite dependency cache out from under it, and the test run that follows fails real-looking tests (`e2e/contact-form.spec.ts`/`e2e/contact.spec.ts`'s `waitForFunction: Test timeout of 30000ms exceeded` errors, the hydration-fiber-property guard those tests use never resolving) that have nothing to do with whatever was actually changed. Clearing `node_modules/.vite` does **not** fix this — the stale server is still holding the old state; the actual fix is finding and killing the real PID (`lsof -ti:4321`, not just a name-pattern `pkill`) and confirming the port is free before rerunning. After any manual `npm run dev`/`netlify dev` session used for visual verification, always check `lsof -ti:4321` is empty before trusting a subsequent `npm test` result — don't assume `pkill`/`kill` on the process you started actually worked.
- **A real `.click()` on anything near the bottom of the viewport (e.g. `Footer.astro`'s links) can flake on the mobile project with `<astro-dev-toolbar>` intercepts pointer events.** Astro's dev toolbar overlay only renders under `astro dev` (never in a real `build`/`preview`, so this is purely a test-environment artifact, not a production bug), and on the Pixel 5 viewport it sits over the footer often enough to fail Playwright's actionability check after the default retry window. `e2e/contact.spec.ts`'s footer-link test hit this and works around it by asserting the `href` attribute directly instead of clicking through — the same pattern already used for the LinkedIn/GitHub link assertions in that file — rather than `force: true` (which would skip the check entirely, including on a stray real overlap) or disabling the dev toolbar globally (bigger blast radius than one flaky test warrants). Prefer an attribute assertion over a real click for any future test targeting a footer (or otherwise bottom-of-viewport) link where the click itself isn't the thing under test.

## Git conventions

This repo follows [Conventional Commits](https://www.conventionalcommits.org/). Format: `type(scope): description`.

- **Type** is required — `feat` and `fix` are the common ones, but any type is fine when it fits better (`docs`, `chore`, `refactor`, `test`, `ci`, `style`, `perf`, …). History so far uses `feat:`, `fix:`, `chore(deps):`, `chore(deps-dev):`, `chore(ci):`.
- **Scope** is optional — a noun in parentheses naming the area touched, e.g. `feat(ci):`, `chore(deps):`. Omit it when the change isn't scoped to one area.
- Dependabot (`.github/dependabot.yml`) handles weekly npm and GitHub Actions (SHA-pinned, see above) bumps — don't manually bump a dependency or an Actions pin it would otherwise cover.
