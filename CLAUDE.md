## What this is

Personal portfolio site for Philipp Storl — Astro v7, Tailwind v4, a couple of React islands, deployed on Netlify. Content (case studies, principles, blog posts) lives in `src/content/` as Markdown/MDX with zod-validated frontmatter.

## Stack facts that shape how to make changes

- **Astro-first, React only where needed.** The only React components are `src/components/ui/ContactForm.tsx` and `src/components/ui/ThemeToggle.tsx`. Everything else is `.astro`. Don't reach for React for new components unless there's real interactivity that needs it.
- **Tailwind v4 is CSS-first** — there is no `tailwind.config.js`. Theme tokens (fonts, colors, animations) live in the `@theme` block in `src/styles/global.css`. **Do not put any `--animate-*` token in `@theme`**, one-shot or infinite (e.g. `--animate-foo: foo 2s infinite` or `--animate-foo: foo 0.5s ease-out both`): Tailwind v4 auto-generates an unconditional `.animate-foo` utility class from every `--animate-*` token regardless of the animation's duration, which overrides any media-query-guarded manual class definition and silently breaks `prefers-reduced-motion` gating. This isn't just a theoretical risk for infinite animations — `--animate-fade-up` (Hero.astro's one-shot entrance fade) shipped with exactly this bug (issue #118's investigation): the guarded copy inside `@media (prefers-reduced-motion: no-preference)` only ever _reapplied_ the animation when motion was fine, while the unconditional `@theme`-generated copy still played it unconditionally, so a `reduce` preference was silently ignored. Define every animation, one-shot or infinite, only as a `@keyframes` + `.animate-foo { animation: ... }` class (with a literal duration, not `var(--animate-foo)`), both inside the `@media (prefers-reduced-motion: no-preference)` block and — matching `.animate-dot-breathe`'s existing pattern — inside `@layer base` too, so a later utility class can't out-cascade it. No `@theme` token, ever, for an `--animate-*` value.
- **`prefers-reduced-motion` gating covers scroll behavior too, not just CSS animations.** `html { scroll-behavior: smooth }` (`src/styles/global.css`) shipped unconditionally for a while — unlike every other animation in this file — so every same-page anchor jump (principle/recommendation card links, the skip link, footer/nav `#contact` links) animated regardless of preference (issue #115). Fixed the same way `.animate-fade-up`/`.animate-dot-breathe` are: nested inside the existing `@media (prefers-reduced-motion: no-preference)` block and wrapped in `@layer base`. A CSS media query can't reach a JS `scrollTo()` call's explicit `behavior` option, though, so `ImageLightbox.astro`'s prev/next navigation (`goTo()`) checks `window.matchMedia('(prefers-reduced-motion: reduce)').matches` at call time (not cached, so a mid-session OS preference change takes effect on the very next scroll) and passes `behavior: 'instant'` instead of `'smooth'` when it matches — the track's Tailwind `scroll-smooth` class was removed entirely since every scroll call now sets `behavior` explicitly, making the CSS-level default redundant. The lightbox's initial open-to-slide jump stays hardcoded `'instant'` regardless of preference on purpose: it's a one-time positioning jump, not a navigation animation, so there's no motion to gate. Any future scroll-triggered UI (another gallery, a scroll-to-anchor feature) needs this same `matchMedia` check on its own JS scroll calls — the global CSS rule only governs native scrolls with no explicit `behavior` option.
- **TypeScript strict mode** (`astro/tsconfigs/strict.json`), path alias `@/*` → `src/*` (see `tsconfig.json`).
- **Node 26** is pinned in `.nvmrc`, `netlify.toml`, and `package.json`'s `engines` field — match it locally. `engines` is strictly enforced, not advisory: a committed root `.npmrc` sets `engine-strict=true` (issue #144), so `npm install`/`npm ci` on a Node version outside `26.x` hard-fails with `EBADENGINE` (exit code 1) instead of warning and proceeding — confirmed against real npm output, not just docs. `.npmrc` is the one deliberate exception to the repository-hygiene CI check's forbidden-tracked-files list (`.github/workflows/ci.yml`'s `repository-hygiene` job) and to `.gitignore`'s local-environment-files block, both of which otherwise treat `.npmrc` as local-only config not meant to be tracked — special-cased in both places specifically so this file can be committed. Every `actions/setup-node@v4` step in `.github/workflows/ci.yml` reads `node-version-file: ".nvmrc"` rather than its own hardcoded `node-version`, so `.nvmrc` is CI's single source of truth too (issue #145) — bumping the Node version only requires updating `.nvmrc`, `netlify.toml`, and `package.json` by hand, not every CI job. `.nvmrc` holds just the major version (`26`), which `setup-node` resolves to whatever the latest `26.y.z` release is at CI-run time — always inside the `engines` field's `26.x` range, so `engine-strict` can't break CI's own install step as a side effect of a patch release. **Unverified risk worth watching:** Dependabot (`.github/dependabot.yml`) runs its own npm/yarn updater in a sandbox with its own Node runtime, not this repo's `.nvmrc`-pinned one — since Node 26 is very recent (not LTS until Oct 2026), that sandbox may not have it yet, and Dependabot failures don't surface as a GitHub Actions run, so a version mismatch there could silently break automated dependency-update PRs with `EBADENGINE` and nothing in CI to catch it. Confirm the next real Dependabot PR still opens and installs cleanly; if it doesn't, that's the tradeoff this change made.

## Conventions to respect

- **Trailing slashes are mandatory** on every internal route (`trailingSlash: 'always'` in `astro.config.mjs`). Every `href`, `page.goto()`, and `toHaveURL()` must end in `/`. This is enforced in CI by `npm run check:trailing-slashes` (`scripts/check-trailing-slashes.js`) — run it locally after touching any route/link, since a missing slash fails the build job, not just lint. The script derives which routes to check by scanning `src/pages/` itself (each top-level `.astro` file, and each subdirectory with an `index.astro`, becomes a checked static route; a subdirectory that also has a `[slug].astro`/`[...slug].astro` becomes a checked dynamic prefix) rather than hand-listing routes, so a new page or collection route is covered automatically without editing the script. It checks both a literal quoted href (`href="/work/foo/"`) and a computed one — either inline (``href={`/work/${slug}/`}``) or, matching the established convention of extracting the href into a named `const` before use (see `WorkCard.astro`), a `const`/`let` assignment (`` const href = `/work/${slug}/` ``) — by requiring the template literal not end immediately after an interpolation with no trailing `/` literal after it.
- **The `/404` route is the one deliberate exception to trailing slashes, and it's load-bearing for `netlify.toml`'s catch-all redirect.** Despite `trailingSlash: 'always'`, Astro's build internals force `dist/404.html` (and `/500`) to stay flat at the output root rather than `dist/404/index.html` — `node_modules/astro/dist/core/output-filename.js`'s `STATUS_CODE_PAGES` set special-cases just those two routes, unconditionally, regardless of the `trailingSlash`/`build.format` config. `netlify.toml`'s `[[redirects]]` rule targets `/404` (no slash) specifically because of this, and `scripts/check-trailing-slashes.js` excludes `404` from its checked routes (`excludedStaticPageNames`) for the same reason — both are documented inline at their respective locations. This is undocumented, version-specific Astro behavior, not a guaranteed contract: re-verify `dist/404.html` still exists at the build root (`ls dist/404.html`) after any Astro major-version bump, since a change here would silently break the redirect with nothing in CI to catch it.
- **Content collections** (`src/content.config.ts`) define three collections with different ordering rules — easy to mix up:
    - `work/` — order comes from a frontmatter `order` field (filenames become URL slugs, so they can't encode order), validated `.int().nonnegative()`. `coverImage` is optional (uses the `image()` schema helper, not a plain string) — the home page card falls back to its text-only layout when absent. `tags` requires `.min(1)`. **`year` is a `z.string().regex(/^\d{4}(–\d{4})?$/)`** — a plain 4-digit year regex (as issue #120 originally proposed) would have broken every existing case study: all 4 current entries use an en-dash range (`"2018–2026"`, `"2022–2024"`, …) since each spans multiple years of work, not a single-year regex. Check real content before tightening a schema field — a constraint that looks obviously correct from the field name can still be wrong for the field's actual values.
    - `principles/` — order comes from the filename prefix (`01-`, `02-`, …); there's no `order` field. Renaming a file reorders it.
    - `blog/` — posts default to `draft: true`; never flip to `false` unless asked to publish. `tags` is `z.array(z.string()).min(1)` with **no** `.default([])` — Zod's `.default()` short-circuits `.min(1)` when the field is omitted entirely (only enforcing the minimum when an empty array is passed explicitly), so keeping a default here would have let a post skip tagging outright and defeated the constraint. Every post must specify at least one tag now.
- **The blog has an RSS feed at `/rss.xml` (`src/pages/rss.xml.ts`, issue #122), built with `@astrojs/rss`.** It shares its published-post query — `getCollection('blog', ({ data }) => !data.draft)` sorted newest-first — with `blog/index.astro` via `src/utils/blog-posts.ts`'s `getPublishedBlogPosts()`, so draft-filtering and sort order can't drift between the page and the feed the way two independent copies could. Feed title/description come from `src/data/site.ts`'s `SITE_NAME`/`DEFAULT_DESCRIPTION`, which `BaseLayout.astro` also imports for its meta tags — that file exists because `.astro` component files can't `export` values (`eslint-plugin-astro`'s `astro/no-exports-from-components` rule blocks it), so the constants had to live in a plain `.ts` module rather than being exported from `BaseLayout.astro` itself. Each item's `link` is built the same way as everywhere else (`stripContentExtension(post.id)` + trailing slash). `/rss.xml` needs no trailing slash and no entry in `scripts/check-trailing-slashes.js`'s exclusion set — the script only scans top-level `.astro` files when deriving static routes, so a `.xml.ts` endpoint was never in its checked set to begin with. `BaseLayout.astro`'s `<head>` links to it via a standard `<link rel="alternate" type="application/rss+xml">` autodiscovery tag, and `/blog/` has a small "RSS feed" text link next to its `<h1>`. The feed builds successfully and is simply empty (`<channel>` with no `<item>` elements) while every post is still `draft: true` — that's expected, not a bug, and was verified by inspecting the built `dist/rss.xml` directly rather than assumed.
- **`src/utils/slug.ts`'s `stripContentExtension(id)` is the single place that strips a content-collection entry's `.md`/`.mdx` suffix down to its URL slug** — every `work`/`principles`/`blog` call site that builds an href, a `getStaticPaths()` param, or an anchor id from `entry.id`/`post.id` should import it rather than re-inlining `entry.id.replace(/\.mdx?$/, '')`. Extracted after this exact regex reached 8 independent copies across 7 files (issue #112: `WorkCard.astro`, `work/[slug].astro` ×2, `blog/[slug].astro`, `blog/index.astro`, `og/[...slug].png.ts`, plus `PrincipleCard.astro` and `principles.astro` migrated in the same pass) — one of them was missing the trailing slash the others had, which is exactly the drift risk a shared source prevents. `formatBlogDate(date)` (the `toLocaleDateString('en-US', { day: 'numeric', month: 'long', year: 'numeric' })` used by both blog pages) lives in `src/utils/date.ts`, not here — it was briefly colocated in `slug.ts` per the issue's own suggested fix, but split out since it's a date-formatting concern rather than a slug one and this repo's `utils/` files are otherwise one-file-one-concern.
- **The homepage About section (`AboutSection.astro`) and the dedicated `/about/` page (`src/pages/about.astro`) render the same `about.ts` bio in full** — unlike `PrinciplesSection.astro`'s `.slice(0, 6)` teaser, About is deliberately not trimmed on the homepage (both paragraphs + the facts `<dl>` appear in both places). `AboutSection.astro` adds only a "Read more about me" CTA (same `ArrowRight`-icon link idiom as `PrinciplesSection.astro`'s "Read all N principles") pointing at `/about/`, whose extra content is a "How this site is built" section backed by `src/data/stack.ts` (the site's own Astro/Tailwind/React/TypeScript/Netlify stack, distinct from `about.ts`'s facts about Philipp's professional stack — don't conflate the two). On the homepage, `AboutSection` sits right after `WorkSection` and before `PrinciplesSection`/`RecommendationsSection` (`src/pages/index.astro`, `src/data/navigation.ts` follows the same order) — Work still leads for anyone skimming for proof, but personal context comes before the more granular Principles/Recommendations sections, and Recommendations (external social proof) stays the section immediately before Contact.
- **The homepage Work section (`WorkSection.astro`) and the dedicated `/work/` page (`src/pages/work/index.astro`) share their collection-fetch-and-grid logic via `WorkGrid.astro`** (`src/components/work/`), rather than each re-querying and re-rendering it — the same "one shared source, not two copies" principle as `about.ts` above, applied to a fetch+markup fragment instead of static prose. `WorkGrid.astro` queries the `work` collection, sorts by `order`, and renders the `[featured, ...rest]` grid using `WorkCard.astro` (also relocated to `src/components/work/`, since it's no longer home-page-exclusive once both call sites use it); each call site just wraps `<WorkGrid />` in its own layout div. Unlike About, Work isn't trimmed for the homepage teaser — both places show the same full 4-card set — so `WorkSection.astro` adds only a "See all work" CTA (same idiom as `AboutSection.astro`'s "Read more about me") pointing at `/work/`. Case study back-links in `CaseStudyLayout.astro` ("← All work" / "← Back to all work") point at `/work/`, not a `/#work` homepage anchor — `navigation.ts`'s `Work` nav item does too, matching how `About` already points at `/about/` rather than `/#about` despite `AboutSection` also living on the homepage.
- **All five homepage teaser sections (`AboutSection.astro`, `ContactSection.astro`, `PrinciplesSection.astro`, `RecommendationsSection.astro`, `WorkSection.astro`) share their heading+CTA row via `SectionHeader.astro`** (`src/components/home/`, `headingId`/`heading`/`href`/`label` props — the `href`/`label` naming deliberately matches `InterlinkCard.astro`'s link-prop vocabulary below) instead of each repeating the same `h2` + `ArrowRight`-icon CTA link markup — the 4th byte-identical copy (added when `WorkSection.astro` got its own CTA row) is what prompted the extraction (issue #97); `ContactSection.astro` became the 5th call site once Contact got its own dedicated `/contact/` page and the homepage section was trimmed down to a teaser (issue #148). It only owns the `mb-12 flex ...` wrapper `<div>`; the parent `<section id=... aria-labelledby=...>` landmark stays in each call site. Each call site derives a single `const headingId = '...-heading'` in its frontmatter and passes that same variable to both `aria-labelledby` and `<SectionHeader headingId={headingId}>`, rather than repeating the literal string twice, so the two can't drift out of sync. `PrinciplesSection.astro`/`RecommendationsSection.astro` compose their dynamic `Read all {totalCount} …` label as a template literal before passing it in — the component takes the final `label` string, not a count. A future 6th homepage teaser section should reuse this rather than re-inlining the heading+CTA block; it's a `home/`-scoped pattern distinct from `InterlinkCard.astro` below, which is used across dedicated pages rather than homepage sections.
- **`/about/`, `/principles/`, `/recommendations/`, and `/work/` fully interlink each other** via `src/components/ui/InterlinkCard.astro` (`href`/`eyebrow`/`label` props) rendered as a 3-up grid through `src/components/ui/InterlinkRow.astro`, which takes an `items: Array<{ href, eyebrow, label }>` prop and maps it into `InterlinkCard`s inside the shared `grid grid-cols-1 gap-4 sm:grid-cols-3` wrapper — extracted once this grid became the 4th byte-identical copy across these pages (issue #99), the same "Nth copy" trigger as `SectionHeader.astro`/`WorkGrid.astro`/`PageHeader.astro` above/below. `InterlinkRow.astro` deliberately renders only the grid row, not an outer positioning wrapper, because the row's _position_ differs per page: `principles.astro`/`recommendations.astro`/`work/index.astro` give it its own `mx-auto max-w-3xl px-6 pb-32` div right before `<Footer />`, while `about.astro` nests it inside the existing `pb-24` div right after the facts `<dl>` with `mt-10` spacing instead — passed via `InterlinkRow.astro`'s optional `class` prop (`class:list`-merged, the same class-forwarding convention `Main.astro`/`InitialsAvatar.astro` use) rather than baking a second wrapper div into `about.astro`. Each page links to the other three — About → Work/Principles/Recommendations, Principles → About/Work/Recommendations, Recommendations → About/Principles/Work, Work → About/Principles/Recommendations — so adding a fifth page to this square means adding one more `items` entry to each of the four existing pages' arrays, not just the new one (and widening `InterlinkRow.astro`'s grid past `sm:grid-cols-3`). The `eyebrow` copy is written per-direction (e.g. "See these principles in practice" from Recommendations vs. "See how this plays out" from About) rather than reused verbatim, since the same destination reads differently depending on where you're coming from. **`/contact/` (added in issue #148) is deliberately not a member of this square** — it's a dedicated page like the other four, but reachable only from the header nav, the homepage teaser CTA, and the footer mail icon, not from `InterlinkRow`. Don't add it to the four existing pages' `items` arrays without a deliberate decision to change this; it was left out on purpose, not missed.
- **`/about/`, `/principles/`, `/recommendations/`, and `/work/` also share their page-header block via `src/components/ui/PageHeader.astro`** (`eyebrow`/`title` props, intro paragraph as a default `<slot />`), instead of each repeating the same eyebrow `<p>` + `<h1>` + intro `<p>` wrapped in `mx-auto max-w-3xl px-6 pt-24 pb-16 md:pt-32` — the 4th byte-identical copy (added when `/work/` got its own header, #96) is what prompted the extraction (issue #98), the same pattern as `SectionHeader.astro`'s and `WorkGrid.astro`'s extractions above. It lives in `ui/`, not `home/` or `layout/`, matching `InterlinkCard.astro`'s placement immediately above as "used across dedicated pages rather than homepage sections" — distinct from `Header`/`Main`/`Footer`, which are site-wide chrome on every page. The component owns the wrapping intro `<p class="text-lg leading-relaxed text-muted">`; call sites only supply its contents via the slot, which is why `recommendations.astro`'s intro (a LinkedIn link mid-sentence) still works unchanged through the slot rather than needing its own prop.
- **Clickable cards that sit next to static/non-interactive tiles need a visibly different resting state, not just a hover change.** `InterlinkCard.astro` (`src/components/ui/`) originally shared the same `border-border bg-card` treatment as the About page's facts `<dl>` tiles directly above it, and read as more static content rather than a link. Fixed by giving it an always-on accent tint at rest (`border-accent/40 bg-accent/10`, the same `accent/10`-`accent/40` vocabulary `InitialsAvatar.astro`'s badge and the theme toggle's active-state pill already use) so it's visually distinct from neutral bordered tiles before any interaction, then deepening that same tint further on hover (`hover:border-accent/70 hover:bg-accent/15`) plus the site's existing `group-hover:text-accent` heading color and `group-hover:translate-x-0.5` arrow shift — the same hover vocabulary `WorkCard.astro` and `PrinciplesSection.astro`'s CTA link already use, just one step deeper from an already-tinted rest state. A `ring`/`ring-offset` treatment was tried and rejected — visually disconnected from the card against the page background and out of place next to the site's flat, border-only aesthetic (confirmed by user feedback, not just a hunch). Also deliberately not a `shadow-*`/elevation treatment, since the site has zero `box-shadow` usage anywhere. Reuse accent-tint-at-rest + deeper-tint-on-hover for any future card-shaped link that sits near non-interactive content — don't reach for `ring` or shadow.
- **Not every content set needs a content collection.** `work`/`principles`/`blog` all have long-form Markdown/MDX bodies, which is what the `glob()` loader + zod schema in `content.config.ts` is for. `src/data/recommendations.ts` (LinkedIn recommendations — name, title, date, relationship, quote) has none of that: each entry is a short structured record with no rich body, so it follows the plain `interface` + exported `const` array pattern already used by `about.ts`/`hero.ts` instead. Reach for a collection only when entries need Markdown rendering, `getCollection()`-style filtering/`render()`, or per-entry `.md`/`.mdx` files; otherwise a typed data file is less machinery for the same result. `recommendations.ts` uses a `featured: boolean` field (same name as `work`'s) to mark the 6 shown in the homepage teaser — `RecommendationsSection.astro` still `.slice(0, 6)`s the filtered result, mirroring `PrinciplesSection.astro`'s `.slice(0, 6)` cap, so a future `featured: true` addition can't silently grow the homepage section. Adding or removing an entry also requires bumping the hardcoded `toHaveCount(n)` in `e2e/recommendations.spec.ts`'s "shows all recommendations" test — it asserts an exact `<li>` count against `recommendations.length`, so it's a stale-count failure waiting to happen if skipped (caught by `self-review`, not CI, the first time).
- **`InitialsAvatar.astro`** (`src/components/ui/`) is the only avatar/photo-placeholder pattern in the codebase — a circular initials badge (`bg-accent/10`/`border-accent/20`/`text-accent`, same token set as `CategoryBadge.astro`), used because the recommendations feature intentionally omits LinkedIn profile photos. It strips a leading `Dr.`/`Mr.`/`Mrs.`/`Ms.` before computing initials so a title prefix doesn't eat one of the two letters. If a future feature needs a person's photo or avatar, use this component for the no-photo case rather than inventing a second pattern.
- **OG image generation** (`src/utils/og-image.ts`) intentionally uses `@fontsource/fraunces` (non-variable) alongside the variable font used by the site, because Satori can read WOFF/TTF/OTF but not WOFF2, and the variable font only ships WOFF2. Don't consolidate these to "simplify" — it'll break OG images.
- **The hero `<h1>`'s Fraunces font and the header/hero's DM Sans are preloaded in `BaseLayout.astro`**, since they're otherwise only discovered via `global.css`'s `@import` chain, costing an extra round trip on the page's likely LCP element. Preloading a font that's only ever referenced through a `@fontsource*` CSS `@import` needs a real, build-hashed URL (not a guessed `/fonts/...` path or the raw `node_modules` path) — resolved by importing the specific `-latin-` subset `.woff2` file directly in frontmatter with Vite's `?url` suffix (e.g. `import frauncesWoff2Url from '@fontsource-variable/fraunces/files/fraunces-latin-wght-normal.woff2?url'`), which returns the same hashed `/_astro/...` path the CSS `@import` chain resolves to. Preload every weight actually painted above the fold, not just "the default" — DM Sans 500 (`font-medium`) for `NavLink.astro`'s nav links and `Hero.astro`'s availability badge, **and** DM Sans 400 for `Hero.astro`'s subheading `<p>` right below the `<h1>`. An earlier version only preloaded 500 (assuming 400 was "just body text"), missing that the subheading is also above the fold — `self-review` caught it a second time after the first attempt already fixed a different weight mismatch, worth remembering as a reminder to check _every_ above-the-fold element's weight, not stop at the first one found.
- **`ContactForm` hydrates with `client:load` on its own dedicated `/contact/` page (`src/pages/contact.astro`), not `client:visible`.** It used to live on the homepage as the last section, hydrated `client:visible` specifically because most visitors never scrolled that far, deferring React's JS execution cost until the form was about to enter the viewport. Issue #148 moved the actual form off the homepage entirely: `ContactSection.astro` no longer imports or renders `ContactForm` at all, it's now a `SectionHeader`-driven teaser (heading + one line of copy) linking to `/contact/`, following the same homepage-teaser-plus-CTA pattern as `AboutSection.astro`/`WorkSection.astro`. On the dedicated page the form is the primary reason to be there at all, so there's no below-the-fold visitor to defer for, and `client:load` is used instead. The underlying islands-architecture race still exists in principle (a click landing before hydration attaches the React `onSubmit` handler falls through to the form's real native submission — `method="POST"`, no `action` — instead of the intended `fetch`-based flow), just with a much smaller window than a scroll-triggered hydration; `e2e/contact-form.spec.ts` guards against it by waiting for the submit button to carry a React fiber property before ever interacting with the form.
- **`ContactForm.tsx`'s `<input>`/`<textarea>` fields use `text-base` (16px), not `text-sm` (14px), even though the surrounding labels/error text stay `text-xs`.** iOS Safari auto-zooms the viewport on focus whenever a focused form field's computed font-size is under 16px — issue #151 hit exactly this on the contact form. `text-base` is the smallest Tailwind size step that clears the threshold. Labels (`labelBase`) and error messages (`errorBase`) stay `text-xs` since they're not focusable and iOS doesn't zoom for them. Don't drop these fields back to `text-sm` for visual density without reintroducing the zoom bug.
- **`public/favicon.svg` renders in a standalone context with no access to the site's webfonts.** A `<link rel="icon">` SVG doesn't get the page's `@font-face`/`@fontsource` setup (`Fraunces Variable`, `DM Sans`), so any `font-family` there falls back to whatever's installed on the visitor's OS — referencing the site's display font does nothing. At real favicon scale (16-32px) a serif face also reads noticeably worse than a bold sans-serif, so use a system sans-serif stack (`'Helvetica Neue', Arial, sans-serif`) instead. The icon is a solid opaque fill by design, not a `prefers-color-scheme`-aware asset like `BaseLayout.astro`'s `theme-color` meta tags — being opaque, it doesn't need to adapt to browser-chrome light/dark themes the way a transparent icon would, so don't add a light/dark split unless asked. Its `rect fill` is also a third hardcoded hex approximation of `--color-accent`, alongside `og-image.ts`'s `colors.accent` — a standalone `/self-review` run (2026-08-10) caught that a `--color-accent` token change had updated the latter but missed this one, since it isn't mentioned by the "kept in sync by comment" convention documented on the category-badge bullet below. Update all three together when `--color-accent`'s light-mode value changes.

    - **The actual fetch-to-Slack-webhook mechanics (POST, headers, try/catch, `console.error`) live in `netlify/functions/_shared/slack.ts`'s `postToSlack()`, shared by both `csp-report.ts` and `deploy-notification.ts`**, rather than each function repeating its own copy — extracted at the 2nd occurrence rather than waiting for a 3rd/4th copy (the threshold most other shared-component extractions in this file use), a deliberate exception for this specific pair since both functions do the exact same "POST `{text}` to a webhook URL, swallow network errors" operation with nothing else in common to justify keeping them separate. Each call site still owns its own message-formatting (`summarize()`) and passes the finished text plus a call-site-specific error-log message into `postToSlack(webhookUrl, text, errorContext)`. The underscore prefix (`_shared/`) is a Netlify Functions convention — files/directories starting with `_` are excluded from being bundled as their own function, so it's importable via a plain relative import without becoming a third `/.netlify/functions/...` endpoint itself. **`postToSlack()` also checks `response.ok` after the `fetch` resolves** (issue #157) and `console.error`s the status/statusText when it isn't — a revoked/mistyped webhook URL or a Slack-side error used to resolve without throwing, silently going dark with nothing logged anywhere; that logging/observability gap is now closed for both call sites in the one shared function. This only fixes visibility, not the caller-facing contract: `postToSlack()` still returns `void` and never throws, so a Slack-side failure doesn't change the `204`/`200` either function returns to its own caller (Netlify's webhook dispatcher, or the browser sending a CSP report) — by design, since neither caller could usefully act on a different status code, but worth knowing if a future change ever wants Slack delivery failures to be visible beyond the function log.
    - **`deploy-notification.ts` verifies Netlify's `X-Webhook-Signature` JWS before trusting the POST body, and fails closed** (issue #157): `netlify/functions/_shared/verify-netlify-signature.ts`'s `verifyNetlifySignature(rawBody, header, secret)` checks the JWT is `HS256`-signed with `DEPLOY_NOTIFICATION_WEBHOOK_SECRET` (a per-notification secret configured in the Netlify dashboard, dashboard-only like the two Slack URLs above), that its `iss` claim is `"netlify"`, and that its `sha256` claim matches the SHA-256 digest of the raw body — implemented by hand against Node's `node:crypto` (`createHmac`/`timingSafeEqual`/`createHash`) rather than pulling in a JWT dependency for this one narrow use. `jsonwebtoken`/`jws` do exist in `package-lock.json`/`node_modules` today, but only as transitive `devDependencies` of `netlify-cli` — not a direct `package.json` dependency, and not something a production Netlify Function should rely on being present, since a `netlify-cli` upgrade could drop that transitive chain at any time. Both comparisons use `timingSafeEqual` (the HMAC signature, and the `sha256` body-digest claim), not a plain `===`, for consistency even though the digest itself isn't secret. The function reads `req.text()` (not `req.json()`, and wrapped in its own try/catch) so the exact raw bytes are available for the digest, `JSON.parse`s afterward. If `DEPLOY_NOTIFICATION_WEBHOOK_SECRET` isn't configured, or the signature doesn't verify, the function returns `401` (logging why, in both cases) rather than falling back to trusting the body — deliberately different from the two Slack-URL env vars' "silently skip if absent" pattern, since accepting an unauthenticated payload here is exactly the vulnerability the issue was about. **Known gap:** `verifyNetlifySignature()` checks `alg`, the HMAC signature, `iss`, and the body digest, but not any timestamp/freshness claim — a captured valid (header, body, signature) triple stays replayable indefinitely. Low real impact today since `deploy-notification.ts` is a pure Slack relay with no side effects beyond posting a message, but worth revisiting if this verifier is ever reused for a webhook with side effects that matter. **`csp-report.ts` deliberately has no equivalent signature check** — it's hit directly by browsers via the CSP `report-to`/`report-uri` directives (see the bullet above), not by a Netlify Outgoing Webhook notification, so there's no Netlify-signed JWS to verify in the first place; the endpoint is unauthenticated by design, the same as any CSP violation reporting endpoint on the web. Don't add a signature check there under a future pass at this issue's suggested scope — there's no secret to check it against.

Without the allowance the browser blocks the beacon's request and it comes back through our own `csp-report.ts` as a violation, even though it's Netlify's platform feature, not anything added in this repo. Don't remove this thinking it's an unused/forgotten entry — it has no first-party call site to grep for.

- **Dark mode** is a manual `.dark` class on `<html>`, set by an inline pre-paint script in `src/layouts/BaseLayout.astro` and toggled by `ThemeToggle.tsx` via `localStorage`. Don't introduce a theming library for this.
- **`ThemeToggle.tsx`'s active-segment highlight is corrected by a synchronous pre-hydration DOM patch, not by a `useLayoutEffect`/`useEffect` alone** — issue #118's naive fix (a lazy `useState(() => ...)` initializer reading `localStorage`) looked correct but wasn't: `ThemeToggle` is mounted `client:load` (`Header.astro`), so Astro server-renders it at _build_ time (no `localStorage`, always bakes in `'system'`) before the browser ever hydrates it. A lazy initializer that reads the real stored value on the client's first hydration render then mismatches that baked-in SSR markup on `aria-pressed`/`className` — confirmed via a real Chromium hydration test, React 19 does not patch attribute-level hydration mismatches ("This won't be patched up," logged to console), so the toggle got permanently stuck on `'system'` for any visitor with a stored theme, worse than the original brief-flash bug. Swapping to `useLayoutEffect` avoided the mismatch but didn't fix the actual complaint either: it can only correct state _after_ hydration runs, and the SSR-baked `'system'` markup still paints first regardless of which effect corrects it, so the flash was still visible in a real browser (caught by the user, not by any of the 108 e2e tests — none of them assert `aria-pressed` after a real page reload with a pre-set `localStorage` value). The actual fix mirrors `BaseLayout.astro`'s dark-mode pre-paint script: a second `<script is:inline>` in `Header.astro`, placed immediately after `<ThemeToggle client:load />` so the buttons already exist in the DOM, reads `localStorage` synchronously (classic, non-module script — blocks parsing, runs before the deferred `client:load` hydration module and before the browser paints) and directly sets each button's `data-theme-value`-matched `aria-pressed`/class attributes. `ThemeToggle.tsx`'s `getStoredTheme()` computes the exact same value via a plain lazy `useState` initializer, so by the time hydration runs, the live DOM (already patched) matches what React's client render computes — no mismatch, because hydration compares against the current DOM, not the original network bytes. Verified with real Playwright/Chromium runs against a `netlify serve` build (CSP `<meta>` and headers only exist in `build`/`preview` output, never `astro dev`): blocking every hydration `.js` request entirely still leaves the toggle showing the correct segment (proving the sync script alone does the job), and polling the DOM every 5ms under 20x CPU throttling from the earliest possible moment never observed the wrong segment. **This `is:inline` script needed its own hash manually registered in `astro.config.mjs`'s `security.csp.scriptDirective.hashes`** — Astro auto-hashes its own processed `<script>` tags into the CSP `<meta>` allowlist, but not author-written `is:inline` ones (confirmed by testing: even with `netlify.toml`'s header-level `'unsafe-inline'` present, the browser still blocked the unhashed inline script, because the `<meta>`'s hash-only policy and the header's policy both apply and a resource must satisfy every applicable CSP simultaneously). If this script's content ever changes, its hash must be recomputed (see the comment in `astro.config.mjs` for the exact method) or it silently breaks in production with nothing failing in CI — the same class of gap as the Shiki/CSP issue documented below.
- **View Transitions** (`<ClientRouter />` in `BaseLayout.astro`) swap page content client-side instead of doing a full reload. A `<script>` module's top-level code only runs once per browser session — so any interactive component that isn't `transition:persist`-ed (unlike `Header.astro`, which is) must wrap its setup in a function and register it on `document.addEventListener('astro:page-load', setup)`, or it silently stops working the second time a user soft-navigates to that page. See `ImageLightbox.astro` for the pattern; the bug it fixes is easy to miss because a hard page reload (or `page.goto()` in tests) always works fine.
- **Desktop and mobile nav links share one `NavLink.astro` component** (`src/components/layout/`, `href`/`label`/`pathname`/`variant` props, `variant: 'desktop' | 'mobile'`), rather than `Header.astro` repeating near-identical `navItems.map()` loops per breakpoint. This follows the same "one shared source, not two copies" precedent as `WorkGrid.astro`/`about.ts` above — extracted at its 2 call sites rather than waiting for the "4th identical copy" threshold `SectionHeader.astro`/`PageHeader.astro`/`InterlinkRow.astro` used: that threshold exists to avoid premature abstraction for speculative _future_ duplication, which doesn't apply here since desktop/mobile nav is a fixed, closed set (there will _never_ be a 3rd or 4th variant). Both variants get the same active-state language — a `relative`/`after:*` underline that fills in on active/hover — rather than mobile getting a weaker text-color-only treatment: an early version tried that (color-only on mobile) and shipped it, but the user caught in testing that a `text-foreground`/`text-muted` shift alone is too subtle to register as "this is the active page," and asked for the same underline both places instead. The two variants only differ in underline _shape_, driven by the surrounding layout rather than a deliberate stylistic choice: desktop's `<a>` stays inline, so `after:-bottom-0.5` underlines just the text; mobile's `<a>` is `block py-3` (a full-width row, for a larger tap target), so `after:bottom-0` on that same block-level element naturally spans the whole row instead, reading like a tab indicator rather than a text underline. Each rendered `<a>` also carries a bare `data-nav-link` marker, so `Header.astro`'s client-side script can scope its `querySelectorAll` to nav links only (excluding the header's other `<a>`, the logo) without needing to know which variant it is.
- **`src/utils/nav-active.ts` is the single source of truth for both "is this nav link active" and "what does active look like"**, imported by both `NavLink.astro`'s server-side render and `Header.astro`'s client-side `updateActiveNav()` script (confirmed working: `astro`'s Vite pipeline resolves the `@/*` tsconfig alias inside a plain, non-`is:inline` `<script>` tag same as it does in frontmatter). `isNavLinkActive(pathname, href)` excludes anchor-only hrefs (`/#contact`) and special-cases `href === '/'` to require an exact match rather than a prefix match (every pathname starts with `/`, so an unguarded `startsWith` would mark a future home-page nav item permanently active). `NAV_LINK_ACTIVE_CLASS`/`NAV_LINK_INACTIVE_CLASSES`/`NAV_LINK_UNDERLINE_ACTIVE_CLASS` are the shared class-name constants both sides toggle (uniformly, not desktop-only) — extracted after an early version of this file hardcoded the same class strings independently in `NavLink.astro`'s `class:list` and in the client script's `classList.toggle` calls, which would have silently drifted the next time either side's active-state styling changed without the other.
- **The flip side of `transition:persist`: a persisted element also keeps stale server-rendered state across soft navigations, not just its JS listeners.** `Header.astro`'s nav links compute their "active" state (`isNavLinkActive`, `class:list`, `aria-current`) from `Astro.url.pathname` at render time — correct on a hard load or `page.goto()`, but since `<header>` is `transition:persist`-ed, a client-side nav (e.g. clicking a nav link) swaps the page body while leaving the _old_ header DOM in place, so the active-link styling stays pointed at whichever page was current before the navigation. Fixed with an `updateActiveNav()` function in `Header.astro`'s script that re-derives active state from `window.location.pathname` and toggles the same classes/`aria-current`/underline imperatively for every nav link (one `querySelectorAll('#site-header a[data-nav-link]')` pass covers both desktop and mobile, since they now share the same toggle logic), run once on load and again on every `astro:page-load` — the same event `ImageLightbox.astro` uses, but here re-running a state update rather than re-attaching listeners. `e2e/navigation.spec.ts`'s "active nav link updates after client-side navigation" test covers both navs; a `page.goto()`-only test wouldn't catch it; a click-through navigation test is required.
- **Every page uses `<Main>` (`src/components/layout/Main.astro`), not a bare `<main>`.** `BaseLayout.astro` renders a "Skip to main content" link (`href="#main-content"`, visually hidden until focused via `sr-only focus:not-sr-only`) as the first element in `<body>`, before `<slot />`, so it's the first focusable element on every page regardless of what that page renders. `Main.astro` is the link's target — it hardcodes `id="main-content"` and `tabindex="-1"` (without the latter, `<main>` isn't natively focusable, so activating the link scrolls the viewport there but leaves DOM focus on `<body>` — caught by `self-review`, not the initial implementation, which repeated both attributes inline across all 8 pages before this component existed to centralize them) and forwards a `class` prop the same way `InitialsAvatar.astro` does, so each page's own layout classes (e.g. `blog/index.astro`'s `mx-auto max-w-3xl px-6 py-24 md:py-32`) still apply. A new page needs to import and use `<Main>` in place of `<main>` to stay covered — forgetting it silently breaks the skip link for that one page without erroring anywhere. Header.astro's own `z-50` sticky positioning means the skip link itself needs a higher `z-[60]` to render above it when focused, and a `bg-card` (not `bg-background`) fill to be visually distinct from the page behind it — both discovered by screenshotting the focused state, not by reading the code. `e2e/navigation.spec.ts`'s "skip link moves keyboard focus to main content" test covers this.
- **Case study screenshots get a lightbox automatically.** Any `<Image>` inside a `<figure>` within a case study's MDX body is picked up by `ImageLightbox.astro` (mounted once in `CaseStudyLayout.astro`) — click/tap to enlarge, with gallery navigation across the whole article. No per-image markup or setup needed; don't reach for a library or React for this.

Use the `<Image>` component's own `position` prop (maps to Sharp's crop anchor, same syntax as `object-position`) to control which part of a full-page screenshot survives the crop.
- **`WorkCard.astro` takes a `showCover` prop (default `true`) that `WorkSection.astro` sets to `false` only for the featured card.** It doesn't hide the cover outright — it adds `md:hidden` to the cover `<div>`, so the featured card's screenshot still shows on mobile but is suppressed on `md:`+ viewports, where the card spans all 3 grid columns and a full-width screenshot would otherwise dominate the row. The `<img>` is still present in the DOM either way (just CSS-hidden on desktop), so Playwright's `toHaveCount()` against it doesn't reflect visibility — use `toBeVisible()`/viewport-specific assertions instead if a test needs to distinguish the two cases.
- **Screenshot-heavy case studies get a sibling `<slug>.sources.txt`** next to the `.mdx` file (e.g. `brand-evolution.sources.txt`, `voices-conference-website.sources.txt`) — a plain-text provenance log mapping each screenshot to its source URL (Wayback Machine snapshot or live capture), exact capture date, and any correction history. It's not loaded by the site or referenced in code; it exists so a caption's date claim is traceable and so corrections (e.g. a mislabeled date) are documented rather than silently fixed. Add one when a case study's screenshots come from archived/external sources, and check it before trusting an existing screenshot's caption date.
- **A `<figcaption>` (or any JSX element) whose text content lands on its own line gets silently wrapped in a `<p>` by MDX's markdown processor** — text immediately adjacent to the opening tag is parsed as inline phrasing, but text separated by a newline is parsed as a block-level paragraph. Since Prettier breaks long lines onto their own line once they exceed its print width, this means a caption's rendered markup can flip between plain text and `<p>`-wrapped purely based on string length, with no explicit `<p>` anywhere in the source. Fix by wrapping the caption text in a JS string expression instead of plain JSX children, e.g. `<figcaption>{'March 2021 — Bananatag merger announcement'}</figcaption>` — a `{}` expression is parsed as JS, not markdown, so it's never subject to this rule regardless of how Prettier wraps it.
- **In plain `.astro` templates (not MDX), text that ends a line with only a line break before the next inline tag compiles to zero whitespace, not one space.** Unlike JSX's line-join behavior, `from\n<a>LinkedIn</a>` in `.astro` markup rendered as `fromLinkedIn` in the built HTML with no space at all — confirmed by grepping `dist/*.astro`'s compiled output, not just eyeballing the source (see `recommendations.astro`'s LinkedIn link). Fix with an explicit `{' '}` expression between the text and the tag when they need to stay on separate lines. A different mechanism from the MDX figcaption issue below (Astro's own compiler vs. MDX's markdown processor), but the same category of gotcha — verify in the built output whenever text sits on its own line next to a tag.
- **Multi-line `{/* */}` JSX comments in `.mdx` files get corrupted by Prettier's MDX printer** — it reformats the comment body as markdown and mangles the `*/` delimiters, which breaks the build. Keep MDX comments to one `{/* ... */}` per line instead of a single multi-line block; see the commented-out import block in `brand-evolution.mdx` for the pattern.
- **Color tokens** in `src/styles/global.css` (`--color-muted`, `--color-accent`, etc.) have been tuned to meet WCAG AA/AAA contrast against their usage context. Treat color value changes as accessibility-sensitive, not pure style edits — check contrast ratios before adjusting them.
- **Interactive controls target the WCAG AAA 44×44px touch-target guidance (`size-11`/`h-11 w-11`), not just AA's 24×24px minimum** — `ImageLightbox.astro`'s controls (`h-11 w-11`) were the original example; `ThemeToggle.tsx`'s three segment buttons, `Header.astro`'s mobile nav-toggle button, and `Footer.astro`'s social links were all bumped up to match (issue #119), replacing `size-[34px]`/`h-9 w-9`. Use the named `size-11`/`h-11 w-11` scale value, not an arbitrary bracket value, per the arbitrary-vs-named-value preference below. `ThemeToggle.tsx`'s inter-segment `gap-[2px]` was widened to `gap-1` at the same time, since three 44px targets packed at the old 2px gap read as cramped even though each one individually cleared the size target. **Growing these controls shrank the mobile header's available width for the "Philipp Storl" logo enough to wrap it onto two lines at a real 320px viewport** (verified with Playwright, not just eyeballed) — `Header.astro`'s inner container padding was changed from a flat `px-6` to responsive `px-4 sm:px-6` to recover the needed room. If a future change grows any header-row control further, re-check the logo at a 320px viewport specifically — neither Playwright project (Desktop Chrome, Pixel 5/393px) covers that width, so nothing in CI would catch a regression here.
- **`--color-border` and `--color-border-strong` are two different tokens for two different jobs — don't merge them back into one.** `--color-border` (`oklch(89% 0.006 80)` light / `oklch(21% 0.006 80)` dark) is the default, deliberately subtle border used almost everywhere: dividers, tag pills, filled cards (`bg-card` or similar already gives those an independent, perceivable boundary). `--color-border-strong` (`oklch(60% 0.006 80)` / `oklch(49% 0.006 80)`, clears WCAG 1.4.11's 3:1 non-text-contrast minimum) is reserved for interactive controls that have **no background fill of their own** and would otherwise be genuinely hard to locate at rest — currently `ContactForm.tsx`'s text inputs, `Hero.astro`'s LinkedIn/GitHub buttons, and `404.astro`'s "back home" link, all outline-only pill/field shapes. A first version of this fix (issue #106) darkened `--color-border` globally instead of splitting it, which technically fixed the WCAG finding but visibly over-corrected the site's whole flat aesthetic once live — confirmed by the user reviewing the deployed site, not caught by a screenshot review beforehand. When adding a new bordered interactive element, ask "does this have its own background fill providing a boundary cue, independent of the border?" — if yes, use `border-border`; if it's a bare outline with no fill, use `border-border-strong`.
- **Prefer a named Tailwind palette swatch (`rose-700`, `blue-800`, …) over an arbitrary-value color (`text-[#c70036]`) when picking a one-off UI color**, e.g. a new category badge. A hand-picked hex is harder to grep for, harder to reason about relative to the rest of the palette, and easy to get subtly wrong on contrast/hue-separation math without actually rendering it — see `category-colors.ts`'s `CATEGORY_BADGE_CLASSES` (issue #62), which went through exactly that arbitrary-hex detour before landing on `rose-700`/`yellow-800`, chosen because they were close enough to the hand-tuned values to be visually equivalent. Only reach for an arbitrary value if no swatch in Tailwind's default palette is close enough — check by comparing rendered badges/elements side by side, not by eyeballing a large color swatch or comparing raw hex codes.
- **Tailwind v4's preflight deliberately leaves `<button>` at the browser's native cursor (`default`), not `pointer`** — fixed globally via a `button:not(:disabled)`/`button:disabled` rule in `src/styles/global.css`, rather than adding `cursor-pointer` per component. New custom rules in that file that target elements which might also get a Tailwind utility class (cursor, color, etc.) should go inside `@layer base` so a future utility class still wins — Tailwind's layer order is `theme, base, components, utilities` (see `node_modules/tailwindcss/index.css`), and **unlayered** CSS always beats **any** layered utility regardless of specificity. The pre-existing unlayered rules above it (`:focus-visible`, `html:has(dialog[open])`) are fine left as-is since nothing competes with them on the same elements.
- **American English spelling** throughout — color not colour, organization not organisation, behavior not behaviour, prioritize not prioritise, etc. Applies to prose (content, README, comments) and extends to direct quotes attributed to other people, where spelling consistency takes priority over verbatim preservation. Doesn't apply to spec-defined identifiers that happen to contain similar substrings (e.g. `aria-labelledby`).
- **No em dashes (—, U+2014) in site copy** — they read as an AI-generated tell. Applies to prose in `src/content/**`, `src/data/**`, and page/component copy in `src/pages/**`/`src/components/**`; does not apply to code comments (`//`, `{/* */}`) or Playwright test titles/descriptions in `e2e/*.spec.ts`, which are developer-facing, not site copy. Two established exceptions where a dash is deliberately kept rather than removed: quoted testimonials in `src/data/recommendations.ts` (verbatim quotes from real people — the American-English-spelling rule above governs spelling in quotes, not restructuring someone's actual punctuation) and citation-style attribution dashes before a name after a blockquote (e.g. `— Jürgen Klopp` in `15-leave-it-better.md`) which are a distinct, standard convention from a mid-sentence em dash. Two repeating structural patterns get a **plain hyphen** (`-`) rather than a reworded sentence: case-study section headings (`## 2018 - The blank page`) and short label:value image captions (`"Before - April 2020, plain HTML, agency-maintained"`, `"2022 - first rebrand"`) in `src/content/work/*.mdx`, and principle frontmatter `title`/`description` fields following a "Main phrase - clarifying phrase" shape in `src/content/principles/*.md` — these are label:value pairs, not prose sentences, so a hyphen swap keeps the pattern intact instead of forcing an awkward rewrite. (All of these hyphens, in captions and principle frontmatter alike, originated as a mechanical em-dash-to-hyphen substitution in commit `ade731dc` — the label:value shape is what makes the hyphen read fine regardless of that origin, not evidence it was a deliberate choice at the time.) It's the pair's _shape_ going forward, not blanket file-wide consistency, that decides the punctuation: a caption or frontmatter field that reads as a full descriptive sentence rather than a short label:value pair gets a colon or comma instead, as in `storyblok-migration.mdx`'s four descriptive-sentence captions (`"Japanese locale at launch: the most immediately legible proof..."`) and principles 05 (title) and 06 (description), edited on a case-by-case basis even though structurally similar principle titles (07, 08, 09, 10, 13, 14, 15) still keep their hyphen. Any other em dash (ordinary body prose) should be reworded using a comma, period, colon, semicolon, or parenthetical, whichever reads most naturally — not a mechanical find-replace.
- **Quote style differs by file type.** Prettier uses single quotes everywhere except `*.css`, `*.md`, `*.mdx`, `*.yml`, and `*.yaml`, which stay double-quoted (see the `overrides` in `.prettierrc.json`) — so double-quoted frontmatter and CSS strings are intentional, not an inconsistency to "fix".
- **`.astro` template markup gets the same low-comment bar as everywhere else in this repo: only comment where the WHY is non-obvious, and never use `<!-- -->`.** Issue #64 found ~40 `<!-- -->` dev annotations (e.g. "Order number", "Two-column: bio text") rendering straight into production HTML — Astro compiles standard `<!-- -->` comments into the build (they ship to every visitor's "View Source"), and `compressHTML` (on by default) only collapses whitespace, it doesn't strip comments of either kind. Almost all of those were pure "what" labels restating the next line (or, in one case, restating the Tailwind classes two lines below), so the fix was deleting them, not relocating them. The handful that survived explain a genuinely non-obvious WHY and are written as `{/* ... */}` — JS-style comments that Astro's compiler drops from the build entirely, verified directly against `@astrojs/compiler`'s `transform()`: the stretched-link-pattern rationale (`WorkCard.astro`, with `PrincipleCard.astro` pointing back to it rather than repeating it — don't let that copy drift back into a full duplicate), the Netlify hidden-form requirement in `contact.astro`, the dark-mode flash-prevention timing in `BaseLayout.astro`, and the decorative-404 `aria-hidden` reasoning in `404.astro`. Astro's own runtime-generated markers (e.g. `<!--astro:end-->`, used by `astro-island` for hydration-boundary detection) are unaffected either way, since those are emitted by the framework at render time, not written as literal source comments. This is lint-enforced, not just convention: `eslint.config.mjs` has a `no-restricted-syntax` rule on the `AstroHTMLComment` AST node (as produced by `astro-eslint-parser`, scoped to `**/*.astro`) that fails `npm run lint`/CI on any new `<!-- -->` in template markup — mirroring the existing `check:trailing-slashes` precedent of turning a convention into a script-enforced check rather than relying on prose alone.
- **`eslint-plugin-react-hooks` is deliberately configured with only `rules-of-hooks` (error) and `exhaustive-deps` (warn), not its `recommended-latest` flat config**, scoped to `**/*.tsx` (the two React islands only — Astro components don't use hooks). As of v7, `recommended-latest` bundles a much larger, React-Compiler-oriented rule set (`purity`, `set-state-in-effect`, `static-components`, etc.) beyond the classic two hook-correctness rules — confirmed by trying it: `react-hooks/set-state-in-effect` immediately flagged `ThemeToggle.tsx`'s mount-only `localStorage` read inside a `useEffect`, which is intentional, working code, not a bug. Don't widen this to `recommended-latest` "for completeness" without deliberately deciding to also fix whatever it newly flags — it's a different, stricter scope than "catch hook bugs," which is what issue #111 asked for.

## Commands Claude should run

After any non-trivial change, in this order:

```bash
npm run format:check              # or `npm run format` to auto-fix
npm run lint
npm run typecheck
npm run check:trailing-slashes   # if routes/links/tests changed
npm run check:audit              # if package.json/package-lock.json changed
npm run build
npm test                          # if components/pages/content changed
```

These mirror the CI jobs in `.github/workflows/ci.yml` (repository-hygiene, lint, format, typecheck, audit, build, test) — if these pass locally, CI should pass. The `contrast` job isn't in this list on purpose: it's report-only and never fails the build (see the bullet above), so it's not part of the "CI should pass" guarantee this sequence gives — run `npm run test:contrast && npm run check:contrast` separately if you want to check it locally after touching page markup or color tokens.

For non-trivial feature, fix, or refactor work, follow these with the `self-review` skill before considering the change done. It forks an independent subagent with no memory of this conversation to review the diff — reviewing your own just-written code in the same context that wrote it tends to rubber-stamp it. Fix high-confidence bugs it reports directly; surface debatable or stylistic findings instead of changing them unasked. Re-run the relevant steps above if the fixes touched anything they cover.

This only closes the loop when _you_ invoke `self-review` mid-task and stay in the same turn to act on its findings. If a human runs `/self-review` directly as a standalone command, the findings are returned as plain output with nothing to automatically continue the loop — fixing them then requires an explicit follow-up turn.

## Testing

- E2E only, via Playwright, in `e2e/`. Tests run against the plain Astro dev server (`astro dev`, port 4321) — not `netlify dev` — started automatically by `playwright.config.ts`.
- Projects run on Desktop Chrome and Pixel 5; update the relevant `e2e/*.spec.ts` when changing routes, copy, or component structure it asserts on.
- `playwright.config.ts`'s `webServer.env` sets `ASTRO_DEV_BACKGROUND: '1'` — don't remove it. Astro 7 auto-detects agentic CLI environments (e.g. Claude Code, via the `CLAUDECODE` env var) and silently daemonizes `astro dev` in the background instead of blocking in the foreground. Without this override, Playwright loses ownership of that process: the orphaned daemon survives past the test run, and a later `npm run build` can overwrite its shared Vite dependency cache out from under it, breaking React island hydration (`_jsxDEV is not a function`) for every test run that reuses it. See the comment at `playwright.config.ts:37` for the full mechanism.
- **A real `.click()` on anything near the bottom of the viewport (e.g. `Footer.astro`'s links) can flake on the mobile project with `<astro-dev-toolbar>` intercepts pointer events.** Astro's dev toolbar overlay only renders under `astro dev` (never in a real `build`/`preview`, so this is purely a test-environment artifact, not a production bug), and on the Pixel 5 viewport it sits over the footer often enough to fail Playwright's actionability check after the default retry window. `e2e/contact.spec.ts`'s footer-link test hit this and works around it by asserting the `href` attribute directly instead of clicking through — the same pattern already used for the LinkedIn/GitHub link assertions in that file — rather than `force: true` (which would skip the check entirely, including on a stray real overlap) or disabling the dev toolbar globally (bigger blast radius than one flaky test warrants). Prefer an attribute assertion over a real click for any future test targeting a footer (or otherwise bottom-of-viewport) link where the click itself isn't the thing under test.

## Git conventions

This repo follows [Conventional Commits](https://www.conventionalcommits.org/). Format: `type(scope): description`.

- **Type** is required — `feat` and `fix` are the common ones, but any type is fine when it fits better (`docs`, `chore`, `refactor`, `test`, `ci`, `style`, `perf`, …). History so far uses `feat:`, `fix:`, `chore(deps):`, `chore(deps-dev):`, `chore(ci):`.
- **Scope** is optional — a noun in parentheses naming the area touched, e.g. `feat(ci):`, `chore(deps):`. Omit it when the change isn't scoped to one area.
- Dependabot (`.github/dependabot.yml`) handles weekly npm bumps — don't manually bump a dependency version it would otherwise cover.

## Don't

- Don't add a `tailwind.config.js` — config is CSS-first in `global.css`.
- Don't edit `dist/`, `.astro/`, or `.netlify/` — generated/local, gitignored.
- Don't loosen security headers or the CSP in `netlify.toml` without being explicitly asked.
